# CEO 面｜把流程优化变成看得见的流水线和账

> 草案，2026-10-26；2026-11-02 并入 [REPLAN-v11](REPLAN-v11.md)（V11.2、V11.8），以本文的画面与指标为准。

## 1. 要解决什么

化言的价值大多体现在没发生的事上：研发没被打断、业务员不用转述、试样不因条件没问清而返工。参与试用的人很难注意到这些。决赛的主要观众是 CEO 一类的人（董事长、徐总），他们关心钱和产能。

CEO 面把同一批客户需求放在两条流水线上跑，并排展示：一条是传化原来的做法，一条是化言。CEO 能看到每件需求在哪个工位停留、在哪里堆积、绕回了几次；旁边的账本按传化自己的规模，把差别折算成研发产能、客户等待时间和钱。

## 2. 画面

**两条流水线，上下并排**

- 旧线工位照传化研发提供的流程图：需求 → 销售记录 → 产品经理转述 → 研发开发 → 产品经理评价 → 销售开单。
- 化言线就是那张图里的红色虚线，需求直达研发开发。实现这条直达的觉、契和 Agent 画在虚线上，作为三个工位：
  - 契能当场解决的，不进研发，直接到销售开单；
  - 进研发的，带着客户原话和已经问清的条件。
- 货物：一件客户需求，就是传送带上的一个方块。方块按它实际走过的路径移动：
  - 被契当场解决的，从入口直接回到客户手里；
  - 在旧线上条件丢失的，到研发后被退回，或者试样失败后转一圈返工。
- 堆积：工位前排队的货物堆起来，排得越久颜色越深。旧线上研发工位前的货堆，就是这个产品要讲的问题。
- 点开任意一个方块，可以看到这件需求的完整经过：客户原话、觉问了什么、依据的是哪条能力、经过了谁、绕过了谁。这部分复用现有的 `route_of` 和 Month 页的单件视图。

**CEO 能操作的东西**

- 时间倍速：一个月的量，一分钟跑完。
- 来单量滑块：把量翻倍、翻三倍，看旧线先在研发工位堵死，化言线还能消化。
- 规模和单价参数：人数、工时成本、试样成本。默认值用传化给的数，拿不到就用标明为"假设"的保守值。评委可以自己拖动，账本跟着变。
- 撤销一条能力：对应的货物立刻改道流向研发。用来说明效率不是靠放松把关换来的。

**整体风格**

沿用 Apple macOS 工作台的视觉方向，用安静的配色。游戏感靠的是流动、堆积、倍速和滑块，不靠装饰。

## 3. 指标

### 3.0 第一屏的主图：三个岗位的时间构成，从现状变到化言

传化研发提供过一张《岗位工作范围对比（实际现状）》。按图上色条的长度量，三个岗位的时间构成大约是：

| 岗位 | 本职 | 被交叉占用 |
|---|---|---|
| 销售 | 72% | 28% 在做产品经理的事 |
| 产品经理 | 32% | 40% 被销售交叉占用，28% 被研发交叉占用 |
| 研发 | 72% | 28% 在做产品经理的事 |

注意：这些比例是从图上量出来的，那张图很可能是示意。要向对方确认是估计还是统计，确认前标为"传化研发估计"。

CEO 面第一屏就用这三条色条。流水线跑起来以后，被化言接走的交叉部分逐段缩短，本职部分逐段变长：

- 销售做产品经理那部分：觉替销售追问，需求直达研发，销售不再转述；
- 产品经理被销售交叉的部分：产品经理 Agent 在后台起草，产品经理不再逐单转述；
- 研发做产品经理那部分和产品经理被研发交叉的部分：契按研发签过的判断回答，需求到研发时已经完整，研发不再回头补问。

每一段缩短多少，按"对应事件少发生了几次 × 每次耗时"计算。次数取自两条线的对比，耗时取参数，算式可以点开看。

同一位研发还提供过一张《岗位工作范围对比（理想状态）》。上面写着三个岗位各自的核心指标：

- 销售：销售额、回款率、新客户数；
- 产品经理：产品线利润、新品上市数量；
- 研发：新品转化率、专利数、配方稳定性。

时间还回来以后，就落到这些指标对应的工作上。CEO 面在每条色条的本职部分写上对应的指标。"多出的时间产出了多少新品、多少专利"属于长期效果，演示时不给数，只说明时间去了哪里。

### 3.1 主图下面放三个数，每个都要让人一眼看出差距

| 头条 | 含义 | 怎么算 |
|---|---|---|
| **还给研发的时间** | 每月多出的研发工时，换算成"相当于多招 N 名研发"；研发本职占比从 72% 升到多少 | 两条线上研发被拉进来的次数之差 × 每次耗时。徐总关心的就是这个比例 |
| **客户等答复** | 客户从提问到拿到第一个有效答复的时间，原来几天，现在几分钟，同时显示倍数 | 按两条线上每件货的时间戳计算 |
| **一年多出来的钱** | 研发工时、业务员和产品经理工时、少失败的试样三项加总 | 每项都能点开看算式和参数来源 |

"更快响应多赢下的单"这类机会价值单独列出，默认不计入总额，标为"假设"。

### 3.2 流水线旁的指标，每个都对应画面上能看到的东西

| 指标 | 画面上对应的现象 |
|---|---|
| 一件需求经过几个人（旧线约 4 人，化言线 1 人多一点） | 方块经过的工位数 |
| 客户自助解决率 | 从入口直接回到客户的方块所占比例 |
| 到达研发时需求信息的完整率，转述了几次 | 旧线上方块在转述工位逐个掉色 |
| 试样一次通过率、返工圈数 | 绕回去的方块 |
| 各工位排队时长、在制品数 | 货堆 |
| 研发每签一次判断，组织少问了几次 | 契工位放行的方块数，这是契的放大效应 |
| 同样的人手能承接多大来单量 | 来单量滑块拖到哪里，旧线开始堵死 |

### 3.3 每个数都标明来源

账本上每个数字都带一个来源标签：

| 标签 | 含义 |
|---|---|
| 实测 | 试用中真实发生的事件 |
| 回放 | 传化真实历史案例进入化言，客户回答由模型扮演 |
| 模拟 | 模拟的业务月 |
| 推算 | 旧流程线按参数计算的结果 |
| 假设 | 传化没给数时用的默认参数 |

头条下方常驻一个开关："按最保守参数"。答辩时的说法是：参数随你调，按你给的最保守的数，差距仍然是这么多。这个开关就是"假设"标签的用处，也能挡住"数是你们自己编的"这类质疑。

## 4. 两条线的数据从哪里来

### 4.1 化言线：从事件日志还原

每件货的工位路径和时间戳，都能从事件中推出来：

- `turn`、`match`、`recommend` 对应客户和契工位；
- `escalate`、`requirement_*` 对应研发工位；
- `trial`、`market_eval` 对应试样和评价；
- `product_released`、`capability_used` 对应发布和复用；
- `auto_executed`、`question_*` 对应觉和 Agent。

现有的 `route_of` 只处理一个会话，这次要扩成对全部会话做汇总。数据来源有三种，按可信程度排列：

1. **试用实例上的真实单**：量少，但全部是实测。
2. **真实历史案例回放**（`eval/backtest.py`）：要等传化的案例到了才有。
3. **模拟业务月**（`sim/month.py`）：现有运行 `month-jue-0-d20-record` 只跑到第 4 天，共 129 段会话。其中自助解决 95 段，升级 23 次，试样 41 次。

### 4.2 旧流程线：用同一批需求按参数推算

旧线不能凭空画，结构依据如下：

- **访谈（2026-10-08、10-10）**：
  - 客户和业务员只会描述宏观现象，业务员再加工转述，需求就变形，研发白干；
  - L1 问答、L2 产品经理转述、L3 研发调配方，研发再拿到市场端评价，评价后回到产品经理写说明书。
- **研究员聊天（2026-10-12）**：
  - 链条是客户—业务员—产品经理—研发；
  - 岗位偏移的主因是沟通不畅、反复交叉对接；
  - 返工的主因是需求不明确，导致产品不达标而反复返工。

推算方式：同一批需求卡走旧线。每件需求在转述中丢掉哪些条件，按失真对照（`eval/distortion.py`）中 G1 业务员转述组的做法，在同一张卡上逐张重跑得出。该组是规则实现、不调用大模型；现有报告只给了汇总数，即关键信息完整率 0.50、研发需退回比例 0.95。丢了必问条件的需求，到研发后要么回问一轮，原路返回客户再回来，要么试样失败返工。每个工位的处理时间和交接等待时间取参数。

**需要传化给的参数**（拿不到就标"假设"，现场可调）：

- 月均客户询问量；业务员、产品经理、研发的人数；
- 各环节的处理时间和交接等待时间；一单平均来回几轮；
- 试样的一次成本和周期；因需求不清导致试样失败的比例；
- 研发和业务员的小时人工成本；研发时间中被短平快项目占用的比例。

- **研发提供的流程图和两张岗位对比图（2026-10，已拿到）**：
  - 旧线工位顺序以流程图为准；
  - 现状的时间构成以"实际现状"那张图为起点。
  
  这三张图只放在 `data/` 下，不入库。上台使用前要征得对方同意。

**与现有实现不一致的地方**：流程图上写的是"产品经理评价"，而化言目前按 REPLAN-v5 D10 的取舍，由业务员带回客户评价并录入（`market_eval`）。旧线照图画，化言线照实现画。这一处是否需要统一，要在会上确认。

## 5. 工作包

每个包做完都停下汇报，确认后再继续。这些包都不改合同：CEO 用现有的 `supervisor` 角色（L2），只多一个 `supervisor:CEO` 成员。它看到的研发内容只有计数和存根。

### C1 流水线数据
- 门面增加一个只读汇总接口：对一个运行目录或试用实例，输出每件货的工位路径（工位、进入时刻、离开时刻、经手人、是否绕回），以及按工位统计的排队情况。
- 工位划分规则写在一处，从现有 `route_of`、`workload` 的口径扩展而来，不另存数据。
- 只对 `supervisor` 开放。

**完成标准**：对 d20 运行和 v96a 试用实例都能输出路径；抽 5 件货，与 Month 页的单件视图逐一核对一致。

### C2 旧流程线推算
- 参数文件：`data/pilot/old_flow.yaml`，内部数据，不入库。仓库里只放一份标明"假设"的示例参数。
- 推算器放在 `eval/` 下，读同一批需求卡和 G1 转述结果，按参数输出旧线上每件货的路径，格式与 C1 相同。
- 业务代码不读这个推算器。

**完成标准**：同一批货在两条线上一一对应；把参数改成"转述不丢条件"时，旧线不再出现返工，用来检查推算器没有夸大差距。

### C3 账本
- 三个头条数字和流水线旁的指标，按第 3 节的口径计算，每个数都带来源标签和算式。
- 提供"按最保守参数"的计算。
- 参数改变时即时重算。

**完成标准**：每个数都能点开看到算式和来源；保守参数下的结果单独列出。

### C4 CEO 面前端
- 两条流水线并排，带货物动画、货堆、时间倍速、来单量滑块、参数面板和撤销能力的演示。
- 点开货物可下钻到单件经过。
- 第一屏只放三个头条数字。
- 来单量滑块只在推算和模拟数据上生效，画面上标明。

**完成标准**：在决赛用的机器和网络条件下流畅播放一个月；断网时用录好的运行目录能完整演示。

### C5 供数
- 用现有模拟月补跑出一个月的量：先决定用大模型扮演角色还是规则离线跑，见第 6 节。
- 传化案例到了以后，跑回放。
- 试用实例的真实单直接接入。
- 三种来源在 CEO 面上可以切换，也可以叠加，每件货都标明来源。

**完成标准**：至少有一个整月的模拟运行；有真实案例时，回放结果以"回放"标签单独显示。
