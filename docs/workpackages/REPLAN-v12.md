# REPLAN v12｜扫描资料补读与检索排序修正

分支 `v12`，自 `v11 @ bb0a09f` 分出。V11.13 的资料库（`data/library/`、`LibrarySource`、`search_sources`）上做增量，不改冻结契约，不碰 `knowledge/`、`jue/`、`sim/`、`agent/loop.py`、`web/`（这句限 V12.0–V12.2；V12.3 起按下文「决赛路演」各包的范围）。

起因：V11.13 登记的 4644 页里 1612 页没抽出文字，全部是考点一的四本扫描教材和一份国标，检索不到；检索排序把「有语义分数的」一律排在只被关键词命中的前面，V11.13 真实链路里目标报告正是只被关键词召回（第 5 名）。Agent 读扫描页本来就能读页图，所以 OCR 补的是「能被检索到」；业务报告没有待补读页，TF-213HE 业务链不受影响。

检索评测不作为主要证据（同 V11.13）；不建页内块结构、章节索引、证据单元分离，等 OCR 后真跑出具体失败的查询再说。

### V12.1｜扫描页补读

1. `scripts/build_library.py --ocr-pending`：对每份资料里仍是待补读的页，从 PDF 按宽 2000 px 重渲，经网关视觉模型转写成 Markdown（提示词同选型脚本），替换 `pages[]` 里的待补读占位；在该资料的 `docs/<doc_id>.json` 里记 `"ocr": {"<页号>": "<模型>"}`。失败的页打印出来，保持待补读；空白页写明空白。已不是待补读的页跳过，重跑即续跑；
2. `sources.json` 的 `pending_pages` 随之更新；之后照旧 `--index`，文字变了的页按 `page_key` 重算向量；
3. `LibrarySource` 读到 `ocr` 里的页时，检索结果和 `read_source` 摘录标明「模型转写，引用前对照原图」；指针仍是 `doc_id#p<页号>@指纹`；
4. 验证：真实跑完 1612 页，报成功、失败、空白页数；抽几页对照原图。

实现时第 3 条改得更短：「模型转写，引用前对照原图」直接写在页文字开头，`read_source`、检索摘录、Agent 看到的都是同一段，`LibrarySource` 不用改。

## 决赛路演：在岗位巡游之外，新增一条看得见的因果链（2026-11-04 登记）

起因：V11.12 的路演局让观众逐个岗位看功能，评委看到的可能只是「客户提问 → AI 追问 → 查资料 → 研发确认 → 推荐产品」，普通 RAG 加工作流也讲得出来。化言要让人看到的是：信息自己变成了事，一次判断变成组织能力，能力改变后面的业务，整个组织的协作方式随之改变。岗位巡游保留（试用者要靠它代入角色），以下全部是**新增**，不改已有工作面的业务交互。表达围绕化言自身的创新、价值与架构组装，不按外部所谓「考点」组织。

### V12.3｜现场真跑的底座

- 导演一拍不再整拍持锁：大模型调用（Agent 准备、模拟客户）在锁外进行，写动作照旧逐个经 `Api.call` 取锁；备局与现场时读进度、读页面不被挡住；
- 路演路径预热：台前按路演脚本跑一遍写入网关录制缓存，现场走同一条真实链路时命中缓存秒出；网关偶发 503 照旧由网关重试；
- 服务启动时预加载 EmbeddingGemma 2 与页向量，避开首次检索约 12 秒；演示机用本机 GPU；
- 研发面补资料库检索的界面：需求单上显示研发 Agent 检索了什么、命中哪几页、用的方法（`embeddinggemma-2` / `keyword`）、两路名次（`keyword_rank` / `semantic_rank`）、整页原图与存下的依据指针；扫描页的模型转写与 `ask_source_image` 单独问图的结果并排，对不上时两个都显示。

### V12.7｜第三幕：觉新增两类决策与研发成果回流

- **能力回流唤醒**（新模板）：一条适用能力生效后，觉在历史里找出情境相同、当时没解决的会话（不立项、已记录、等待中），向归属业务员提出「是否回访客户」，附新能力与当时的原话；业务员签字后客户在 Client-View 收到消息；
- **说明书与研发判断不一致**（新模板）：已生效的研发层适用能力超出该产品说明书写明的范围（如说明书 125–130℃、研发确认 133℃），觉向产品经理提出「是否更新说明书」，产品经理 Agent 用对外要点起草；
- **新品发布回到公开层**：沿用现有发布、封存要点与反向包装链路，进入第三幕的关卡步骤，下一位客户自助命中。
