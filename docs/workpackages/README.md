## 首版 Demo 验收（M3）

1. **L1 闭环**：现场输入客户的宏观描述 → 觉提示追问面料、设备 → 补充后每个槽位可回查原话 → Jev 推荐产品 → 业务员看到「产品＋用法」，研发视角看到机理和配方要点，两者确实不同。
2. **升级回流**：一个没有合适产品的需求 → 升级到产品经理 → Agent 起草、产品经理确认 → 研发需求单每条可回查原话 → 研发录入试样 → 发布新品 → **再来一段同类对话，L1 直接命中新品**；研发积分增加。
3. **权限**：业务员套问配方，被拒并写审计；懂化学的客户要求解密，经研发审批后该客户看到机理（看不到配方）。
4. **定时发现**：模拟业务周上至少跑通机会汇聚，「处置」与「不处置」两个分支的后果有图可看。
5. **标注**：界面顶部能看出 Jev、觉、抽取器各用的是什么实现，现场运行还是记录回放，数据为模拟数据（种子是否占位）。

## 并行规则

- 分支：A 用 `dev/a`，B 用 `dev/b`。每完成一个工作包、本包测试通过后，由人合并进 `main`，另一方随时 `git merge main`。
- 只修改各自「允许修改的范围」内的路径。
- `src/huayan/contracts/`、`huayan/domain.py`、`huayan/events.py`、`huayan/bus.py`、两个桩、`tests/fixtures/` 由 WP-0 产出，其他包**只读**。发现契约有问题：停下来，在汇报里写清楚，由人改契约。
- 测试只用 `tests/fixtures/mini_seeds/`（WP-0 产出的小种子），不依赖 `seeds/` 的具体内容，这样种子替换不会打断测试。
- 测试原则见 `AGENTS.md` 第 4 节：全项目不超过 10 个测试。

## 时间不够时先砍什么

按顺序砍：Jev 第三问（回答是否有依据）→ 泄露风险与知识冲突的业务周分支（保留模板与界面上的单次演示）→ 大模型轮询基线 → 大模型版模拟客户（用模板版）→ 评测页（图放 README）。

**不砍**：追问提示、原话可回查、L1/L3 披露不同、升级回流后 L1 直接命中、套问被拒、机会汇聚的处置/不处置对照、降级与模拟数据标注、Jue-K 与 B1/B2 的如实对比。
