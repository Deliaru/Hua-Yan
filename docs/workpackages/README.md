## Demo 讲什么

化言的主旨是**转译**：把客户的场景语言，逐层转成研发能直接开工的化学语言，而且不走样。和「一次性翻译器」的区别，就是三根支柱，Demo 要让它们都出现在转译这条线上：

| 支柱 | 在 Demo 中的样子 |
|---|---|
| 会追问 | 觉在对话中提示业务员追问关键信息，场景需求卡的每个槽位都绑定客户原话 |
| 分层转译、分层可见 | L1 场景需求卡 → L2 产品需求语言 → L3 化学语言需求单，每层只用自己能看的知识；三层对照视图一屏看清 |
| 权责对等 | 需求单每一句标明依据了**哪位研发的哪条转化知识**，引用即记分；研发修改转译可沉淀为自己的知识；L1 永远只拿到包装后的结果；解密要研发本人审批 |
| 失真可度量 | 同一批需求卡上，业务员转述 / 一次性翻译 / 化言三组对照 |
| 多层 Agent | 每个人一个角色助手：自然语言指挥、自己调用原子工具；觉发现的问题直接派给对应的助手主动处理；助手借用委托人权限，越权只知道「谁知道」；生效靠委托人确认，谁确认谁负责 |

L1 直接推荐产品（知识库里已有答案的情况）保留，作为「短路径」演示一次。

## 首版 Demo 验收（M3）

1. **转译主线**：客户只说宏观现象 → 觉提示追问 → **L1 场景需求卡**（槽位 + 原话）→ 没有现成产品，升级 → **L2 产品需求**（产品经理 Agent 起草、产品经理确认，引用案例与 L2 转化对照）→ **L3 化学语言需求单**（研发助手起草、研发确认）；起草中觉发现缺一个会改变转译的信息，**回问**派给业务员，客户回答后自动回填。需求单每一句都能点回客户原话，并标明依据的转化知识及其归属人。
2. **三层对照**：同一个需求在 L1 / L2 / L3 三列并排：L1 只有场景需求卡和包装后的结果；L2 多出产品需求与案例，所引 L3 知识只显示「研发 R01 的转化知识（L3）」；L3 能看到化学语言、所引知识原文、机理与配方要点。
3. **权责对等与回流**：研发修改一条转译并沉淀为自己的转化知识（积分 +）；研发录入试样、给出对外要点 → 产品经理用反向包装生成 L1 说明书并发布 → 同类对话 L1 直接命中新品；贡献看板显示每位研发的知识被引用次数与积分。
4. **权限**：业务员套问配方被拒并写审计；懂化学的客户要求解密，须产品归属研发本人审批，通过后看到机理、看不到配方。
5. **失真对照**：同一批需求卡上，业务员转述 / 一次性翻译 / 化言三组的关键信息完整率、错误率、追问次数、研发需退回比例，有图有表；另有机会汇聚在业务周上「处置 / 不处置」的对比图；Jue-K 五类决策的可靠性图，以及与原型规则分数的校准对比。
6. **标注**：界面顶部能看出 Jev、觉、抽取器、角色助手各用的是什么实现（规则 / 大模型 / 桩 / 离线），现场运行还是记录回放，数据为模拟数据（种子是否占位）。
7. **角色助手**：业务员、产品经理、研发三人只用自然语言和确认卡走完主线；觉发现的机会汇聚、确认后的需求单、对外要点、解密申请都自动派给下一棒的助手并由它主动处理；助手的工具轨迹可见，越权检索只显示「研发 R01 · L3」；每个生效动作都记下确认人。

- 测试原则见 `AGENTS.md` 第 5 节：全项目不超过 11 个测试。
