## 1. 四类岗位在试用中做什么

| 岗位 | 在试用中的工作 |
|---|---|
| 业务员 | 输入和澄清客户需求，纠正系统理解，处理商务衔接与客户反馈 |
| 真人产品经理 | 判断产品范围、机会和商业边界；后台 `pm:agent` 承担逐单转译 |
| 研发 | 查看需求和依据，回问、接单或退回，作出专业判断，审定成果与使用授予 |
| 研发负责人 | 在已有权限范围内查看进展、重复工作和能力使用，处理例外与管理判断 |

四类岗位共同参与，每张单只经过它需要的人。L0–L3 是知识边界，负责人按授予阅读 L3 原文。

觉的方向：**形成、维持、筛选并提交值得决策的事项**；契让专业判断形成有来源、有范围、可复用、可撤销的能力。试用让这两件事在真实业务里发生。Jev 回答已经提出的问题，和觉的发现各管一段。

## 2. 四件事

### ① 让大家处理同一份业务

`ui/server.py` 目前按浏览器创建独立应用实例。把试用接到**同一个应用实例和一份已有业务数据**，按角色进入，服务端按该角色执行现有权限。通用多租户、企业 SSO 与组织管理随正式上线再做。

沿用已有保存机制，页面刷新或回来后看得到已提交的需求、判断和待办；调整模型配置时业务原样保留。试用用真实时间。模型等待明显阻塞的入口，改为后台执行。

Agent 调用失败时给出清楚提示，整项重试；进程中断后业务数据保留，未完成任务重新执行，粒度到任务即可。签字、发布、授予等已生效的结果按对象现状判断，重试只生效一次。

### ② 修掉妨碍办事的问题

用 V8 的实际失败输入复现和修复：

- 客户回答「不清楚」、一次答多项或纠正条件后，回问正常结束，已知信息完整保留。
- 同一研发处理不同需求时，助手按当前对象装配上下文，每单各归各单。
- 助手真正把草稿写进对象；产品经理准备缺口、对象编号错误和「说完成但没做」都正确处理。
- 语义理解在抽取入口修，下游读结构化结果。
- 从试用资料形成能力时，完整保留实际涉及的专业限制；当前结构表达不了的部分交专业人员确认，结构随真实资料按需扩展。

一次修复围绕一个明确的业务问题，成套修改相关文件。修完用原失败输入复验，再走受影响的业务链；普通界面瑕疵在试用中持续改。

### ③ 把觉与契接进这次真实工作

用一组相关业务贯通：需求进入并得到澄清，觉主动提出有关事项，Agent 准备，真人处理；研发判断或试样反馈回到业务中；适当的判断经确认与授予，进入下一件符合条件的需求。

再换一个关键条件，确认交回专业处理；撤销或人工刷新一条依据，确认这条链路的推荐与能力使用随即停用。沿用已有来源指纹、能力状态和引用。

试用配置实际加载要展示的觉模型，核对家族和特征一一对应；规则回退在界面上标明。看觉主动提出的事项是否有用、打扰是否适度、处理后能否更新或结案。学习增益另做针对性对照。

### ④ 让真实岗位使用，按使用改进

开发者先按各角色走通上述业务，修掉共享数据、权限、串单和错误适用这类影响试用结果的问题，即可安排人员试用；其余情形在试用中边用边改。

现场讲解、协助操作、手工补充资料和失败重跑都是正常协助。专业判断由对应岗位作出；简要记录哪些由系统完成、哪些需要帮助、哪里卡住。发现阻断就定位修复，检查受影响部分后继续。

业务来源可以是真实当前需求或来源清楚的历史案例。试样结果按实际来源说明，物理实验用已有结果，检验的是软件协作过程。试用前备好资料、角色入口与简短说明即可。

## 3. 工程按试用需要做

**成熟组件可以借鉴或直接采用，每项选择对应一个具体问题和采用后的收益。**现有机制满足试用就继续用；执行底座真的妨碍业务时，再局部改进或替换。（上一版预先指定的 LangGraph、数据库 checkpointer、持久 runner 和 Temporal 路线已撤回。）

这次要的是：一份共享业务、角色会话、基本保存、对象各归各单、普通错误看得见能重试，以及觉和契的主要行为成立。通用并发控制、逐步骤恢复、周期来源巡检、完整依赖传播、故障注入矩阵和长期训练平台，按实际使用的需要排进后续版本。

现有回归测试全部保留，为已出现的关键缺陷补检查；真实语义用实际模型核对，业务链由真人试。测试按需增加。

开发效率高，就用来更快试验和修改。每项新工作先回答：它解决这次试用里的哪个具体问题，或者证明哪项产品价值？

## 4. 够用的标准

开发者确认这条链能走通：**需求 → 澄清与判断 → 研发处理与反馈 → 成果或能力形成 → 后续需求使用**。四个岗位都有真实工作可做，觉主动提出并更新有关事项，契的范围和撤销在实际入口生效，普通错误就地重试——到这一步就交给人员试用。

试用后集中回答四个问题：他们能否办完事；哪些地方仍然费劲；哪次专业判断真正被下一件业务用上；觉提出的事情哪些有用、哪些多余或遗漏。留一份简短问题记录和有代表性的过程截图／录制，支持修复和路演。报数字时写清版本、样本和计算方法。

「可以交给人试」和「人已经试过」按实际进度分别说明。真人参与安排与软件准备并行；研发负责人可以在业务处理后查看结果、提出意见，时间灵活安排。

### V9.2 模型等待不卡住别人，失败可重跑

- 助手对话、产品经理 Agent 准备等耗时入口放到后台执行，界面显示进行中并取结果（沿用 `/api/progress`、`agent_process`）；读请求和别人的写操作照常进行。
- 失败给出清楚提示，界面可以把这一项整个重跑。
- 进程中断后重启：总线上仍开着、该由 Agent 准备的问题重新派一次。签字、发布、授予已经生效的，按对象现状判断，重跑只生效一次。

完成：一人让助手起草时，另一人能正常查看和签字；人为断开模型接口，界面报错，恢复后重跑成功；Agent 准备到一半时杀进程，重启后这项重新准备，已发布的东西没有被发第二次。

**完成记录（2026-10-22）**

- 不卡住别人：试用实例的会话锁换成模拟器已有的闸口（`sim/schedule.py` 的 `Gate`），业务状态只由持有者改，等大模型和 clef 返回时让出；Hub 工具的「Agent 起草」标记改为按线程。觉提出的问题不再在写操作里准备，写完叫醒后台，由后台派给 Agent；过程面板按人记。界面每 4 秒看一次事件数，别人的提交和后台准备完成后自动刷新。
- 失败可见、可重跑：模型接口的错误回 503，写明「已提交的内容都在，再点一次就是重跑」；助手这一轮失败时整轮撤回，重发同一句即重跑。后台准备失败记在问题上（`/api/agents/failures`），不占派单次数，下一次后台周期自动重跑，收件箱「准备中」写明失败并可「现在重跑」（`/api/agents/retry`）。网关重试间隔改为按配置（`retry_waits`），默认不变，试用配置为 3、10 秒。
- 重启续跑：派单记录只在内存里，重启后总线上开着、未准备的问题自然重新派；签字、接单、自动执行和标记准备都先查对象状态，重跑只生效一次。
- 验证（真实模型）：升级后立即返回，产品经理 Agent 在后台准备两项（约 80 秒）期间另三人照常读取；研发助手起草 15 秒期间负责人、产品经理的读取都在 0.1 秒内返回；业务员助手运行时研发接单 0.2 秒完成，再接一次被拒。换到断开的模型配置：助手 19 秒报错、对话无残留，后台准备失败显示在研发收件箱；换回后点重跑约 20 秒准备完成。产品经理 Agent 准备到一半时杀进程，重启后这项重新准备并完成一次，之前已准备的四项没有重做，接单与各项结案各一次。`tests/test_trial.py` 覆盖失败记录、重跑权限与对话撤回。
- 留给后续：产品经理页的待办没有接入失败提示（问题会出现在签字研发的收件箱里）；同一会话两人同时说话时的先后仍按到达顺序处理。

### V9.6a 条件修正、依据失效与角色入口

V9.6 之后的外部审查复现了一组确定性缺口，集中在三个承诺上：客户条件准确传到底、专业判断只在有效范围内复用、各角色按权限使用信息。真人试用前分四组修完，每组围绕一个结果。

1. **条件修正贯穿到发布。**
   - 现状：客户在返工阶段补充或更正条件后，结构化条件已经对了。但只有 `draft` 状态才会清掉自动生成的产品稿；回问答完只清「准备完成」标记，`preparation_gap` 只看草稿是否为空，于是旧稿可以再次确认。发布时 `release_product` 取第一条通过的试样，`package_sheet` 从旧产品稿取条件，发布出去的适用范围和说明书可能仍是旧条件。发布后，原客户会话停在 `escalated`。
   - 要做到：
     - 条件变了，产品稿和化学稿里由 Agent 起草的部分按新条件重新起草；研发、产品经理改过的条目保留，并标明需要因新条件重新确认。待确认的问题回到准备中。
     - 说明书和发布的适用情境，用本单当前确认的条件和最后一次通过的试样。
     - 发布后，原会话收到新产品的推荐。
     - 名称、类别由研发在发布时填写；没有转译出来的机理不存成正式机理。
2. **每张推荐都有一条有效依据。**
   - 现状：撤销后的重算调用匹配时没带研发限制，产品只剩带限制的能力时，旧推荐和已撤销的能力编号都还在。研发审定、研发判定适用推送的推荐存的是空候选，失效检查找不到依据，结论撤回后推荐照旧可见。
   - 要做到：自动推荐、研发审定推荐、撤销后重算，用同一套适用条件和限制判断，推荐上记下所依据的能力。依据失效就换成仍有效的依据；没有可替代的，就撤回推荐并重新匹配，由觉照常跟进。
   - 撤销某一条适用授权，不连带撤销基于同一结论授予的「可说的话」。结论本身不成立时走 `withdraw_claim`，知识层已经会挂起依赖它的能力。（更正 V9.6 记录里把这一点列为问题的写法。）
3. **角色入口按现有权限校验。**
   - `/api/turn`：服务端认定的当前身份必须是这个会话的客户本人或负责它的业务员；说话角色仍按身份限定（业务员可替客户录入原话）。
   - `/api/agents/trace`：只给这段助手对话的委托人本人查看。
4. **觉的信号与试用资料。**
   - `trial_risk` 规则也数「必问条件还没取得」（新增 `n_missing_required`；原 `n_missing` 是试样失败指向、尚未回问答过的条件），不只数客户答过「不清楚」的。
   - 试用配置停用泄露风险（`leak_risk`）的提出。已知它在正常跟单时误报，分层访问、授予和撤销继续负责信息控制。
   - 选定业务涉及的产品适用范围，以及横档是否把加工形态列为必问条件，列成清单交产品经理确认。种子里空的适用范围目前按「不受限」匹配，确认前不改写。

完成：外部审查复现过的分支各有回归检查并通过，包括改条件后重新发布、撤销后只剩带限制的能力、撤回研发直接推荐所依据的结论、跨角色写会话和读轨迹、未问与答「不清楚」的区别。试用实例上把改条件和撤销再走一遍。之后安排 V9.7。
