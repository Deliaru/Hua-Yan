## 1. 目标、状态与完成定义

开发效率不作为删除必要能力的理由。范围按真实试用需要、业务依赖、证据缺口和正确性确定；允许成套修复跨组件问题，允许复用成熟底座。不能把目标收缩成一段录制、一组离线数字或开发者按既定台词切换角色。

保留两根支柱：**觉（Jue-K）持续形成、维持、筛选、提交值得决策的事项；契（Qi）使有来源、经专业确认的判断，在明确范围和授权下被组织使用、追踪和撤销。**Jev/OneJev 处理已经提出的决策，与觉的发现职责不同。真实试用检验两者能否共同改变实际协作；学习模型相对规则的增益另行证明，不以一个 AUC 代替产品价值。

### 1.1 两个状态分别记录

| 状态 | 达成条件 | 截至本次审查 |
|---|---|---|
| **可交付真实试用** | §4 的 T1–T12 中可由开发者验证的软件行为与交付准备项通过；资料、账号、参与说明、恢复方式、问题记录入口可交付；已知缺陷不会使主链、权限或结果可信度失效 | **未达到**。共享空间、身份、执行恢复、上下文和条件保真等需补齐 |
| **真实试用已完成** | 四类真实岗位实际参与并完成其职责，保留输入、判断、结果、失败和修复后复验记录 | **尚未发生／尚无本轮记录**。人员安排属于外部条件，不能由开发者代签或模拟通过替代 |

代码通过检查后可准确报告“已具备试用条件”；只有真实参与发生后才报告“试用已完成”。实际试用发现的阻断问题须回到对应工作包修复，不能把已交付当作验收豁免。本文不预先宣布用户认可、化学试验成功或业务收益成立。

### 1.2 四类岗位的真实职责

| 角色 | 本次需要完成的工作 | 权责边界 |
|---|---|---|
| 业务员 | 提交与澄清客户原话，补充或纠正条件，处理商务衔接、试样协同与客户反馈 | 能说明“不清楚”；不能替研发确认专业结论，也不能读到未授权原文 |
| 真人产品经理 | 处理确有需要的产品适用范围、机会、产品生命周期和商业边界判断 | 后台 `pm:agent` 的逐单转译不能代替真人产品经理；不要求其逐单转述 |
| 研发 | 技术判断、接单或退回、回问、试样解释、成果审定、专业知识确认与按权授予 | 专业确认、向谁授予什么用途、产品范围批准是不同判断；界面须说明正在确认什么 |
| 研发负责人 | 查看授权范围内的组织工作与依据，处理治理、风险、例外和责任归属事项 | 可沿用 `supervisor` 职责再明确权限；不是新增 L4，不自动读取全部 L3，不成为每单必经审批 |

L0–L3 是知识和使用边界，不是四道串行审批。全链条要求业务有始有终；常规需求应在可处理的岗位完成，需要专业或治理判断时才交给相应责任人。

### 1.3 什么计为真实

真人自主输入、修改和签字，实际模型处理新输入，业务接口产生可追查的软件状态，分别记录。可使用获准的业务材料、匿名材料或真实历史案例；材料来源和删改范围必须标明。现场新产生的试样结果、已有实物试验记录、重建案例和模拟结果不得混称。公开 Demo 的种子与回放继续保留，但不计作对应在线能力和真人协作的通过。

试用环境可使用获准资料，公开仓库不保存内部原文、账号或密钥。尚未接入钉钉、ELN、CRM 或实际生产系统时，应准确写明接口状态；在独立试用环境中完成真实业务协作本身有效，不能声称已完成外部生产写回。

## 3. 责任边界与成熟组件的复用

### 3.1 修复必须回到负责该判断的组件

| 责任 | 负责组件 | 不得转移到哪里 |
|---|---|---|
| 理解原话、指代、否定、未知与纠正 | 统一语义抽取，保留证据和结构化结果；Agent 对自己收到的任务作语义准备 | 下游门面、回答、知识库或觉再按关键词猜一次 |
| 形成并维护候选、筛选和提交事项 | 觉与其对象、特征、评分及责任映射 | HTTP 路由或执行框架暗藏“此时应该做什么”的业务流程 |
| 起草、查证、调用工具准备工作 | 对象内 Agent，经统一模型网关和领域门面 | 仅聊天声称完成，或直接改数据库绕过门面 |
| 当前操作是否允许、来源与能力是否有效 | 服务端身份、领域门面、契的类型和条件检查 | 模型自报角色、旧记忆、旧 checkpoint 或界面按钮是否可见 |
| 专业结论、授予、产品与治理决定 | 相应真人责任人，或其已经明确授权的自动动作 | 为跑通链路让模拟人或 Agent 代签 |
| 执行、等待、重试和恢复 | 成熟执行组件与持久运行驱动 | 觉评分器、聊天记录或请求内循环承担全部运行状态 |

人的主动委托可进入正常业务入口并记录来源；不是每个动作都必须先由觉提出。继续一项已批准工作是执行恢复，不是新的业务判断。门面保留权限、类型、状态和明确安全约束，不能恢复“有回问或失真就一律禁止研发接单”这类替人判断的门。

### 3.2 执行底座：选定一条完整路径

V2 默认按 **LangGraph Functional API＋数据库 checkpointer＋持久运行驱动**设计，沿用当前 Python 控制流、领域门面和模型网关。交付物必须写明数据库、运行进程、任务受理、启动恢复、等待唤醒、并发和幂等策略；checkpointer 本身不是后台队列。模型调用和有副作用的工具动作要有可恢复边界，把整个 `run_turn` 套成一个大节点不算完成。

若该方案不能满足 §4 的行为验收，可将 **Temporal Workflow/Activity** 作为替代执行路径；记录替换依据，只交付一套生产执行路径，不同时堆叠两套框架。选型以行为正确性为准，不能因底座难做而删掉共享、等待、恢复或当前权限复核。框架恢复可能重新执行步骤，业务动作仍需持久的动作 ID 与去重；网关和运行时的重试职责必须分清。

来源：[LangGraph Functional API](https://docs.langchain.com/oss/python/langgraph/functional-api)、[持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[中断与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Temporal 动态 Agent loop](https://docs.temporal.io/ai/cookbook/agentic-loop-tool-call-openai-python)。这些资料说明可复用的执行机制，不证明化言已经接入或满足验收。

### 3.3 其他成熟机制按问题借鉴

知识的采集、结构化、复用、维护可参考 [KCS v6](https://library.serviceinnovation.org/KCS/KCS_v6/KCS_v6_Practices_Guide/030/030) 与知识生命周期；人工确认可参考 [Dify Human Input](https://docs.dify.ai/en/api-reference/guides/human-input-flow) 的动作、状态、过期和重复提交处理；授权可参考 [SpiceDB caveats](https://authzed.com/docs/spicedb/concepts/caveats) 对条件未知的显式表达，以及 [consistency](https://authzed.com/docs/spicedb/concepts/consistency) 的版本一致性。它们不替化言判断专业限制是否完整，也不自动清理模型上下文。

这些是设计参照，不是必须安装的依赖清单。优先复用已有实现，只有在明确边界不足且行为验收需要时接入组件。现有网关已经有结构化输出校验和修复重试，不应再重建一套平行网关。独立评测可使用现有脚本或成熟评测库，不建一个与试用无关的大平台。

## 4. 全链条验收

所有项目均须记录结果与依据；本轮文档修订不预填“通过”。功能检查可由开发者完成，真人角色试用必须由相应参与者实际操作。修复后的复验记录与原失败记录同时保留。

| 编号 | 验收内容 | 通过时必须观察到的结果 |
|---|---|---|
| T1 | 共享业务空间与独立身份 | 四类岗位独立会话接力同一对象；最新状态一致；操作绑定服务端确认的主体；改客户端参数不能冒充其他角色 |
| T2 | 资料接入与责任归属 | 试用材料通过适配器进入，定位来源、片段、指纹、密级和责任人；草稿与已审定内容区分；模型猜测不成为来源事实 |
| T3 | 自然表达与事实修订 | 新表达、否定、指代、多条件、未知和部分回答得到正确处理；缺省不抹掉旧事实；更正有来源；未表示的新概念保留并交人处理 |
| T4 | 需求到结果的角色协作 | 从需求、澄清、技术处理到试样／反馈、成果审定、发布能够完成；接单、拒绝、退回与修改有正常路径；PM 和负责人完成真实职责 |
| T5 | 觉形成、维持、筛选、提交 | 未额外交办“建任务”时提出有关事项；依据变化后更新、结束或重提；重复扫描不重复派发；责任人与评分来源可查；漏报和无用打扰可记录 |
| T6 | 多对象并行与上下文隔离 | 同一研发交替处理条件不同的 A、B，A 等待时 B 能继续；草稿和引用不串单；合法共享知识与对象事实明确区分 |
| T7 | 人工等待与拒绝 | 关闭页面后待批准动作仍在；业务未提前生效；其他对象继续；批准绑定动作与依据版本；依据变了需重新检查或重新批准 |
| T8 | 专业条件与授予 | 专业确认、使用范围授予和产品批准分别说明；温度、范围、单位、否定、组合条件等限制完整保留；无法表达时不能变成更宽可执行能力 |
| T9 | 结果回流与下一次复用 | 第一件业务形成经确认的判断；下一件条件符合的需求实际使用它；条件不足保持不确定，边界外不错误推广；使用能追到来源与责任人 |
| T10 | 来源变化、撤销和当前使用 | 通过明确的刷新／recheck 入口检测变化；能力及相关当前推荐、草稿、记忆引用、恢复动作不再使用失效依据；历史记录仍能解释当时依据 |
| T11 | 可靠执行与恢复 | 模型失败、签字响应丢失、页面关闭及服务重启后状态可解释且可续办；同一动作只生效一次；未知结果不显示成功；恢复检查当前授权 |
| T12 | 可交付与真实反馈 | 参与者按说明使用正常界面完成工作；记录开发者帮助、失败与返工；负责人能从组织视图回到具体对象核查；有完整试用记录和未通过清单 |

T1–T12 均区分工程验证与真人表现：开发者可先用不同测试身份验证软件行为、业务链路和交付准备；T4 的真实岗位处理、T12 的实际参与及反馈等，必须在真人试用中另行记录。账号、说明、问题记录、恢复入口和可核查工作面是交付准备项。两类证据单独标状态，不能用“还没邀请人员”掩盖工程缺口，也不能因工程通过就填“真人试用完成”。

T8 至少需要一条含多个限制的专业判断。可以用“材料 A 且温度不超过某值”这样的**合成结构测试**检查条件完整性，但它不构成化学建议。专业正确性仍由相应业务人员确认。字符串出现于原文只证明引文存在，不能证明生成的可执行条件没有弱化原意。

T10 区分“已检测到变化后的禁止使用”和“何时检测到外部变化”。写清检测入口、频率或事件来源、最后核验时间和未核验状态；没有接入实时事件就不宣称实时监测。重确认应展示来源变化和适用范围差异，不能仅换一个指纹自动沿用全部旧批准。

T11 的危险窗口用必要的故障注入验证：步骤完成但尚未保存回执、签字已生效但响应丢失、等待确认时重启等；真人试用再完成可见的续办。持久对象文件与可恢复执行是两个验收点。

## 6. 验证、价值测量与证据记录

### 6.1 三类验证各自回答一个问题

1. **确定性回归与故障验证：**权限、条件、对象隔离、状态、幂等和恢复是否正确。默认快速、离线；允许结构化模型输出夹具测试下游是否遵守语义。测试数量服从风险，不设 11 个上限，也不禁止 Agent Loop 的必要测试。
2. **实际模型核对：**新自然表达是否得到正确语义和可用草稿。样本在调整前冻结，分别标明独立核对、调参、失败回归；不能用规则抽取器通过难例来证明模型理解。
3. **真实角色试用：**人能否完成任务，系统是否减少重复工作并让判断进入下一次业务。测试通过、模拟回放和真人试用互不替代。

每次较大运行先写清要判断的假设、基线和输出；先用能定位问题的验证，再做集成。不要为了一个语义问题重造模拟世界；也不能因短测试已通过而跳过全链条试用。

### 6.2 价值指标与公平对照

至少记录：完成／失败的具体业务、研发实际介入及重复介入、澄清与返工、人工确认和维护成本、有效复用与错误复用、无用打扰与漏报、参与者能否独立完成、是否愿意继续使用及理由。少量案例先逐案展示，不把百分比包装成普遍收益；未观察到的长期效果写“未观察”。

若比较产品效果，使用相同资料、权限、模型能力和业务任务，基线至少包括一个有检索、工具、人工确认和正常工作流能力的成熟被动助手方案。不能仅与刻意弱化的聊天框比较。若比较学习增益，另固定候选、训练/测试隔离和错误成本，报告阈值、覆盖、漏报、打扰及不确定性；负结果如实保留。

### 6.3 每份运行或试用记录的最小字段

| 项目 | 记录内容 |
|---|---|
| 版本 | 代码 SHA、配置、模型/提供方、实际加载 checkpoint、数据版本或哈希、运行日期 |
| 参与与数据 | 真实岗位、实际操作者、材料出处与授权范围、匿名化/重建说明、模拟或实物结果标记 |
| 对象与过程 | 工作空间、需求/问题/能力 ID、来源版本、原话、更正、确认、执行结果、失败与帮助 |
| 结果 | 各 T 项结果、未通过原因、人工成本、后续复用、边界检查、参与者反馈；事实与主观评价分开 |
| 修复与复验 | 缺陷 ID、负责组件、原因、关联提交、受影响验收、修复后结果；旧输入转为回归材料 |

试用时项目方可讲解入口和术语；代填专业判断、代签、后台改状态、临时改种子或注入答案必须作为干预记录，不能把这种链路算作独立完成。参与者反馈原意保留，不让模型将“勉强走通”改写为认可。

## 8. 防止再次陷入碎修

每个失败先回答：**哪条业务行为没有成立，哪个组件拥有这个责任，缺的是信息、表示能力、权限还是执行保障？**再修改该责任边界。修复记录带上反例和受影响链路，不能只加使本句通过的词表、门槛或提示词。

同一口径再次改变时，先核对它在量什么实际结果；不要继续换代理计数。一次验证聚焦一个可判定假设，必要的跨文件改动可以一起完成。现行规则只写在当前入口，历史计划不继续追加现行命令；证据与配置绑定，失效数字在引用处标记历史或重跑。

附录保留 V8 的 43 条问题，让后续实施能够追溯这份计划的原因；它们的“已修/未修”是历史状态，不替代本轮验收。其中 #35 纠正为部分修复，其余需要在对应工作包以实际代码和记录复核。
