## 1. 要让四类岗位完成什么

| 岗位 | 在试用中的工作 |
|---|---|
| 业务员 | 输入和澄清客户需求，纠正系统理解，处理商务衔接与客户反馈 |
| 真人产品经理 | 在需要时判断产品范围、机会和商业边界；后台 `pm:agent` 继续承担逐单转译 |
| 研发 | 查看需求和依据，回问、接单或退回，作出专业判断，审定成果与使用授予 |
| 研发负责人 | 在已有权限范围内查看进展、重复工作和能力使用，处理确有需要的例外与管理判断 |

四类岗位共同参与，不要求每张单依次经过四个人。L0–L3 仍是知识边界，负责人不因职务自动获得全部 L3 原文。

觉的方向保持为**形成、维持、筛选并提交值得决策的事项**；契让专业判断形成有来源、有范围、可复用和可撤销的能力。试用要让这两件事实际发生。Jev 处理已经提出的问题，与觉的发现职责分开。

## 2. 接下来按四件事推进

### ① 让大家处理同一份业务

当前 `ui/server.py` 按浏览器创建独立应用实例，四个人分别打开页面并不共享需求。先把试用接到**同一个应用实例和一份已有业务数据**，给参与者分配简单的角色会话，由服务端按该角色执行现有权限。无需先建设通用多租户、企业 SSO 或组织管理平台。

继续使用已有保存机制，页面刷新或回来后能看到已提交的需求、判断和待办；调整模型配置不应清空业务。实际试用使用正常时间，不再靠每次 POST 推进模拟时钟。模型等待造成明显阻塞时，针对该入口作简单异步或后台处理。

Agent 调用失败时给出清楚提示，允许整项重试；进程中断后可以保留业务数据、重新执行未完成任务。**不要求恢复到每一次模型调用或工具步骤。**签字、发布、授予等已经生效的结果，以现有业务状态判断，重试不要重复产生关键效果。

### ② 修掉已经妨碍办事的问题

优先用 V8 的实际失败输入复现和修复：

- 客户回答“不清楚”、一次答多项或纠正条件后，回问能正常处理，已知信息不会莫名丢失。
- 同一研发处理不同需求时，助手不串单；先按当前对象装配上下文，不为此先建设通用记忆治理系统。
- 助手真正把草稿写进对象，产品经理准备缺口、对象编号错误和“说完成但没做”能正常处理。
- 语义理解在抽取入口修，下游使用已有结构化结果；不再为了某句话过关，四处追加正则判断。
- 从试用资料形成能力时，保留实际涉及的专业限制。当前结构表达不了的部分留给专业人员确认和处理，不悄悄忽略，也不提前建设覆盖所有专业条件的语言。

一次修复围绕一个明确的业务问题，可以成套修改相关文件。修完用原失败输入复验，再走受影响的业务链；普通界面瑕疵和不影响判断的问题可以在试用中继续改。

### ③ 把觉与契接进这次真实工作

用一组相关业务贯通以下过程：需求进入并得到澄清，觉主动提出有关事项，Agent 准备，真人处理；研发判断或试样反馈回到业务中；适当的判断经确认与授予，进入下一件符合条件的需求。

再换一个关键条件，看看系统是否保留必要的专业处理；撤销或人工刷新一条依据，检查这次链路的推荐与能力使用是否停止采用失效判断。沿用已有来源指纹、能力状态和引用，不扩成全系统缓存、记忆、历史对话的自动失效工程。

试用配置应实际加载打算展示的觉模型，核对家族和特征是否对应；规则回退如实标明。看觉是否主动提出有用的事项、是否重复打扰、处理后能否更新或结束。学习增益可以另做针对性的对照，但全候选采样、训练记录重构和大规模评测不是开始试用的前提。

### ④ 让真实岗位使用，再改影响使用的问题

开发者先按各角色走通上述业务，修掉共享数据、权限、串单和错误适用等会让试用结果失真的问题，就可以安排人员试用。无需等所有异常情形都被证明正确。

允许现场讲解、协助操作、手工补充资料和失败重跑。专业判断由对应岗位作出；简要记录哪些是系统完成、哪些需要帮助，以及哪里卡住。发现阻断就定位和修复，再检查受影响部分，不必每次重新搭一套完整评测。

可采用真实当前需求或来源清楚的历史案例。试样结果按实际来源说明；没有现场做物理实验，就使用已有结果检验软件协作过程。试用前准备好可用资料、角色入口与简短说明即可，不另设一套材料合规或证据审批流程。

## 3. 工程做到支撑这次试用即可

上一版提前指定 LangGraph、数据库 checkpointer、持久 runner 和 Temporal 替代路径，依据不足，现撤回。**成熟组件可以借鉴或直接采用，选择要对应一个具体问题以及采用后的收益。**现有机制能满足试用就继续用；发现执行底座确实妨碍业务，再决定局部改进或替换，不把框架迁移作为独立目标。

这次需要的是：一份共享业务、简单角色会话、基本保存、对象不串、普通错误能看见并重试，以及觉和契的主要行为成立。通用并发控制、逐步骤恢复、周期来源巡检、完整依赖传播、故障注入矩阵和长期训练平台，不作为本轮交付条件；后续是否需要由实际使用决定。

保留现有回归测试，为已出现的关键缺陷补必要检查；实际模型用真实表达核对，业务链用真人试。没有测试数量上限，也没有为了完整而覆盖所有理论故障的要求。

开发效率高意味着能更快试验和修改，不意味着要把所有可能用到的基础设施提前建设完。新增工作先回答：它解决这次试用里的哪个具体问题，或者证明哪项产品价值？

## 4. 怎样判断这一版够用了

开发者先确认这条链能够走通：**需求 → 澄清与判断 → 研发处理与反馈 → 成果或能力形成 → 后续需求使用**。四个岗位有可做的真实工作，觉能主动提出并更新有关事项，契的范围和撤销在实际使用入口有效，普通错误不需要清空全部业务重来，就可以交给人员试用。

试用后集中回答四个问题：他们能否办完事；哪些地方仍然费劲；哪次专业判断真正被下一件业务用上；觉提出的事情哪些有用、哪些多余或遗漏。留一份简短问题记录和有代表性的过程截图／录制，足以支持修复和路演。需要报数字时再补清版本、样本和计算方法。

“可以交给人试”和“人已经试过”按实际进度说明，不另建两套验收制度。真人参与安排与软件准备并行；研发负责人也可以在业务处理后查看结果、提出意见，不必强行安排同一时刻在线。

## 5. 保留的开发约定

当前接口仍以 [CONTRACTS](../CONTRACTS.md) 为准；本次只改文档。实施遇到确需改变冻结契约的地方，说明具体改动并按实际授权处理，不为每个普通实现选择新增审批。

业务动作走现有门面，模型调用走统一网关，权限沿用知识与能力边界。觉不接管执行重试，门面不靠新增业务门槛替人判断，Agent 不把聊天回复当成已完成的动作。

历史模拟、实际模型运行和真人反馈按事实说明；内部业务资料和密钥不进公开仓库。长期愿景继续保留，当前实现只根据发生过的工作更新。开发中优先读这份计划，遇到具体问题再查历史记录，避免把每一代的限制叠加执行。
