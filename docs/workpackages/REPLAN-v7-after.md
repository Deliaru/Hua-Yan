## 0. 定位：两根支柱

决赛要让评委看到两样只有化言有的东西，两者互相独立，一根被质疑，另一根照样成立：

1. **觉 = 任务的来源**：没人提任务时，觉提出「此刻该谁决定什么」；不该打扰人时，觉保持沉默；它在运行中按结果重训。
2. **契 = 能力的来源**：研发的知识不给你看，但可以授权给你用；授予、撤销立即改变各层行为；功劳记在被使用的判断上。

原计划的第二根支柱是「权责平面」（知识看不见、功劳流得回、权力只在人手里），契是它的升级：从「看不见」走到「看不见但用得上」。现场片段相应改为：觉的发现与沉默；三态（未授予 / 已授予 / 已撤销）；四步能力复用；觉的自进化与安全对照。

### 1.2 收集真实返工案例（v7 Q7.5 的输入）

- 请一线研发口述 5–10 个真实返工案例，每个三样：客户**最初怎么说**（尽量还原原话）、最终方案依赖哪些条件、哪些条件是试样之后才补上的。
- **先冻结词表再标注**：标注开始前冻结 `slots.yaml`，记下冻结时间与文件指纹；之后新增槽位只能由一线研发凭业务常识提出并记录时间。不能看了回测答案再补槽位（铁律 5）。
- 照实回忆，不编写；只做测试，不进训练。研发给的条件比例和常漏的条件，可以用来校准模拟器（写明出处）。
- 官方资料到手后，从「客户需求及解决方案」「工厂试样记录」里按同样格式补充，输入类型按 v7 Q7.5 的四种分开统计。
- 案例放 `data/backtest/`，不入库。

### 1.3 一线核对

- 请研发逐条核对化言所依据的一线需求清单（内部材料）：「这是不是你们说的、化言的做法对不对」。确认过的在答辩里标「一线确认」，被否定的照实修改。
- 问研发对积分与记功的看法：这套回报能不能让他们愿意贡献、还缺什么、积分最好怎么用。原话连同反对意见一起保留。

### 1.4 觉的两域证据页

- 觉的骨架（问题模板 × 对象、打分、发布、问题总线）来自赛前在物流场景的项目，在那里学会判断「该不该调车、该不该限流」，并在困难负样本上保持沉默；在化言里用同一套方法重新实现、重新训练。
- 做一页两域对照：决策目录、对象、对照方、打断与误报、校准、发现开销、**不利面**（低召回操作点、高召回时打断多于规则告警、部分决策只学到一半、全部是合成数据）。数字与图复用物流项目已有的评估包，注明出处与合成数据口径。
- 可选：在觉视图加入口，回放物流项目里「全网空车潮时规则告警响个不停、觉保持沉默」那一段。
- 口径：同一套方法与计算层，各自实现、各自训练，不是同一套代码，没有迁移权重。边界：「这证明发现层可训练、可校准、会沉默，不证明物流业务效果。」

## 2. v7 之后

### 2.1 真实试用证据包

- 一线研发和业务员**自己操作**，不按脚本；只记岗位，不写姓名；取得授权后录屏。
- 至少拍下一个可观察的业务状态变化，首选契的四步：研发判一次「已有产品适用」并授予 → 产品经理批准 → 下一位同类客户在前台直接命中 → 研发撤销后回到研发；研发和产品经理都拿到「被使用」记分。
- 请研发看自己的「我授予的能力」与「知识与积分」页，原话连同反例保留；顺带问 1.1 的 Q5。
- 请他们给出收益测算的粗略参数，填进 Demo 已有的估算卡。
- 如果试用中出现「人自发做了、觉没提」的决定，记下来，作为觉也会漏、结构进化有原料的真实记录。
- **验收**：一页证据包（时间、岗位、任务、结果、原话、反例、一线需求核对结果）加一段授权录屏。

### 2.2 答辩材料按决赛评审维度重写

- 以第 0 节的两根支柱做骨架：先讲定位句「问对的人，只问一次」，再讲觉、契，每条配「别人通常怎么做 / 化言怎么做 / 代码、测试与报告」。README 开头加一张「两根支柱 + 证据」的表。
- 评审维度对照表替换 README 现有的速读表。
- 路演按 Q1 准备长短两个版本；短版只保留三态和自进化安全对照。
- 问答库：
  - VISION 第 10 节与 PITCH 第 13 节的全部问题；
  - 已知短板各写一句诚实的答法（对照数字来自模拟、检索不和企业 RAG 比、推进类决策是规则打分、积分没有兑现、觉在真实数据上的增益待验证）；
  - 「人有我有」逐项：我们也有，代码在哪；「人有我弱」逐项：照实承认并说补法；
  - 「试样失败之后呢」：产品原因走知识冲突，需求条件缺失走 `trial_rework`（v7 Q5.5）；
  - 「觉在高召回端是不是不如规则」：照实说物流项目的不利面。
- 讲 30 → 14 → 5（人工中转节点）时，同时讲研发开工时的需求完整率。
- 讲数字时说清出自哪一套口径（第 3 节第 3 条）。
- 一页纸质材料：定位句、两根支柱、「人有我有」对照表。

### 2.3 管理层视图（并入现有页面，不新开页）

- 「知识与积分」页加一栏「谁的判断被谁用了」：按人汇总「被使用」记录，跨研发的使用单独标出。
- 「评测」页加一块组织视图：需求分流（自助、交销售、进研发、复用、汇聚）、研发开工时的需求完整率、「每解决一个客户问题需要几次研发判断」随时间的线、授予与撤销次数。数据来自 v7 的 `capability_used`、决策记录与 `app.workload`。

### 2.4 「觉也会漏」：只讲机制和试点方案

- 现状：人执行生效动作时，同一对象上没有已提出的问题，门面记一条 `human_decision`，目录统计会数它；模拟业务周里这类记录为 0，不拿它当数字证据。
- 问答库准备机制说明（代码位置）与试点方案：影子模式、抽样复核、事后回放。2.1 试用里若出现真实记录，就用它来讲。

### 2.5 钉钉入口（待讨论）

- 候选三档：推卡片（觉的问题卡、贡献回馈卡）；卡片按钮回调门面签字方法；转发客户聊天文本进入 L1 抽取。契做完后，觉提出的 `qi_grant` 做成「授予 / 不授予」两个按钮的卡片最顺。
- 讨论时要考虑：第二档要申请企业内部应用和公网回调地址，一周内不可控；推送点放在 hub 或门面，不放进只读的 `bus.py`；推卡片会把客户原话送进钉钉群，碰到 Q3 的保密边界。

### 2.6 现场兜底

- 公网 Demo 可用性检查；断网时切本地离线回放；手机投屏失败改用录屏；BYOK 现场试跑；在有 `uv` 的环境复跑 11 个测试。
- **多准备一个本地版本**：用真实产品目录起草的种子（v7 Q4.5）跑的那一版，只在现场机器上。
- 两轮完整彩排，包括问答攻防。
- **验收**：拔掉网线，现场片段照样能讲完。

## 3. 硬约束

1. 测试总数仍为 11 个，只扩已有测试。
2. 真实资料绝不进公开仓库：终赛资料、口述案例、真实产品目录、由它们编译或起草出的一切都放 `data/` 下（已被 git 忽略），通过配置切换，不覆盖 `seeds/`；提交前用 `git status` 核对。
3. 两套口径并列：公网 Demo 是模拟数据，本地「真实数据版」用真实资料；所有数字标明出自哪一套，现场切换版本时口头说明。
4. 防止评测标签泄漏：回测标注前冻结词表（1.2）；业务问答样例只作评测集，不进任何来源。
5. 只读模块不动：`bus.py`、`clock.py`、`events.py` 等共用模块只读；通知类出口放在 hub 或门面。
6. 口径统一：「企业 RAG、ELN、钉钉的接口位置已具备，正式对接在试点阶段」；契的适配器只说「替身 RAG 已接通，企业 RAG 按同一接口接入」。
