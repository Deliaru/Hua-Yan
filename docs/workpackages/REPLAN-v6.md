## 0′ 方向校准（v6.1，2026-10-12 第二批一线反馈，优先于本文其余各节）

> 依据：功能化学一线业务需求交流中对岗位职责的定性归纳（不是工时统计）。
> 结论先行：**V6 的机制方向是对的，但价值的论证落点错了。** 原稿把证据押在「绕过了谁、少签几次字、研发介入次数」上；研发真正关心的是**需求不明确 → 开发不达标 → 返工 → 没精力做中长期课题**。本节改落点，不改架构、不推倒已提交的 V6-1、V6-2。

### 0′.1 根因：一条因果链，不是六个并列问题

```
需求在源头没有被完整、准确地定义（客户只会说现象；必要的工艺条件、限制条件没人负责问全）
  └─ 按岗位顺序逐手转述，每转一手丢一部分、变一部分（失真）
       ├─ ① 信息不全的需求进入研发 → 开发目标偏差 → 试样不达标 → 返工        ← 研发资源最大的损耗点
       ├─ ② 研发只能回头找销售、产品经理补问、澄清、纠偏 → 跨岗反复对接 → 岗位职责交叉  ← 现象，不是根因
       └─ ③ 每次判断都留在个人脑子里 → 同类问题下次重来、短平快重复进研发
            └─ 研发产能被短期返工与重复工作占满 → 中长期课题被挤压 → 企业长期创新能力受损
```

- **切入点（具体、可证）**：研发开工前，需求是否已经被说清楚。
- **企业级落点（有机制支撑的宏大立意）**：研发产能是功能化学企业最稀缺的创新资源。化言决定这份资源被什么占用：只有说清楚的、真正新的需求才占用研发；研发每做一次判断，组织就学会一次，下一次同类需求不再占用研发。
- **修正 0.1 节**：岗位偏移不是靠「重新划分职责」解决的。它是需求沟通不畅的结果：需求一开始就被准确理解、补全、转译并且能复用，被迫参与反复沟通的人自然会回到本职。PPT 里的必要协作都保留：销售反馈市场需求、产品经理跨部门协调、研发做现场排查和定制方案。**要拿掉的是因为信息缺失、转述错误、重复需求才被迫发生的无效工作。**
- **不说「研发不再处理客户需求」**，改说**研发不再为说不清的需求返工、不再为同一类问题重复判断**。

### 0′.2 现有机制审查：哪些是关键，哪些是辅助

| 因果环节 | 关键机制（已实现） | 状态 |
|---|---|---|
| 源头说不清 | 觉的 `ask_slot`：按「问到后推荐或升级会不会改变」决定追问；Jue-K 的追问标签已含「应升级且为研发必问信息」。客户自助会话里由觉直接追问，不依赖业务员习惯 | 已有，V6-1 已接到客户自助 |
| 转述失真 | 分层转译 + 每条带客户原话（`quote_refs`）+ 引用知识归属；`distortion` 发现漏承接的约束和无原话条目 | 已有 |
| 开工前不完整 | `ask_back`：L2/L3 起草时发现缺一项会改变转译的信息就回问客户；**`accept_requirement` 在有未答回问、未处理失真时不能接单**，这本身就是「开工门槛」 | 已有，原叙事没讲 |
| 是否满足客户 | 试样记录 + 业务员录入客户评价（`market_eval`）；发布前必须有通过的试样和客户评价 | 已有；缺定量的性能目标（如牢度等级），列入长期 |
| 不达标后从头解释 | 试样不达标、客户评价不通过之后，觉不会重新打开同一张单的回问 | **缺口**（见 0′.4 的 P1） |
| 同类问题重复消耗 | C′ 扩产品适用范围（研发判一次，以后在 L1 就命中）；D 合并重复需求；`knowledge_conflict`（试样失败和说明书的适用声明冲突时，提示更新说明书）；研发与产品经理的知识沉淀 | V6-3 已完成（含 V6-3.1 修补），已有 |

- **觉的独特性（讲这一条，不讲「多 Agent」）**：
  - 普通 Agent 只回应被提出的请求，知识库只回答被问到的问题，流程引擎只执行预先画好的步骤。
  - 觉持续观察整个组织的状态，回答的是「此刻需要谁、做哪一个决策」：缺哪条信息会改变下游判断、这份需求该不该占用研发、几份需求是不是同一个课题、产品声明和试样证据是否冲突。
  - 觉不调用大模型，可审计；Jue-K 从人的处置中学习，组织的判断习惯因此可以训练、可以复用。
  - 一句话：**觉是研发注意力的分配层。**
- **辅助能力（照常保留，但不当主角）**：Jev（推荐和披露的概率）、角色 Agent（起草）、自动执行、签字次数减少、RouteStrip「绕过了谁」。它们是手段，不是价值本身。
- **原叙事讲过头的地方**：「人工节点越少越好」「研发介入次数越少越好」。真正该比的是：研发介入的那几次是否有效，需求进研发时是否完整。

### 0′.6 标准答案（替代第 7 节）

> 研发没有时间做中长期课题，根子在需求不明确：客户只会说现象，必要的工艺条件和限制条件没人负责问全，信息再经业务员、产品经理逐手转述，到研发时既不全也走了样。研发只能边开发边补问，产品不达标就返工；同类问题下次又从头来。销售、产品经理、研发职责的交叉，正是这种反复对接的结果。
>
> 化言不是把这条链搬到线上，而是在研发开工前把需求说清楚，并让组织记住每一次判断：觉持续计算「缺哪条信息会改变下游判断」，在客户对话、转译和回问中把它问出来，没问清就不进入接单；需求按性质分流，只有现有产品解决不了的才占用研发；研发判定一次「已有产品适用」，产品经理就把它变成产品边界，同类需求以后在客户自助阶段就解决；重复的短平快需求由产品经理附商业判断汇成一个课题。销售、产品经理、研发之间必要的协作都保留，拿掉的是因信息缺失和重复而被迫发生的无效工作。
>
> 模拟验证显示，真正需要研发的需求，进入研发时必问信息完整率从约 49% 提高到 91%，需退回补问的比例从约 95% 降到约 20%。返工次数与研发工时结构的改善是合理预期，需要企业试点验证。

## 0. 一句话

一线原话：原来是黑线（需求 → 销售记录 → 产品经理转述 → 研发），化言要把它变成红线（需求 → 研发）。
**四层是知识边界，不是审批节点。** 信息自动跨层转译，人只在「真有判断价值」的地方出现。

答辩要回答的问题，本轮必须能用**真实状态变化**回答：

| 岗位 | 过去被迫在做 | v6 之后不再做 | 回归到 |
|---|---|---|---|
| 业务员 | 回答重复技术问题、记录需求、当传话人 | 客户自助问答；需求由 Agent 采集，**升级不再要业务员签字** | 报价、采购、客户关系 |
| 产品经理 | 逐单转述需求、在市场和研发之间反复解释 | 逐单 L2 转译交给产品经理 Agent 在后台做 | **维护产品适用范围、判断产品机会、纠正转译偏差**（见 0.2 节）；判断沉淀为本人名下的 L2 知识 |
| 研发 | 补问缺失信息、纠正需求、审定已有产品复用、处理短平快 | 复用已发布产品**不再找研发审定**；同类需求先合并；可一键「不立项」 | 只看已转译、带原话的有效技术需求，结合产品经理的商业判断决定是否立项 |

### 0.1 岗位为什么会偏移（根因）

> v6.1 修订：岗位偏移是需求沟通不畅的**结果**，根因与证据以 0′.1、0′.3 为准；本节四条保留为组织层面的展开。

**传统流程按岗位顺序组织，而不是按需求性质组织。**

1. **每张单都走全程。** 不论难易，需求都要依次经过业务员 → 产品经理 → 研发。于是业务员在做技术问答，产品经理在做传话。
2. **信息每转一手就丢一部分，下游只能回头补问。** 研发的时间花在采集信息、纠正需求上。
3. **判断能力只集中在研发。** 只有研发能说「能不能做」，所有拿不准的问题都涌向研发，短平快挤占中长期研发。
4. **经验留在个人脑子里。** 下一次同类需求又从零开始，产品经理没有时间做产品组合与生命周期管理。

**只把这串签字从线下搬到线上，四个根因一个都没变**（v5 本质上就是这样：业务员签升级 → 研发审复用 → 研发接单，顺序照旧）。v6 改的是组织方式：

- **按需求性质分流**，不按岗位顺序（A–D）；
- **知识复用让常规需求不需要人**（公开资料、适用范围内自动复用）；
- **人只在判断点出现**（立项、技术确认、保密、发布、商务、产品边界）；
- **产品经理的判断上移到产品层**，管机会和产品，不管单子；每一次判断都变成系统下一次能自动执行的依据。

**判别标准（答辩用）：** 对每个岗位问一句，「过去每张单都要做的事，现在还要不要做？」，用 A–D 的真实运行逐项回答（见 V6-5 岗位判别表）。

### 0.2 产品经理：与系统协作，不被 Agent 替代

原则：**产品经理不回到每张单上，而是在「产品」与「例外」两个层面和系统协作。** 产品经理 Agent 是后台转译能力，负责逐单 L2 转译；真人产品经理（`pm:P01`）负责只有人能做的三件事：

| 产品经理的工作 | 怎么和系统协作 | 岗位价值 |
|---|---|---|
| **1. 维护产品适用范围** | 研发判定「已有产品适用，只是超出标注范围」（不立项时指定产品，或审定采用了产品经理 Agent 的复用建议）后，觉提出 `scope_update`「是否扩展该产品适用范围」；产品经理 Agent 起草，`pm:P01` 签字；结果沉淀为本人名下的 L2 知识并记分 | 扩展直接写进产品匹配所用的 `Product.solves`：**产品经理每扩一次，这类需求以后在客户自助阶段就命中产品，不再生成需求单。** 研发对每一类超范围用法只判断一次，产品经理把这次判断变成产品边界 |
| **2. 判断产品机会** | `opportunity` 由 `pm:P01` 签，签字时写商业价值与产品方向说明，随合并单交研发 | 立项 = 产品经理的商业判断 + 研发的技术判断，不再由研发一个人拍板 |
| **3. 纠正转译偏差（只处理例外）** | 研发退回需求单或觉发现失真时，派给 `pm:P01` 修正 L2，而不是让 Agent 自己重写；修正可沉淀为知识 | 产品经理只看出问题的单子；修正经验变成知识，下一次 Agent 转译会引用 |

归属：产品经理 Agent 的草稿不记分；`pm:P01` 的修订、适用范围扩展记在本人名下，被引用时按原作者记分。本轮**不**给 `pm:P01` 恢复个人 Agent。

## 7. 验收问题的标准答案（材料与答辩用）

> v6.1：以 0′.6 为准，下文保留为岗位层面的补充说法。

> 传统流程按岗位顺序组织，每张单都要走完业务员、产品经理、研发，所以业务员在做技术问答、产品经理在做传话、研发在补信息和处理短平快。化言改的不是签字的介质，而是组织方式：按需求性质分流，人只在判断点出现。
>
> 化言把三件事从员工身上拿走了：业务员不再当技术问答入口和需求记录员（A、B）；产品经理不再逐单转述（由产品经理 Agent 后台完成），转而维护产品适用范围、判断产品机会、纠正例外——每扩一次适用范围，同类需求以后就不再进研发（C′）；研发不再审定已有产品复用、不再逐张接收重复的短平快需求（C 的自动复用、D 的汇聚）。需求之所以更短地到达研发，是因为觉判断「现有产品不行」之后直接执行升级、产品经理 Agent 直接完成 L2/L3 转译，中间没有人需要再签一次字——而研发拿到的仍是带客户原话、带知识来源、受分层保密约束的需求单。人只留在立项、技术确认、保密、发布和商务这几个真正有判断价值的地方。
>
> 研发是否因此获得更多中长期研发时间，需要企业试点验证；本 Demo 只证明「不必要的研发介入」在机制上被拿掉了。
