## 0. 为什么重整

v3/v4 跑通了端到端链路，但交互和觉的定位偏离了愿景：

1. **人在给助手打字。** 业务员对助手说「客户说：……」，研发逐字口述对外要点和沉淀的知识，助手只做转发。愿景是**助手生产内容，人做判断、签字**。业务员转述客户原话这一步，还把「传话游戏」搬进了系统自己的界面。
2. **确认卡签的是函数参数**，不是内容。「谁确认谁负责」要求签字人看清自己签了什么。
3. **觉只盯链条两头**：L1 槽位、需求单槽位、三个定时统计。L2/L3 之间的交接、对外文本、研发的修改、流程停滞，都不在觉的视野里；该由觉提出的判断时刻散落在提示词和门面规则里。觉只在发言接口被顺带调用，界面上也没有觉视图。
4. **演示是功能巡游**：没有对照组，最强的时刻（回问）被淹没，评委感受不到代价。

## 3. 规格 ①：交互

### 3.1 通用原则

- **工作面在中间，副驾在右侧。** 工作面是这个人的工作对象，人直接在上面干活；副驾栏是助手的批注、建议和私下对话。
- **对外和对内两个通道分开**：发给客户的话、交给下一层的单子，和私下问助手的话，不在同一个输入框里。
- **按钮就是确认。** 「发给客户」「转产品经理」「交研发」「发布」「批准解密」等按钮背后是待确认动作；助手提议的动作以确认卡出现，卡上是内容预览（Q4）。人直接按按钮时调门面，不经过助手。
- **觉的问题挂在它说的那个东西上**：槽位提示在需求卡和输入框旁，失真和泄密批注在对应条目上，回问在业务员会话里，停滞在收件箱里。都显示概率和 `scored_by`。
- **大模型只在需要时调用**：业务员点「帮我回一句」、任何人私下提问、被派单时、提议生效动作时。觉的提词、Jev 推荐、规则骨架不调大模型。
- 离线模式：草稿为录制或规则产物，状态条标注（铁律 6）。

### 3.2 业务员（L1）

| 区域 | 内容 |
|---|---|
| 工作面 | 和客户的对话流。客户发言、业务员发言直接录入（演示者扮客户），不经过助手 |
| 副驾：主动 | 场景需求卡实时填充，每个槽位挂原话；**觉提词**：「问一下用什么缸，问了会改变推荐」，带概率，点一下填入输入框；Jev 推荐卡；没有合适产品时，「建议转产品经理」与起草好的升级说明；回问到达时，「研发需要知道染浴 pH：可以这么问……」 |
| 副驾：按需 | 「帮我回一句」：起草回复，放在输入框上方，采用或修改后发出；私下问：「LV205 能用在气流缸吗？」只查 L1，带出处，越权只显示「谁知道」 |
| 按钮 | 发给客户；转产品经理（Q1）；申请解密（客户懂化学时副驾提示） |

### 3.3 产品经理（L2）

| 区域 | 内容 |
|---|---|
| 工作面 | 产品需求单文档：方向 + 条目；每条左挂客户原话，右挂依据（归属人 · 知识；L3 只见归属）；助手起草的条目带标记 |
| 收件箱 | 派来的升级与机会汇聚（含多位客户的原话）、回问状态、停滞提醒。**打开时草稿已经起好** |
| 副驾：主动 | 2～3 个方向选项（各自依据哪些案例、哪位研发的知识），产品经理选一个或改一个，助手按方向重排条目；觉的失真批注（「客户说过浴比很低，L2 没有承接」）挂在对应条目上 |
| 副驾：按需 | 选中一条说意图（「加上不能影响色光」）；问「以前有没有类似案例」 |
| 包装 | 研发放出对外要点后，助手起草说明书，并对照封存清单自查；觉的对外泄密批注挂在说明书上 |
| 按钮 | 交研发（预览：研发将收到的需求单）；发布（预览：业务员将看到的说明书与用法） |

### 3.4 研发（L3）

| 区域 | 内容 |
|---|---|
| 工作面 | 化学语言需求单，和产品需求、客户原话并排；每条带依据（含原文）和原话 |
| 收件箱 | 待转译的需求单、解密申请、知识冲突、回问答复 |
| 副驾：主动 | 起草化学语言条目与方向假设；觉批注挂在条目上（「缺染浴 pH，已派业务员去问，答复回来后第 2 条会重写」）；研发改了一条后，助手**提炼一条可沉淀的转化知识**：泛化、去掉这位客户的特定信息、指出与已有知识相近或冲突之处 |
| 对外出口 | 研发确认转译、试样通过后，助手起草**「封存 / 放出」两栏**：哪几点是窗户纸、建议封存，哪些可以对外（效果、适用条件、用法），并做泄露自查。研发逐条勾选、修改后签字 |
| 解密（第二档） | 助手按这位客户的问题起草说明：讲到机理，用他能懂的话，不含配方与封存项；研发改深浅后签字（Q3） |
| 按钮 | 确认转译；沉淀（预览：知识条目）；对外要点（预览：封存 / 放出）；批准 / 拒绝解密（预览：客户将看到的内容）；录入试样 |

### 3.6 演示主线（草案，WP-D2 细化）

一个客户、两种结局，按三个病根分三幕：开场讲一个有代价的失败（推了溢流缸的 LV205，客户是气流缸低浴比，回修三次）→ 第一幕单卡对照（信息不完整、转述失真）→ 第二幕回问为高潮，加沉淀和三层对照（可溯源、权责对等）→ 第三幕封存与觉视图快进（窗户纸、飞轮）→ 收尾计数器（感知便宜、行动按需、人负责）。现场只真实输入两三句，其余事先载入。

### 4.2 运行方式

- **写后增量评估**：门面每个改状态的方法结束时，对受影响的对象评估一次（会话槽位、需求单槽位、交接、修改、对外文本），不再依赖界面的发言接口。
- **定时部分**（主题、知识、提问者、停滞）：每次请求检查是否到期（沿用 30 业务分钟）；演示可加速。
- 每次判断写 JueRecord；发布层不变（阈值、去重、证据、悬赏）。
- `huayan/jue/` 仍不 import 网关，文本类信号（对外泄密）用规则匹配算属性，不调大模型。

### 4.4 必须如实说的

- 前置条件划定觉能看到的范围，打分器只在范围内排序和给概率；Jue-K 的增量是校准概率与排序，不是发现规则没想到的东西。
- 回问的 Jue-K AUC ≈ 0.51，**回问实际由规则前置条件驱动**，演示中回问的概率是基率，不说成「模型判断」。
- 新类型在阶段 1 是规则打分，界面标 `scored_by: rule`。
