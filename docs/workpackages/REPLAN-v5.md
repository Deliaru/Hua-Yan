## 0. 为什么重整

v3/v4 跑通了端到端链路，但有三处偏离了愿景：

1. **觉被做成了边上的告警器。** 觉只盯链条两头（L1 槽位、需求单槽位、三个定时统计），流程推进写死在门面和派单里（`add_turn` 自动升级、`hub._hand_over` 确认后派单）；Jev 升级是旁路入口；该由觉提出的判断时刻散落在提示词里（如「主动问要不要沉淀」）。愿景里的觉是「持续判断现在是不是该提一个问题、是什么问题」，**流程应当由觉提出的决策推动**。
2. **人在给助手打字。** 业务员对助手说「客户说：……」，研发逐字口述对外要点和沉淀的知识，助手只做转发；确认卡签的是函数参数。愿景是**助手生产内容，人判断和签字**。业务员转述客户原话这一步，还把「传话游戏」搬进了系统自己的界面。
3. **演示是功能巡游**：没有对照组，最强的时刻（回问）被淹没，评委感受不到代价。

## 3. 角色与交互

### 3.1 角色

| 角色 | 层 | 谁 | 做什么 | 签什么 |
|---|---|---|---|---|
| 业务员 | L1 | 人 + 副驾 | 和客户对话；按觉的提词追问；拿推荐；把试样交给客户并带回评价（Q12） | 发给客户；转产品经理 Agent（升级）；采用 / 不采用现成产品建议（D17）；申请解密；客户评价（Q12） |
| 产品经理 Agent | L2 | **Agent** | 被派到升级时先用 L2 知识查现成产品（D17）；查不到或不被采用时，把场景语言转成产品需求语言，给出方向（如「加一点保护剂，让染料均匀分散」）；处理失真批注与退回；研发放出对外要点后包装说明书 | **不签任何东西**，产出等研发接单或审定；不记积分 |
| 研发 | L3 | 人 + 副驾 | 接单（= 立项，Q13）；把产品需求转成化学语言；改转译、沉淀；封存 / 放出；试样；审定发布；审批解密 | 接单 / 退回；确认转译；沉淀；封存 / 放出；发布；批准解密；录入试样 |
| 主管 | — | 人 | 处理泄露风险 | 冻结权限 |

可见性不变（架构第 3 节）：中间过程只对 L2、L3 开放；产品经理 Agent 只用 L2 知识，L3 只见归属；封存项只对 L3 可见；业务员只拿到包装后的结果。

**积分**：被引用积分在「研发接单」时记给所引 L2 知识的归属人，在「确认转译」时记给所引 L3 知识的归属人；沉淀、试样通过、发布照旧记给研发。

**研发是签字的集中点**（接单、确认、沉淀、封存、发布、解密），这是把产品经理换成 Agent 的代价，见 7.3。

### 3.2 通用交互原则

- **工作面在中间，副驾在右侧。** 工作面是这个人的工作对象，人直接在上面干活。
- **觉的决策挂在它说的那个东西上**，显示 `scored_by`：槽位提词在输入框旁，失真和泄密批注在对应条目上，接单、确认、发布等推进决策在收件箱和工作面顶部。规则打分的推进决策**显示为「到点」而不是概率**，不冒充校准概率。
- **按钮就是签字**（Q4）：副驾把草稿写进领域对象，人按按钮，按钮调门面原子方法。确认卡只用于私聊里副驾的提议。
- **对外和对内两个通道分开**：发给客户的话、交给下一层的单子，和私下问助手的话，不在同一个输入框里。
- **大模型只在需要时调用**：被派到决策、人点「帮我回一句」、私下提问。觉、Jev 推荐、规则骨架不调大模型。
- 离线模式：草稿为录制或规则产物，状态条标注（铁律 6）。

**前端硬性要求**（WP-U2 验收逐条对照，违反即返工）：

1. **离线与现场是同一个工作面。** 离线时客户的话由工作面上的「下一句」按钮填进客户输入框，演示者可改后发出；不做剧本播放器，客户的话不经过副驾。
2. **私聊默认折叠**，标题写「私下问副驾（不会发给客户）」；私聊里不出现签字按钮，签字只在工作面上。
3. **草稿就地出现**：回复草稿预填进「发给客户」的输入框；升级说明、L3 条目、封存 / 放出两栏、说明书出现在各自的位置，带「副驾起草」标记，可直接修改；按钮上方显示的是内容本身，不显示参数 JSON。
4. **收件箱区分「准备中 / 待签」**：准备中只显示主人在做什么，待签才有按钮。
5. **没有产品经理页面**：产品经理 Agent 的产出只在研发工作面、三层对照页、觉视图上出现。
6. **觉视图**：以研发身份打开看到整条线程，业务员只看到自己签的三类决策（推荐还是升级、客户评价、回问提示）；横轴是业务时间，每个决策一条泳道；Jue-K 打分画曲线与阈值，规则打分画阶跃并标「规则」；节点显示主人、签字人、处置结果；底部「觉的大模型调用 0 次」取自计量器，不写死。
7. **接口样例先行**：A 在 T+2 提供 `jue_timeline` 与两个工作面的 JSON 样例（放 `web/src/fixtures/`），前端据此开工，不自造数据结构。

### 3.3 业务员（L1）

| 区域 | 内容 |
|---|---|
| 工作面 | 和客户的对话流。客户发言、业务员发言直接录入（演示者扮客户），不经过助手 |
| 副驾：觉的决策 | 场景需求卡实时填充（每个槽位挂原话）；**追问**提词「问一下用什么缸，问了会改变推荐」带概率，点一下填入输入框；**推荐还是升级**：Jev 推荐卡，或「建议转产品经理 Agent」与起草好的升级说明；**回问**：「研发需要知道染浴 pH：可以这么问……」（话术与证据里只出现槽位，不出现 L3 的转译理由）；**客户评价**（Q12） |
| 副驾：按需 | 「帮我回一句」起草回复，预填进发送框，采用或修改后发出（「发给客户」由门面做规则拦截：命中封存项或 L3 关键术语时不发出，提示业务员改写；不生成研发的问题）；私下问「LV205 能用在气流缸吗？」只查 L1，越权只显示「谁知道」 |
| 现成产品建议（D17） | 产品经理 Agent 查到现成产品时，收件箱出现待签卡：产品、用法、一句面向客户的说明（标「产品经理 Agent 起草」）、依据「产品经理 P01 的历史案例（L2）」；采用即发推荐卡给客户，不采用写理由 |
| 按钮 | 发给客户；转产品经理 Agent；采用 / 不采用现成产品；申请解密（客户懂化学时副驾提示）；录入客户评价 |

### 3.4 研发（L3）

| 区域 | 内容 |
|---|---|
| 收件箱 | 觉提出的、签字人是这位研发的决策：接单、确认转译、沉淀、封存 / 放出、对外泄密、发布、解密申请、知识冲突 |
| 工作面 | 化学语言需求单，和产品经理 Agent 的产品需求、客户原话并排；每条带依据（含原文）和原话；觉的批注挂在条目上（失真、「缺染浴 pH，已派业务员去问」） |
| 接单 | 产品经理 Agent 起草好产品需求单后，觉提出「是否接单」；有未答回问或未处理失真时按钮不可签。研发接受，或写理由退回（Q10） |
| 副驾：准备 | 接单后起草化学语言条目与方向假设；研发改了一条后提炼可沉淀的转化知识（泛化、去掉这位客户的特定信息、指出与已有知识相近或冲突之处）；试样与客户评价通过后起草**「封存 / 放出」两栏**并做泄露自查；说明书命中封存项时改写说明书 |
| 发布审定 | 产品经理 Agent 包装好说明书后，觉提出「能不能发布」：工作面上是业务员将看到的说明书与用法，以及对外泄密检查的结果 |
| 按钮 | 接单 / 退回；确认转译；沉淀；封存 / 放出；发布；批准 / 拒绝解密；录入试样 |

### 3.5 产品经理 Agent（没有工作台）

- 它的工作在研发工作面、三层对照页和觉视图上可见：起草了什么、依据了谁的知识、被研发退回过几次。
- 被派到觉的决策（现成产品复用、升级、机会汇聚、L2 回问、L1 → L2 失真、退回、包装说明书）后自己准备，产出只是草稿；现成产品建议由业务员签字，其余由研发签字。
- **先查现成产品**（D17）：L1 只按说明书的适用表匹配；产品经理 Agent 还能看历史案例与 L2 转化对照，能找到「说明书没写、但案例里用过」的方案。找到就不占用研发。
- 种子里的 `pm:P01` 保留为**历史 L2 转化知识的归属人**（Agent 引用这些知识时照常记分给 P01），只是不再有工作台；解说词：「过去产品经理积累的转述经验，现在由 Agent 引用，功劳仍记在本人名下」。
- 对外泄密命中时，它只收到「第 n 句需研发处理」，**不拿到命中的封存内容**；改写由研发副驾完成。

### 3.7 演示主线（草案，WP-D2 细化）

一个客户、两种结局：开场讲一个有代价的失败（推了溢流缸的 LV205，客户是气流缸低浴比，回修三次）→ 第一幕单卡对照（信息不完整、转述失真）→ 第二幕在觉视图上走一遍循环：追问 → 升级 → 产品经理 Agent 先查现成产品（「已查 3 个案例，无现成产品」）→ 第二位客户同类升级，觉在主题泳道上提出「是否立项」（机会汇聚，D18）→ 产品经理 Agent 转述 → 研发接单 → 回问（高潮）→ 沉淀 → 试样与客户评价 → 封存 → 发布 → 新客户在 L1 命中 → 收尾计数器与飞轮（这一轮又多会了一件事，觉又多了一批带处置结果的样本）。

**支线（20～30 秒，D17）**：另一位客户、另一个现象，事先载入到「现成产品建议待签」：产品经理 Agent 从 P01 的历史案例找到现成产品，业务员签字，客户当场拿到推荐；研发收件箱什么都没出现。解说：「不是每个升级都要占用研发」。这个支线的主题不能和主线相同（能复用就不构成机会汇聚）；种子要有一条「说明书没写、P01 案例里用过」的产品与条件组合。业务员和研发两个人类角色，现场只真实输入两三句，其余事先载入。

「事先载入」= 用门面离线跑到某个检查点（如「研发待接单」）并保存状态，界面从该状态起继续现场操作；不是播放录屏，也不是脚本替人按按钮。

## 4. 觉：全过程的决策点发现器

### 4.1 定义

- **输入**：整个过程的状态——会话、需求单（各层条目、草稿、修改、回问、退回、签字情况）、对外文本、试样与评价、产品、检索行为。
- **决策目录**：模板 = 决策 × 对象类型 × 前置条件 × 打分 × 主人（谁准备）× 签字人。分两类：**推进类**（流程往前走需要有人决定）与**异常类**（出了需要处理的情况）。
- **输出**：每个时刻对每个「决策 × 对象」给出「此刻需要被决策」的概率；超过阈值即提出问题。绝大多数时候接近 0。
- **不做的**：不回答问题（准备答案的是产品经理 Agent 与副驾，推荐与披露的概率由 Jev 给出）、不调用大模型、不签字。主人与签字人由模板写定，不是觉临时决定的。

### 4.2 统一循环

```
状态变化 → 觉评估受影响的「决策 × 对象」→ 提出问题（总线）→ 派给主人准备（产品经理 Agent / 副驾起草）
        → 签字人在工作面上签字（按钮）→ 门面原子方法改状态 → 状态变化
```

- 一个问题有两个阶段：**准备**（派给主人，产出草稿）→ **待签**（草稿就绪，出现在签字人的收件箱）。前置条件写「上一步已签字、本步未签」；「无未答回问、无未处理失真」之类是**可签条件**，不满足时按钮不可签，不作为前置条件。
- **准备完成由谁标记**：门面原子方法 `mark_prepared(qid, by)`，由 hub 在主人的 Agent Loop 结束后调用（离线时在规则骨架起草后调用）；不暴露为助手工具。主人是人（如业务员副驾起草升级说明）时，草稿写入即 `mark_prepared`。
- **需求单何时存在**：业务员签字 `escalate()` 时，门面创建一张空需求单（`status=draft`，只带会话引用与客户原话）；机会汇聚发布时同样创建一张空单并关联主题。觉随后对这张单提出 `accept_requirement`，准备阶段派给产品经理 Agent 起草 L2。
- **机会汇聚何时关闭**：关联的需求单被研发接单时，门面关闭 `opportunity` 问题（resolution `accept`）；被退回则保持打开。
- 门面只保留原子方法与权限校验；**删除 `add_turn` 内的自动升级与 `hub._hand_over` 的写死派单**；`agents.dispatch()` 只派总线上的问题。
- 追问 `ask_slot` 保持提示通道（每轮发言给业务员的提词，不进总线），但同样写 JueRecord、进觉视图。

### 4.3 决策目录

「状态」：✓ 已有，**新** 阶段 1 新增，二 第二档。「阶段 1 打分」中「规则」为模板 `rule_score`，界面标 `scored_by: rule`。

| 决策 | 类 | 对象 | 前置条件（何时到点） | 主人（准备） | 签字 | 阶段 1 打分 | 状态 |
|---|---|---|---|---|---|---|---|
| 追问 `ask_slot` | 推进 | 会话 × 槽位 | 缺失槽位会改变候选 | — | —（提示） | Jue-K | ✓ |

| 机会汇聚 `opportunity` | 推进 | 主题 | 同类升级在窗口内反复出现、无对应产品 | 产品经理 Agent（合并起草） | 经「接单」生效 | Jue-K | ✓ |

### 4.4 运行方式

- **写后增量评估**：门面每个改状态的方法结束时，对受影响的「决策 × 对象」评估一次；不再依赖界面的发言接口。
- **异常类自动关闭**：异常类问题（失真、对外泄密、知识冲突）在下一次评估时前置条件不再成立（例如研发已改写说明书），门面以 `answered` 关闭，处置记入 JueRecord。
- **定时部分**（主题、产品 × 条件、提问者、停滞）：每次请求检查是否到期（沿用 30 业务分钟）；演示可加速。
- 每次判断写 JueRecord；问题的处置通过 `question_resolved` 事件与 JueRecord 关联，成为标签。
- `huayan/jue/` 仍不 import 网关；文本类信号（泄密）用规则匹配算计数。

### 4.5 数据飞轮

| 飞轮 | 输入 | 产出 | 本次 | 后期 |
|---|---|---|---|---|
| 知识 | 每一次升级、研发的每一次修改 | 经研发确认的转化知识；发布的新品回到 L1，同类需求不再升级 | 已有；沉淀改为副驾提炼、觉提出 | L2 知识的增长（见 4.7） |
| 判断 | 每次判断（JueRecord）+ 人的处置 | 校准后的概率、按代价定的阈值、重训的 Jue-K | 记录完整；按模板统计被忽略率，给出阈值建议（只对 Jue-K 打分的决策） | 真实处置回填、在线校准 |
| **决策目录** | 被忽略的问题（提多了）；**人自发决策**（漏了） | 已有决策点的前置条件与阈值调整；**新的决策点** | 只记录：「人自发决策」严格定义为**执行生效动作时，同一对象上没有已提出的对应问题**，记录动作、对象与当时的属性快照 | 对人自发决策按（动作 × 对象类型）聚类，浅层决策树学出候选前置条件，生成候选模板；候选作为问题提给主管，批准后写入模板目录（Q11），先用规则打分，下一轮进入 Jue-K 训练。本地计算，不调大模型；目录的结构性变化总是人签字 |

不在模拟业务周上演示「挖掘新决策点」：模拟周由我们的脚本生成，挖出来的只会是脚本本身，是循环论证。

### 4.7 必须如实说的

- 推进类决策在阶段 1 由规则打分：到点即提出，没有学习成分；觉视图上画成阶跃并标「规则」，解说时不说「概率」。Jue-K 的价值在时机和必要性不确定的决策上（追问、机会汇聚、拼凑）。
- 前置条件划定觉能看到的范围；新决策点靠后期的目录飞轮，不靠打分器「想到」。本次只记录飞轮所需的数据，不说「已自动发现」。
- 回问的 Jue-K AUC ≈ 0.51，**回问实际由规则前置条件驱动**，演示时不说成「模型判断」。
- OneJev 读属性比规则表达式稳，但概率未校准（平静负样本均值 0.52），不能直接放宽前置条件。
- 对外泄密用规则匹配，**挡不住换个说法的泄露**，与 VISION 第 7 节「不说零泄露」一致。
- 现成产品复用由规则「到点」提出；找不找得到取决于产品经理 Agent 检索 L2 知识的结果，演示数据中的那条案例是我们构造的模拟数据。
- 产品经理换成 Agent 后，**L2 转化知识本次不增长**（研发只沉淀 L3；研发接单时对 L2 的修改沉淀为 L2 知识留到后期）。
- 若 Q12 选备选方案：「试样即市场评价，由研发录入」是简化，待确认。
