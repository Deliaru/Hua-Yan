# 业务周对照：签字推进的真实链路上的定时发现，以及处置 / 不处置

> 全部为模拟数据：占位种子 + 程序生成的模拟业务周 `data/week/w1`（5 个业务日，130 条剧本：111 段客户会话、7 次试样、12 次业务员提问），注入 7 个情况（3 个真注入、4 个困难负样本）。
> 复现：`uv run python scripts/run_week.py --week data/week/w1`（6 次运行共约 1.5 分钟；同一剧本重跑 `metrics.json` 一致）。
> 数字见 `metrics.json`，图 `week_detection.png`、`week_escalations.png`；运行目录 `runs/week-w1-<发现器>-<分支>/`，处置记录在其中的 `week_log.jsonl`。决策目录的逐模板统计见 `docs/reports/catalog_stats.md`。

## 怎么跑的

- **流程按签字推进**：觉提出问题 → hub 派单、离线骨架准备（起草需求单、转译、包装、复用 / 汇聚提议）→ 进入待签后「模拟人」按 C12 签字（退回率 0）→ 状态改变 → 觉再看。运行器只扮演客户和签字的人，不在代码里写死「下一步做什么」。
- **真实链路**：会话 = 模拟客户开场 → 按觉的提示追问 → 推荐或由觉提出升级、业务员签字；试样走 `record_trial`；业务员提问走知识库检索（越权部分被拦截并记事件）。**抽取为规则、Jev 为桩、起草走 hub 离线骨架**，零成本。
- **定时发现**：每个业务日 11、13、15、17 点 `scan` 一次，事件触发的检查照常进行。三种发现器只换定时三类（机会汇聚、知识冲突、泄露风险）的模型，其余链路完全相同：
  - 觉原型（`config/templates/`，规则前置条件 + 规则打分）；
  - Jue-K（`models/jue_k/`，本地推理）。定时三类在 40 个生成周的真实链路事件上训练，w1 用另一个种子生成、不参与训练；
  - 规则告警（`config/baselines/rule_alert/`）：常见做法，比如「同一主题升级 ≥ 3 次就报」。
- **两个分支只在定时三类的签字上不同**。`handle`：真注入上的问题由对应的人签字（机会汇聚 → 研发合并需求单并接单，之后转译确认、1 个业务日后录入通过的试样、市场评价、对外要点、研发发布；知识冲突 → 更新说明书；泄露风险 → 冻结高层级访问），不在注入清单里的问题 dismiss。`ignore`：定时三类只记录发现、不签字。
- 运行器扮演客户，所以读需求卡；注入清单只在 `handle` 分支决定签不签、以及算指标时读（铁律 5：只在 `eval/`）。

## 发现（`ignore` 分支）

命中 = 在注入的 `[最早合理发现, 最晚有效发现]` 窗口内发现、且 family 与对象一致。提前量 = 离窗口截止还有多久。

| 发现器 | 真注入命中 | 困难负样本误报 | 平均提前量（命中的） | 注入外的发现 | 发现环节大模型调用 |
|---|---|---|---|---|---|
| 觉原型 | 3 / 3 | 1 / 4（inj:7） | 53.1 小时 | 0 | 0 |
| Jue-K | **3 / 3** | **0 / 4** | 53.1 小时 | 0 | 0 |
| 规则告警 | 2 / 3 | 2 / 4（inj:5、inj:7） | 54.0 小时 | 2 | 0 |

逐条（发现时刻）：

| 注入 | 内容 | 觉原型 | Jue-K | 规则告警 |
|---|---|---|---|---|
| inj:1 机会汇聚 | 锦纶氨纶 + 气流缸的色花，多位客户反复升级、无产品可用 | 10-12 12:46 ✓（第 2 次升级） | 10-12 12:46 ✓ | 10-12 13:06 ✓（等到第 3 次升级） |
| inj:2 困难负样本 | 同一个客户就同一无解需求反复问 | — | — | — |
| inj:3 困难负样本 | 同一现象多次，都有产品能解决 | — | — | — |
| inj:4 知识冲突 | 某产品在声称适用的面料上 3 次试样失败、原因为产品 | 10-14 15:00 ✓ | 10-14 15:00 ✓ | 10-13 13:51（早于最早合理时刻：规则「失败 ≥ 1 次」在第 1 次失败后就报，不计命中） |
| inj:5 困难负样本 | 1 次失败、原因是设备，另有正常通过 | — | — | 10-16 15:00 ✗ 误报 |
| inj:6 泄露风险 | 某业务员短时间内多次换角度问同一产品的原理和配方 | 10-14 11:00 ✓ | 10-14 11:00 ✓ | 10-14 11:00 ✓ |
| inj:7 困难负样本 | 另一业务员正常地连续问多个不同产品的用法 | 10-12 15:00 ✗ 误报 | — | 10-12 15:00 ✗ 误报 |

看到的：

- **三者的差别在两类异常上，不在机会汇聚上**。本周 inj:1 主题第 1 天就有 3 次升级，觉在第 2 次、规则告警在第 3 次报出，只差 20 分钟。差别在知识冲突（规则在第 1 次失败后就报，后来又误报了设备原因的 inj:5）和泄露风险（觉原型和规则都误报了正常问用法的 inj:7）。
- **Jue-K 是唯一没有误报的**。泄露风险上它主要靠「要求讲原理的次数」区分 inj:6 与 inj:7（`docs/JUE_K_TRAINING.md` 第 11 节）；觉原型的规则 `0.05 × n_blocked + …` 被检索的拦截计数推到饱和，对两人都报。
- 规则告警的知识冲突没有「说明书已更新就不再提」的前置条件：`handle` 分支里研发更新说明书后，同一个问题在之后每次扫描都被再提出（`week_log.jsonl` 中 HY-LV101 共签 22 次）。觉的模板有这个前置条件，只提一次。

## 后果：处置 vs 不处置（`handle` 分支，inj:1 主题）

| 发现器 | 分支 | 发现时刻 | 新品发布 | 发现后同主题升级 | 发现后 L1 直接命中 | 全周升级次数 |
|---|---|---|---|---|---|---|
| 觉原型 / Jue-K | ignore | 10-12 12:46 | — | 4 | 0 | 15 |
| 觉原型 / Jue-K | **handle** | 10-12 12:46 | 10-13 12:46 HY-LV206 | **3** | **1** | **14** |
| 规则告警 | ignore | 10-12 13:06 | — | 3 | 0 | 15 |
| 规则告警 | handle | 10-12 13:06 | 10-13 13:06 HY-LV206 | 2 | 1 | 16 |

觉原型与 Jue-K 在机会汇聚上的发现与处置完全相同，合为一行。处置分支在发现当时合并需求单、接单、确认转译，1 个业务日后试样通过并发布 HY-LV206；10-15 那位客户在 L1 直接拿到新品推荐，不再升级。规则告警的 handle 分支全周升级反而多 2 次：它在第 1 次失败后就让研发把 HY-LV101 的适用面料改掉，比觉早约 1 天，于是 10-14 两段涤棉会话（sess:50、sess:60）改为升级，而在觉的分支里它们仍被推荐 HY-LV101。按注入，HY-LV101 在涤棉上确有问题，所以这里不能简单算作早报的代价或收益：规则这次报对了方向，但它在只有 1 次失败时就报，同样会报设备原因的 inj:5。图 `week_escalations.png` 是按天的升级次数。

`handle` 分支的完整签字记录（Jue-K）：机会汇聚（合并 req:4 进 req:2）→ 接单 → 确认转译 → 试样 → 市场评价 → 对外要点 → 发布；10-14 11:00 冻结 S02 的高层级访问；10-14 15:00 更新 HY-LV101 说明书。觉原型另有两次对 S01 的泄露风险提问被 dismiss（误报）。

## 必须如实说明的限制

- 只有 1 个模拟业务周，数量很小（inj:1 主题全周只有 5 次升级），结果只能看方向，不能当统计结论。
- 抽取为规则、Jev 为桩、起草为离线骨架；模拟客户与规则抽取共用种子中的口语说法表，会话环节偏乐观。
- 签字由「模拟人」在问题进入待签后立即完成（退回率 0），试样结果设为通过；真人的处理延迟和退回不在这里。动作全部只改变本系统内的状态。
- 注入窗口、困难负样本由生成器按规则构造（`src/huayan/sim/week.py`），不是真实业务记录；Jue-K 的泄露风险依赖当前的检索口径。
