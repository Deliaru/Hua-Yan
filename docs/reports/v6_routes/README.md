# 岗位对照：同一批需求，传统人工流转 / 逐岗协作 / 化言动态协作三种走法

> 全部为模拟数据：`demo/routes.yaml` 的 A、B、C、C′、D 台词，共 6 个会话（D 由两位客户各提一次）。
> 复现：`uv run python scripts/demo_routes.py`（离线，几秒；同一配置重跑 `metrics.json` 逐字节一致）。公开演示配置 `--config config/app.demo.offline.yaml`（觉用 Jue-K）结果相同。
> 数字见 `metrics.json`，评测页第 05 块读它（`metrics.json` 与评测页中 `v5` 键即逐岗协作、`v6` 键即化言动态协作）。

## 怎么跑的

- 两遍都经界面同一个入口 `Api.call`：每次写操作推进业务时钟并 `tick`，与浏览器里点按钮一致。抽取为规则、Jev 为桩、助手不运行（离线）。
- **化言动态协作**：客户自助会话。研发在 C 选「不立项：已有产品适用（锦纶固色剂）」，产品经理签扩适用范围；C′ 是同类需求再来一次；D 两张同类单由产品经理签机会（附商业判断）合并，研发接一张。
- **逐岗协作**：同样的台词放进业务员陪同会话，每个岗位都配 Agent，但业务员签字升级、研发逐张接单；不使用不立项、扩适用范围、产品经理签机会。用的是同一套代码，不是历史录制。
- **传统**：按黑线流程定义计数（每个需求经过业务员记录、产品经理转述、研发接收、产品经理评价、业务员开单 5 个人工节点），**不是测量**。
- 脚本对化言动态协作的每条路径的关键结果做断言：A 无人工、无需求单；B 业务员看到完整原话与已推荐产品、没有重新采集；C 自动升级 → 不立项 → 扩范围、不经业务员；C′ 不产生需求单、研发 0 介入、产品经理获得引用记分；D 产品经理签机会、研发只收一张合并单；客户身份读内部评价、L2、L3 知识被拒。

## 计数口径

- 人工中转节点 = 事件日志里业务员、产品经理、研发本人的处理事件（升级签字、接单、不立项、扩范围、合并……；不含产品经理 Agent 与觉自动执行；合并时随之写下的整单改写不另计），业务员接手的会话（陪同，或商务诉求交给业务员）另计 1。
- 人工签字 = 人对觉提出的决策签字、接单或驳回；低风险 = 业务员签升级、研发审定已有产品复用。

## 限制

- 只有 6 个会话，是结构对比，不换算工时；研发因此多出多少中长期研发时间，需要企业试点验证。
- 「补问信息、纠正需求」一行两列不能直接比大小：动态协作下 C 在研发转译前就判为不立项，没走到回问那一步。
- 逐岗协作列是同一套代码按逐岗人工签字方式运行，觉、转译、知识库与化言动态协作列完全相同——这是一次消融对照。
