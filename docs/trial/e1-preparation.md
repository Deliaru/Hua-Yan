# E1队友准备包：采集、标注与接续说明

本包对应《化言评测集建设方案》的E1及“队友先做什么”。只交付可独立完成的格式、材料清单、访谈提纲和合成离线检查；不代办材料获取、专业确认或真人业务验收。用户审查本包通过后才进入E2。代码与材料以v10为基线，v11队友可接续使用。

## 1. 文件与一条命令

- 标注入口：`data/knowledge_v10/evaluations/E1/cases.yaml`，初始为空，不预填真实案例。
- 空白标注表：同目录`annotation-template.yaml`，填写完必备项后再移入cases.yaml。
- 合成示例：`tests/fixtures/e1/synthetic-cases.yaml`，也可放本地E1目录供查看；6条均非企业材料。4条dev、2条heldout只演练分区，不能作为未见泛化证据。
- 记录变更：本地E1目录`CHANGELOG.md`；原话、标注人与来源索引均不入库。

```powershell
uv run --locked --no-sync python scripts/backtest_cases.py --prepare --cases tests/fixtures/e1/synthetic-cases.yaml --seeds seeds --out data/knowledge_v10/validation/E1-preparation-20261103
```

`--prepare`只检查标注格式与词表，不启动业务、不读取正式qi_state、不调用抽取/觉/Jev或任何模型。生成summary.json、details.json、report.md、vocab_gaps.md。词表缺口单列，原词不改写；格式错误直接报错。检查完成不等于金标经专业核对或模型能力通过。原来的回测入口保留；新格式用显式`--prepare`进入准备检查，不冒充旧回测已消费新字段。

默认只检查dev；`--split heldout`仅供正式报告阶段显式使用。相同原始资料/业务案例的原话、改写、追问与纠正必须使用同一个source_group，并留在同一分区。按来源分组约1/3预留heldout；已经看过答案调试的例子归dev。不可为了凑比例拆同一来源，也不把合成预留叫盲测。

## 2. 标注字段

文件顶层为`cases: [...]`，一条样本对应一件需求的连续原话。必备项不能写“研发已确认”等未经发生的状态。

| 字段 | 填写方法 |
|---|---|
| id | 稳定的脱敏样本编号，不能重复 |
| source | 原始文件/口述记录编号及段落、条目或页码，能在本地追溯 |
| source_group | 同一原始资料或业务案例的分组编号；不能跨dev/heldout |
| kind | 真实=直接业务原始记录；还原=人员口述后整理；合成=开发者或模型编写 |
| labeled_by / labeled_at | 实际标注人及岗位、带时区时间；草稿标“待填写”，不得进入正式样本 |
| basis | 原话片段、页码或标注理由；晚到条件须写发生补问/补样/返工的依据 |
| split | dev或heldout，由来源分组固定 |
| phenomenon | 当前phenomena.yaml的编号或标签；未覆盖则保留原词记缺口 |
| first_words | 客户第一句话，逐字保留；脱敏替换处作明确标记 |
| turns | 按原顺序追加的客户发言，保留否定、纠正和“不知道”，不要改成总结 |
| final_conditions | 最终已明确的枚举条件，字段用slots.yaml编号；未知不填入此字典 |
| unknown | 客户明确说不知道的条件编号；尚未问到不能填入。温度统一用temperature_c |
| late_conditions | 只标当时没问到、后来导致补问/补样/返工的条件；同时给最终值或明确未知及依据，不由开发者猜测。首句已提供但后来改口的条件不计入 |
| temperature_c / temperature_quote | 可选摄氏闭区间[下限,上限]，单值两端相同；逐字引文。单次试验点不表示产品适用范围 |
| tags | 可选[否定, 纠正]，用于后续单独报告，不能靠模型自报成为专业标签 |

同一最终条件不能同时标为已知和未知。温度以外的连续量、单位和多阶段工艺保留在原话及basis中；不强行转为枚举或换算。无法按现结构表达时先记词表/表达缺口。现有词表为placeholder，准备检查未把它变成企业确认词表。

纠错与漏问分别标注：SYN-E1-003首句已有“气流缸”，后改为“溢流缸”，保留否定/纠正tags，late_conditions为空；SYN-E1-002首句未提供设备，合成背景设定因漏问设备导致补样，后续才补充“设备是溢流缸”，才将equipment标为late_conditions。两例都只是合成标注示范，不能替代真实返工依据。某条件仅仅在后续发言出现，还不足以认定它是晚到条件。

## 3. CRM/企微采集字段与脱敏说明

这是一份交接清单，不要求本轮去索取数据或联系人员。

| 原始字段 | 用途与保留要求 |
|---|---|
| 案例/会话编号、所属资料编号 | 关联source与source_group；同一件需求保持一个来源组 |
| 客户第一句原话、连续后续发言 | 构成first_words/turns；保留完整句子和顺序，不用“要柔软”等事后摘要替换 |
| 说话人角色、发言轮次与相对时间 | 识别谁说的、何时纠正；不能把研发判断写成客户原话 |
| 最终核实的材料、设备、染料、温度及其他条件 | 供后续专业标注；原始值、单位、区间同时保留 |
| 最初误述、明确未知、尚未询问的条件 | 分开记录；未填写不自动代表不限 |
| 补问、补样与返工的次数、触发条件和记录位置 | 支持late_conditions；不据次数反推因果 |
| 关联试样/报告/工单编号及原记录位置 | 供本地回查，链接保持受控 |
| 记录来源、整理人、核对人及时间 | 区分原始记录、口述还原和专业核对，不预填签字 |

脱敏时将姓名、客户企业、电话、邮箱、地址、合同与订单号替换为稳定代号，同一主体在同一案例中保持一致。完整映射表只放提供方受控位置，不随评测包或Git交付。产品型号如需替换，也使用稳定代号，并由资料方维护与知识状态的对应；不能自行改成一个现有产品。

面料/设备/现象、数值、单位、区间、否定、纠正和“不清楚”属于评测所需语义，不得为了脱敏删改。含配方或内部判断的记录保持内部密级，不能因转为样本或汇总而公开；正文进入data，Git仅保留本指南和合成夹具。

## 4. 补样/返工案例访谈提纲

以下是准备好的问题，不表示访谈已经发生。

1. 请选一件确实发生过补问、补样或返工的需求。它的业务/报告编号是什么？
2. 客户最开始具体说了哪句话？有原聊天记录吗；若只有回忆，明确记为口述还原。
3. 当时已经知道哪些材料、设备、工艺与数值？哪些是明确不知道，哪些根本没问？
4. 后来才知道的关键条件是什么？客户当时如何补充或纠正原话？
5. 有哪段记录能证明这个条件导致补问、补样或返工？若不能确定因果就标待核对。
6. 先后补问几轮、试样几轮，经过哪些岗位？保留各自依据，不把估计写成实测。
7. 如果第一轮问清这个条件，后续哪些步骤有可能减少？将此回答标为专业人员判断，不算已经发生的收益。
8. 谁能核对最终条件和晚到条件？哪些信息仍有矛盾或不能确定？记录实际核对结果，不代签。

## 5. 词表缺口与接续口径

缺口记录至少包含样本id、原词、原话位置、当前词表缺哪项、是否影响判断、后续核对意见。未覆盖的现象、条件和取值由脚本列入vocab_gaps.md，开发者不选一个“最接近”的值。词表改动需另按工程流程处理，随后重核已标样本并更新词表指纹。

本次检查只记录准备状态，真实/还原/合成及dev/heldout分母分别列出；不输出准确率、研发完整率、零容忍“0泄露/0丢失”等业务成绩。后续如需验证模型能力，必须实调当前项目配置的真实模型并记录实际型号、caller、计量和原始响应，不能用mock或规则冒充模型结果。

接续后的E1成绩需分别记录原始多轮发言结束时的抽取结果，以及追问后/进入研发时的完整率，避免模拟客户补充答案掩盖原抽取错误；业务员原样转述、一次性翻译和化言各有自己的输入范围。此处仅交接评测口径，没有执行这些对照。
