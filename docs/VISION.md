> 版本 v2｜2026-10-11｜内部设计文档，对外材料以 README 为准

## 1. 一句话

**别人做的是更懂化学的翻译器；化言做的是让需求在传递中不再失真的系统——会追问、可溯源、能度量、肯沉淀。**

**架构版：化言是一个没有写死工作流的多层 Agent 组织。「此刻什么需要被决定」由一个可训练的模型（觉）提出，Agent 起草，人签字；需求在客户、业务员、产品经理 Agent、研发之间逐层转译，每一句都能回到客户原话和知识的主人。**

口号：**传声不走样。**

### 1.1 给评委的七个升级点

常规做法是赛道的及格线；右边每一条都有可复现的证据，数字均来自模拟数据上的真实运行。

| 问题 | 常规做法 | 化言 | 证据 |
|---|---|---|---|
| **Agent 的任务从哪来** | 人下指令，或工作流写死「下一步交给谁」 | **任务来源本身是一个可训练的模型**：觉看着全过程，提出「谁此刻要决定什么」，Agent 被派单后起草，人签字，状态改变后觉再看。代码里没有一处写死流程推进 | 15 个决策模板驱动从追问到发布的全链路；模拟业务周里觉提出 50 个问题、人签 20 次，新品从发现到发布全部由此推进（`docs/reports/catalog_stats.md`）；hub 只按模板写定的主人派总线上的问题 |
| **需求怎么传** | 一次性把客户的话翻成技术语言 | **三层编译**：场景语言 → 产品需求语言 → 化学语言，每层只用本层能看的知识；每一条都带「source map」——客户原话 + 依据了谁的转化知识 | 真正到研发的需求，研发退回比例约 95% → **19.5%**，关键信息完整率 49% → **91%**（300 张卡中 41 张应升级的卡，`docs/reports/distortion/`） |
| **该问什么由谁决定** | 提示词里写「缺信息就追问」 | **问什么是学出来的**：Jue-K 从处置结果里学到「这单多半要到研发，研发要的信息现在就该问」 | 应升级的卡上追问 1.32 次 vs 规则 0.80 次，L1 能解决的卡上反而少问；专家先验偏离时，学习曲线显示模型用处置结果修正专家知识（`docs/reports/jue_k/`） |
| **机密怎么守** | 提示词里写「请勿泄露」 | **权限在数据层，不在提示词层**：Agent 根本拿不到它不该说的东西；再由觉盯住「换角度拼凑机密」的行为，两道防线 | L1 拿不到 L2/L3、产品经理 Agent 只见归属不见原文均有测试守住；拼凑机密的发现上 Jue-K 误报 0/4，常见规则告警 2/4（`docs/reports/week/`） |
| **知识怎么来** | 让专家上传文档，建知识库 | **知识是研发的资产**：被引用记分、试样成功记分，上层知识对下层只显示归属不显示原文，解密由本人审批；研发改过的转译自动提炼成可沉淀的知识，记在本人名下 | 升级 → 沉淀 → 发布 → 下一位客户在 L1 命中新品，引用与贡献记分全程由端到端测试守住（`test_wp_a3`） |
| **好不好怎么知道** | 演示几个挑好的例子 | **先造尺子**：把「传话游戏」变成可度量的失真，三组做法在同一批需求卡、同一个模拟客户上对照 | 同一种子重跑逐字节一致；不利的结果同样列出（只看全部卡时规则觉好于 Jue-K） |

| **怎么进企业** | 再造一个知识库、再推一个新 App | **不替换，嵌进去**：企业已有的 RAG 是化言的知识来源，化言在它之上加权限分层、转译、发现与归属；钉钉 / 飞书是工作面，觉的问题变成待办卡片，签字就是卡片上的按钮（第 11 节） | 全系统只有一个检索入口（`KnowledgeBase.search`），权限过滤、审计、记分都包在它外面，换成企业 RAG 只换内部排序；大模型全部走 OpenAI 兼容网关，换私有化模型只改配置；觉在 CPU 本地推理 |

再加一条贯穿全部的工程事实：**发现层零大模型调用**。觉全天开着也几乎不花钱，大模型只在「有问题要处理」时才被调用，成本随决策数量增长，而不是随数据量和时间增长（失真对照中觉调用 169 次、大模型 0 次）。

## 2. 我们要解决的问题

### 2.1 官方场景

赛道 AI＋功能化学的重点推荐场景是「AI 化学家」：专业需求理解、内外部知识检索与融合、解决方案辅助生成。官方列出的痛点包括：客户描述不专业、难以转成标准化技术需求；知识分散在非结构化资料里；外部知识容易覆盖内部专业知识；方案生成依赖专家经验。

**这是本赛道的及格线，大多数队伍都会做一个「更懂化学的翻译器」或「更准的 RAG」。** 化言不在检索准确率上硬拼，而是把问题重新定义。

### 2.2 一线业务需求交流中看到的真实情况

（基于功能化学一线业务需求交流）

- **传话游戏。** 客户和业务员都不懂化学，只会描述宏观现象；业务员转述一遍，需求就变形了，研发按变形的需求开发，返工。
- **三方互相保密，看到的东西不同。** 客户/业务员、产品经理、研发三方，各自能看到的内容不一样，要做分层。
- **诀窍是一层窗户纸。** 很多客户的问题，研发知道「调个 pH 就行」。不懂化学的客户只该拿到包装好的「传化产品＋工艺」，否则关键工艺知识可能外流；懂化学并明确要求的客户，可以解密给他。
- **知识在研发脑子里，不在库里。** 已有知识库能检索，但「场景语言 ↔ 化学语言」的转化只有研发掌握。
- **权责不对等。** 研发把自己的专业知识交出去，却难以获得明确归属与认可，所以不愿意贡献。要让贡献有回报，比如按被引用计积分。
- **已有语料可以续上。** 企业已有的场景语言转化语料，可以作为初始知识导入，在真实需求中继续校正。
- **系统都在，缺的是把它们串起来的东西。** 业务流转、实验记录、知识检索各有系统，缺的是一条把需求从市场串到研发、并标明谁决定什么的流程。
- **研发之间也需要互通有无。** 研发共享各自的「知识盲点」也应有补偿，比如积分或互换知识。
- **真正的问题在组织层面。** 多数方案只会面向客户、按以往经验输出方案；组织封闭、知识共享程度低、权责不对等，这几个问题更需要机制去回应。

### 2.3 重新定义

真正的问题不是「翻译不准」，而是一条会失真的需求传递链，有三个病根：

| 病根 | 表现 | 一次性翻译器能解决吗 |
|---|---|---|
| 信息不完整 | 客户没说面料、工艺，业务员也没问 | 不能，翻译再准也变不出没说的信息 |
| 转述失真 | 业务员按自己的理解改写 | 部分能 |
| 知识不愿共享 | 研发不贡献，转化知识沉淀不下来 | 不能 |

## 3. 三根支柱，和撑起它们的一层

### 3.0 架构层：觉是任务的来源

今天的 Agent 再能干，任务也要人或工作流先给出来：人下指令，或流程图写死「升级之后交给谁、确认之后做什么」。需求协同恰恰是流程图写不全的地方：什么时候该追问、哪张单该升级、哪几位客户其实在说同一件事、谁在换着角度套配方——这些「该有人决定」的时刻散落在对话、需求单、试样和检索记录里，没有人会替它们开工单。

化言把「任务从哪来」单独做成一层，交给觉：

- **觉看着全过程，只回答一件事：此刻有没有需要被决定的事，是什么决定、针对谁、多大把握。** 绝大多数时候它的回答是「没有」。
- **提出之后，由决策目录写定的主人准备、签字人签字。** 产品经理 Agent、业务员和研发的 Agent 都是被觉派单后才动手；签字改变状态，觉再看。
- **系统里没有工作流引擎。** 门面只放原子动作，hub 只派总线上的问题，「确认之后派给谁」不写在代码里。要多管一件事，就在决策目录里加一个模板：先用规则打分冷启动，有了处置数据再交给 Jue-K。
- **企业自己的流程图，可以直接写成决策目录。** 流程图上每一个「谁在什么条件下决定什么」，就是一个模板：前置条件、主人、签字人、打分方式。企业自己的流程管理，在化言里不需要另写一套流程，而是一份由企业设计、经人批准的决策目录；组织调整时改的是目录里的主人与签字人，不改代码，也不重训模型。

所以化言的三根支柱不是三个并列的功能，而是**同一层发现 + 不同的决定**：追问是觉在客户面前的决定，升级、接单、回问、沉淀、封存 / 放出、发布是需求链上的决定，机会汇聚、知识冲突、拼凑机密是没有人会来问、只能被发现的决定。

这是团队在赛前项目 JUE 中提出的「信息反射层」第一次进入多角色组织（见 6.1）：在物流里，它发现「该不该调车」；在化言里，它发现「该追问什么、谁在套话、哪条知识在打架」。同一套机制，换的是经验。

### 3.1 主动追问：从「翻译需求」到「问对问题」

对话进行中，觉持续判断「现在缺哪个关键信息、值不值得问」，并提示业务员**趁客户还在就问**。追问是结构化的：「信息槽位 × 需要追问的概率」，按信息价值排序，**问得少、问得准**。这是觉在决策目录里离客户最近的一类决策（觉的全貌见第 6 节），也是和「在提示词里加一句缺了就追问」的区别。

**问什么是学出来的，不是写出来的。** 业务员面前的价值是「问了推荐就对了」，研发面前的价值是「我要的信息在客户还在时就问到了」。觉在对话中不知道这张单最后会不会到研发，只能按概率权衡，这正是规则写不出、要从处置结果里学的东西。Jue-K 学到之后，在多半要升级的会话里多问研发必问的信息，在 L1 能解决的会话里少问，真正到研发的需求退回比例从约 95% 降到 19.5%。同一段对话，经过不同处置结果训练的觉，注意的东西不同——这是「经验塑造注意」的第一个实证。

### 3.2 失真可度量：一个别人拿不出来的评测台

用「需求卡＋模拟客户」构造可重复的测试：模拟客户只用宏观现象描述，被问到才透露细节。在同一批需求卡上对比三组方案——业务员转述（现状）、一次性翻译 Agent（大多数队伍的做法）、化言——比较关键信息完整率、失真率、追问次数、需要研发退回重问的比例。

展示时先看**单卡对照**：同一张需求卡、同一个模拟客户，左边一次性翻译，右边化言，看到研发会不会退回；再看整批需求卡上三组的统计。

**先造尺子，再说自己准。** 「传话游戏」过去只能靠抱怨，没有办法度量；评测台把它变成同种子可复现的数字，「研发需退回」就是研发返工的代理指标。这把尺子不依赖化言：任何一种需求理解方案都能放进来比。我们也把对自己不利的结果一起报出来（只看全部卡时规则觉好于 Jue-K、留出现象上 Jue-K 更差），可信的尺子比好看的分数更有用。

### 3.3 组织机制：只有内部人员才知道的规则

- **按客户画像决定披露**：保护客户黏性和定价，而不仅是保护研发；
- **沉淀有回报**：每条经研发确认的转化知识记在研发名下，被引用、试样成功都记积分；研发手里握着自己知识的「解密钥匙」，谁能看、看到哪一级，由研发审批。这把「权责对等」落到了机制上。

**把「窗户纸」变成可计量、可授权的资产。** 常规知识库默认知识是公共品，所以专家不愿意交；化言默认知识有主人：**上层知识对下层「可见归属、不可见内容」**——产品经理 Agent 知道这句转译依据了哪位研发的知识，却看不到原文；每一次引用都记在主人名下，就像版税；谁能看原文由主人本人审批，就像授权。研发交出知识，换来的是被记录、被引用、被回报，而不是被无偿取用。这是对「权责不对等」这个组织问题的机制解。

**每处理一次需求，系统就多会一件事。** 研发在需求单上改过的转译，由 Agent 提炼成知识、研发审定后入库；新品发布回 L1，下一位客户在业务员那里就能直接拿到推荐，不再升级。企业已有的场景语言转化语料，可以作为初始知识导入，从此在每一次真实需求中被研发校正和续写。

### 3.4 Agent 治理：借权不越权，无主无权

Agent 越能干，越需要回答「它凭什么能做这件事」。化言的回答写在代码里，而不是写在提示词里：

- **Agent 的权限是委托人权限的子集**：业务员的 Agent 看不到业务员看不到的东西，工具在代码里绑定委托人；
- **Agent 只起草，人才生效**：草稿写进领域对象，人在工作面上按按钮签字，按钮直接调用门面；助手没有确认工具；
- **没有委托人的 Agent 没有生效工具**：产品经理 Agent 不签字、不记积分，它的产出以研发接单为生效点；
- **产生决策需求 ≠ 获得执行权限**：觉提出问题，不替任何人做决定。

这四条都有测试守住（`test_wp_l`：产品经理 Agent 拿不到 L3 原文与封存项、没有生效工具，非委托人不能确认）。

### 3.5 数据层安全：结构隔离挡住 Agent，行为发现盯住人

企业不敢上 Agent，最常见的理由是「它会不会把不该说的说出去」。靠提示词约束大模型守密，挡不住提示注入，也挡不住模型自己发挥。化言的做法是**让 Agent 根本拿不到**：权限只在知识库、披露和门面里执行，传给 Jev 和 L1 Agent 的内容只含请求者权限内的知识，L1 的任何输出都不含 L2/L3 内容。

结构隔离挡得住 Agent，挡不住人一点点拼：一位业务员换着角度、短时间内反复问同一产品的原理和配方。这一类没有人会来报告，只能被发现——它是觉的「拼凑机密」决策。两道防线叠起来：**结构隔离管 Agent 能拿到什么，觉管人在做什么。**

## 4. 角色与三层

| 层 | 角色 | 能看到什么 | 在流程中做什么 |
|---|---|---|---|
| L1 | 客户、业务员（销售） | 产品推荐、用法、产品说明书 | 业务员直接面对客户：按觉的提示追问、拿到推荐；解决不了时签字升级；把样品交给客户并带回客户评价 |
| L2 | **产品经理 Agent** | 中间过程：场景需求卡、L2 转化对照、产品需求、研发需求单（所引研发知识只见归属，封存项不可见） | **第一步转译**：场景语言 → 产品需求语言（如「加一点保护剂，让染料均匀分散」）；把研发放出的对外要点反向包装成说明书。只起草，不签字 |
| L3 | 研发 | 全部，包括客户完整原话、L3 转化对照、机理、配方、实验记录、封存项 | **接单**（= 立项）或写理由退回；**第二步转译**：产品需求 → 化学语言；修改的转译沉淀为自己的知识；开发、试样；决定哪些窗户纸**封存**、哪些作为对外要点**放出**；审定发布；审批解密 |

中间过程只对产品经理 Agent 和研发开放。

**产品经理由 Agent 担任。** 产品经理的职责是「市场和研发的衔接」：把市场前端的需求转成产品开发需求交给研发。这个转述与衔接由产品经理 Agent 承担，它只用 L2 知识，产出是草稿，以研发接单为生效点。过去产品经理积累的转述经验仍记在本人名下，被 Agent 引用照常记分。对外说「Agent 承担产品经理的转述与衔接」，不说「取代产品经理」。

**人类角色以「工作面 + Agent 协作」工作。** 工作面是这个人的工作对象（业务员面前是客户，研发面前是需求单），人直接在上面干活，**与自己的 Agent 协作**：Agent 旁听、起草、批注，人也可以用自然语言让它查询、起草、修改草稿。**助手生产内容，人判断和签字**：唯一必须由人提供的是研发脑子里的窗户纸，助手负责结构化、泛化，研发审定。

## 5. 闭环

1. 客户和业务员对话，觉提示追问，需求被补全；
2. Jev 在 L1 知识里匹配产品，有把握就推荐，按客户画像决定披露版本；
3. 没有合适产品时，觉提出「是否转产品经理 Agent」，业务员签字升级。产品经理 Agent **先用 L2 知识查有没有现成产品**——L1 只按说明书匹配，它还能看历史案例，常能找到「说明书没写、但案例里用过」的方案；找到就交研发审定——产品经理 Agent 写给客户的那句说明出自 L2 案例，要由能看全部依据的研发审过才转给业务员，业务员再转述给客户；研发只审一句话、不立项，案例的归属人照样记分。查不到才进入**分层转译**：产品经理 Agent 把场景语言转成产品需求语言，研发**接单**（= 立项）或写理由退回；研发 Agent 再转成化学语言，研发修改、确认。每一层只用本层能看的知识，每一句都能回到客户原话，并标明依据了谁的转化知识。起草中发现客户没说的信息会改变转译时，觉提出**回问**，由业务员趁客户还在回头去问；
4. 研发开发、试样；业务员把样品交给客户，带回**客户评价**（市场端评价）；研发 Agent 起草「封存 / 放出」两栏，研发审定哪些窗户纸封存、哪些作为对外要点放出；
5. 产品经理 Agent 把对外要点反向包装成说明书，觉检查有无泄密，研发审定后**发布回 L1 知识库**，下一位客户在 L1 就能直接匹配；
6. 研发在需求单上修改过的转译，由 Agent 提炼成可沉淀的转化知识，研发审定后记在自己名下；知识被引用、试样成功、产品发布都记在归属人名下；
7. 觉在后台持续扫描：多个客户的同类未满足需求（机会汇聚）、知识互相矛盾（知识冲突）、有人在拼凑不该看的内容（泄露风险）。机会汇聚到点后，产品经理 Agent 读几位客户的原话，判断说的是不是同一件事、起草合并；研发签字合并后接单，即立项。

上面每一个「谁要决定什么」的时刻——追问、升级、现成产品复用、接单、回问、确认、沉淀、客户评价、封存 / 放出、发布——都由觉提出，交给主人（产品经理 Agent 或业务员、研发的 Agent）准备，签字人在工作面上签字；签字改变状态，觉再看下一步。**流程由觉提出的决策推动，不写死在系统里。**

**每走完一次升级，系统就多会一件事。** 这也是续上已有转化数据投入的方式：每处理一次真实需求，就顺带沉淀一条经研发确认的转化数据，已有的转化语料可以导入作为初始知识库。

## 6. 觉与 Jev

- **觉：全过程的决策点发现器。** 它看着整个过程——会话、需求单的各层条目与修改、回问、退回、签字、对外文本、试样与评价、检索行为——对**决策目录**里每一个「决策 × 对象」给出「此刻需要被决策」的概率，超过阈值就提出问题；绝大多数时候输出「没有」。决策目录分两类：**推进类**（流程往前走需要有人决定：追问、升级、现成产品复用、接单、回问、确认、沉淀、客户评价、封存 / 放出、发布）与**异常类**（出了需要处理的情况：转译失真、对外泄密、知识冲突、拼凑机密）。觉不回答问题、不调用大模型、不签字；每个决策由谁准备、谁签字，由目录写定。
- **Jev：问题提出来后，判断各个答案的可能性。** 有问题才调用；推荐哪个产品的概率同时是觉判断「是否升级」的信号。
- 最终拍板的是人。
- **角色 Agent 与产品经理 Agent。** 业务员和研发各有一个 Agent：被派到觉的决策时自己准备，把草稿写在工作面上对应的位置；人看、改，按按钮签字。Agent 借用委托人的权限，只能起草和提议，签字权在人手里——这让「权责对等」对 Agent 同样成立。产品经理 Agent 没有委托人，所以只起草、不签字、不记积分。
- **三个数据飞轮。** 知识飞轮：每一次升级和研发的每一次修改，沉淀为经研发确认的转化知识，新品回到 L1。判断飞轮：觉的每次判断与人的处置被记录，用来校准概率、调阈值、重训 Jue-K。**决策目录飞轮**：被忽略的问题说明提多了，人在没有被提问时自发做出的决定说明漏了；后期据此调整已有决策点、生成候选的新决策点，经人批准加入目录。本次把数据记全，自动改进与加入是后期能力。

**如实说明**：Jue-K 按 v5 语义重新训练，覆盖有样本的五类决策（追问、回问、机会汇聚、知识冲突、拼凑机密），每类与规则打分比较，胜出才用模型；推进类决策当前由规则打分，到点即提出，界面上标「规则」，不说成模型概率。回问若新模型不胜过规则，仍由规则前置条件驱动。

觉和 Jev 来自团队赛前项目 JUE。觉的骨架（问题模板 × 对象、打分、发布、问题总线）与业务无关，在 JUE 中用于物流场景；化言把它用在知识协同领域，训练版称为 **Jue-K**。

### 6.1 觉从哪来、要去哪

**JUE 的长期定义**：觉是一个可通过经验训练的**信息反射层**——从持续的外部信息中形成、筛选值得处理的事项，在没有人下达具体任务时，也能把值得进一步处理的内容交给高层 Agent 与人。它研究的不是「收到一道题以后怎样答好」，而是「还没有人出题时，什么值得被想」。Jev 回答已经提出的问题，觉负责提出问题；介绍时可以说「Agent 的发现层」「任务的来源层」。

**化言在这条路线上的位置**：

| JUE 的长期主张 | 在化言里第一次有了什么 |
|---|---|
| 替代 Agent 的「需求目标输入层」：具体任务不必都由人或规则先列出来 | 一个多角色组织里，Agent 的任务全部来自觉；产品经理 Agent 没有委托人，它在流程中的每一项工作都是觉派的 |
| 产生认知需求 ≠ 获得执行权限 | 落成可测的不变量：觉只提出，Agent 只起草，人才生效（3.4） |
| 共同机制可迁移，领域经验决定激活什么 | 同一套骨架从物流（调车、限流）搬到知识协同（追问、泄密、知识冲突），两边没有共同的业务语义；换的是决策目录和训练数据 |
| 经验塑造注意（「警察和普通人面对同一件事，联想不同」） | 追问标签加入「研发必问」后，Jue-K 在同样的对话里把注意分给下游研发需要的信息（3.1） |
| 发现「没有人会来问的问题」 | 机会汇聚、知识冲突、拼凑机密：没有人会开工单说「他在套配方」 |
| 决策类型自生长 | 决策目录飞轮的数据（被忽略率、人自发决策）已经全量记录；自动生成新决策点是下一步 |

**路线**：比赛中原型与 Jue-K 跑通、数据记全 → 上线**影子模式**（觉只提问、不动作，人照常工作，积累「状态、决策、处置、结果」，这类数据只能在运行中得到，是壁垒所在）→ 用真实处置数据重训和校准，扩充决策目录 → 同一发现层接入配方优化、缺料预警等场景。

## 7. 边界：不做什么、不能说什么

**不做：**
- 不接入真实钉钉、ELN、客户系统，只描述接入路径（第 11 节）；本次 Demo 是**架构与业务流程演示**，界面是工作面的示意，不是最终产品形态；
- 不重做企业已有的向量检索：Demo 的检索是关键词实现，只为演示权限分层与归属；
- 不做语音识别，对话以转写文本输入；
- 不做配方生成或配方优化；
- 不做完整的积分兑换、绩效体系，只做账本和视图；
- 不训练大模型。

**不能说：**
- 不说「已接入传化数据」：全部是模拟数据；
- 不说「零泄露」：结构性隔离挡得住前台 Agent，挡不住从大量结论反推原理，后者由泄露风险发现来缓解；
- 不说「真实业务已验证」：评测是在模拟客户和模拟业务周上的相对比较；
- 不把演示里的概率数字说成实测结果，除非它来自真实运行；规则打分的推进决策不说「概率」；
- 不说「觉已自动发现新的决策点」：本次只记录决策目录飞轮所需的数据；
- 不说「取代产品经理」，说「Agent 承担产品经理的转述与衔接」；
- 不点名评价其他团队或供应商的已有方案，只说「常规 RAG 在这个场景下的结构性局限」。

**大叙事的红线（v3 补）：**
- 「潜意识」「反射」只作比喻，不作主张；不说「通向自主意识」；
- 不说「首创」「业界第一」：主动 Agent、何时唤醒 Agent 等相邻研究存在，只说「我们把发现层单独做成可训练、可度量、可替换的一层」；
- 决策目录是**闭集**：不说「觉能发现任意问题」；
- 「跨领域迁移」指**机制与代码骨架的复用**，不是模型零样本迁移：Jue-K 是在化言数据上重新训练的；
- 第 11 节的接入是**路径与接口位置**，不说「已支持钉钉 / 飞书」「已对接企业 RAG」；能指给评委看的只有代码里的接缝（唯一检索入口、模型网关配置、总线与签字按钮）；
- 「没有工作流引擎」指流程推进不写在代码分支里；推进的规则写在决策目录（模板的前置条件、主人、签字人）里，这一点主动说明；
- 推进类决策是规则打分，只有五类有样本的决策由 Jue-K 打分，不说「全流程由模型驱动」；
- 不以「零大模型调用」作标题：它是发现层的成本事实，放在效率一栏；
- 七个升级点的每个数字都带上来源报告；说「研发退回从 95% 降到 19.5%」时同时说清是「模拟数据上、应升级的 41 张卡」。

## 8. 对外定位

**目标用户**：传化功能化学的业务员、研发，以及希望把专家知识沉淀为企业资产的管理层；产品经理的转述与衔接由产品经理 Agent 承担。

**对管理层的价值主张是双赢**：研发的知识贡献可度量、有回报，所以愿意持续贡献；公司因此获得可复用的知识资产，降低对个人经验的依赖，同时保护客户黏性和定价。

**30 秒介绍（演示版完成后使用）：**
> 客户说「洗几次就发硬」，业务员转述成「要更柔软」，研发做了柔软剂，方向错了——真正的问题是耐洗性。化言让需求在传递中不走样：对话中主动提示该追问什么，生成的需求单每一条都能回查客户原话，按身份分层披露知识，解决不了的需求由产品经理 Agent 和研发逐层转译，新产品再回流到一线；每一个该有人拍板的时刻，都由系统提出、由人签字。研发的每一条知识贡献都被记录和回报。

**10 秒版（架构）：**
> 别人让 Agent 更会回答；化言让「该处理什么」由一个可训练的模型提出。Agent 起草，人签字，需求在三层之间转译不走样，研发的知识有主人、有回报。

**按评审五项的落点：**

| 评审项 | 化言的主张 | 支撑 |
|---|---|---|
| 技术可行性与实现可信度 | 全链路可运行、可离线复现，降级处处标注 | 11 个测试守住关键不变量；离线主线与现场版；报告附复现命令 |
| 技术创新与效率提升 | 发现层（任务来源）单独成层、可训练；三层编译带 source map；发现层零大模型调用 | 1.1 节七个升级点；失真对照、Jue-K 胜负判定、业务周对照 |
| 业务价值与场景契合度 | 来自一线业务需求交流的三个病根：信息不完整、转述失真、知识不愿共享，各有机制对应 | 失真对照；研发退回比例；新品回流 L1 |
| 工程化潜力与规模扩展 | 新业务决策 = 加一个模板，规则冷启动、有数据换模型；发现成本随决策数增长而不是随数据量增长 | 决策目录 15 个模板；Jue-K 本地推理 |
| 企业落地可行性 | 不替换、嵌进去：企业 RAG 当知识来源，钉钉 / 飞书当工作面，ELN 回流试样，私有化模型换配置；影子模式上线；权限在数据层；续上已有的转化语料投入 | 第 11 节的接缝表；3.4、3.5 节；结构隔离测试 |

## 9. 未来方向（对外只讲到这里）

更多化学业务场景（配方优化、缺料预警等可以复用同一套发现层）、真实对话与实验数据接入、按企业组织结构配置的层级与审批流程。

**一套发现层，管住一家企业「该有人决定」的时刻。** 化言是这层能力在「市场—产品—研发」协同上的第一个落地：先影子模式积累真实处置数据，再用它重训觉、扩充决策目录，最后把同一层接到配方优化、缺料预警、设备切换等场景——每多接一个场景，加的是决策模板和训练数据，不是一条新的工作流。

后期方向（数据已在记录，机制未做）：

- **研发之间的盲点互换**：研发 A 的转译引用了研发 B 的知识，已经给 B 记分；下一步是研发之间按归属申请、本人审批的知识互换，让「补别人的盲点」也有回报；
- **按一致率放权**：每一次「Agent 起草 → 人修改 → 签字」都留了记录。某类决定上 Agent 的草稿长期被原样签字，就提请把它降为「Agent 处理、人事后抽查」；反之则收回。放权的提案由系统给出，批准权在管理层；
- **管理层视图**：知识贡献账本、各类决定的次数与处理时长、谁的知识被谁引用，帮助管理层看见专家知识在组织里怎么流动。

## 10. 评委追问

| 追问 | 回应 |
|---|---|
| 这不就是工作流 / BPM 加了个 LLM？ | 工作流把「下一步」写死在流程图里；化言的推进来自觉对全过程的判断，加一个推进点是加一个模板，不改代码。更关键的是，流程图里没有的事——几位客户在说同一件事、某条知识在试样中屡屡失败、有人在拼凑配方——也会被觉提出来 |
| 觉不就是规则告警？ | 觉输出的是要做的决定（是否追问面料、是否合并需求单），不是指标异常；五类有样本的决策由训练模型打分、概率经过校准；在困难负样本上，业务周里 Jue-K 误报 0/4，常见规则告警 2/4 |
| 为什么不让一个通用大模型每隔几分钟看一遍？ | 成本和稳定性：觉全天开着几乎不花钱，同样的输入给同样的判断，每次判断都记录下来可以复盘、可以重训；大模型只在有问题时出场 |
| 标签和客户都是你们自己模拟的 | 承认。我们的贡献是把「传话游戏」变成可度量的任务、给出评测台和口径，以及上线后用影子模式拿真实处置标签的路径；对自己不利的结果也一起列出 |
| 一次性翻译的对照组是不是太弱？ | 承认当前 G2 是规则实现。它输的主要不是翻译质量，而是客户在开场白里没说的面料、设备、工艺，翻译得再准也翻不出来——这是不追问的结构性局限，换更强的模型也补不上。（若补上真实大模型的 G2 列，在此替换为实测数字） |
| 研发真的愿意用吗？ | 研发最在意的是「交出去没有归属」；化言的回答是知识有主人：可见归属、不可见内容，引用记分，解密本人审批。是否足以改变行为需要上线验证，我们把它列为预期收益 |
| 权限靠提示词能守住吗？ | 不靠提示词。Agent 拿到的内容只含委托人权限内的知识，结构上就看不到；人拼凑机密的行为由觉发现 |
| 企业已经有很强的 RAG 了，你们的检索很简单 | 对，我们不和企业 RAG 比检索。RAG 解决「找得到」，化言解决「找到之后谁能看、怎么转成研发听得懂的话、依据了谁的知识、该不该有人决定」。企业 RAG 接在唯一的检索入口后面当知识来源，权限、审计、记分照常生效 |
| 员工要换一个新系统吗？ | 不换。业务流转本来就在钉钉 / 飞书上：对话用听记转写进来，觉的问题以待办卡片推给主人，签字就是卡片上的按钮，研发的需求单是一个可以打开的页面。当前 Demo 是架构与流程演示，工作面就是将来卡片和页面的内容 |
| 数据出不出企业？ | 大模型全部经过 OpenAI 兼容网关，换成企业私有化部署的模型只改配置；觉是本地小模型，CPU 推理；知识与账本都在企业内部 |

## 11. 落地形态：嵌进企业现有的系统，不另起炉灶

**定位：化言不替换企业已有的系统，而是把它们串成一条不走样的需求链。** 企业已经有向量化的知识库、钉钉上的业务流转、ELN 里的实验记录；缺的是「谁能看什么」「怎么从场景语言转到化学语言」「此刻该谁决定什么」「这条知识是谁的」。化言补的正是这一层。

| 企业已有 | 化言怎么接 | 当前 Demo 里的替身 | 代码里的接缝 |
|---|---|---|---|

**上线路径**：

1. **影子模式**：接上钉钉听记与企业 RAG，觉只提问不动作，问题只推给试点的一位业务员和一位研发；人照常工作，系统记录「觉提出了什么、人怎么处置、结果如何」；
2. **试点签字**：一个产品线、一个现象族上启用工作面签字与知识归属，研发审定的转译开始沉淀、记分；
3. **重训与扩目录**：用影子期的真实处置数据重训 Jue-K、校准阈值；按被忽略率和人自发决策调整决策目录；
4. **扩场景**：同一发现层接配方优化、缺料预警、设备切换等场景，加的是模板与训练数据。

**当前 Demo 的定位**：架构与业务流程演示。它证明的是分层权限、逐层转译、觉驱动推进、知识归属这几件事在一条完整链路上能跑通、可度量；企业系统的接入是上面的路径，不是已完成的功能。
