# 化言：愿景与定位

> 版本 v1｜2026-10-10｜内部设计文档，对外材料以 README 为准

## 1. 一句话

**别人做的是更懂化学的翻译器；化言做的是让需求在传递中不再失真的系统——会追问、可溯源、能度量、肯沉淀。**

口号：**传声不走样。**

## 2. 我们要解决的问题

### 2.1 官方场景

赛道 AI＋功能化学的重点推荐场景是「AI 化学家」：专业需求理解、内外部知识检索与融合、解决方案辅助生成。官方列出的痛点包括：客户描述不专业、难以转成标准化技术需求；知识分散在非结构化资料里；外部知识容易覆盖内部专业知识；方案生成依赖专家经验。

**这是本赛道的及格线，大多数队伍都会做一个「更懂化学的翻译器」或「更准的 RAG」。** 化言不在检索准确率上硬拼，而是把问题重新定义。

### 2.2 一线业务需求交流中看到的真实情况

（基于功能化学一线业务需求交流）

- **传话游戏。** 客户和业务员都不懂化学，只会描述宏观现象；业务员转述一遍，需求就变形了，研发按变形的需求开发，返工。
- **三方互相保密，看到的东西不同。** 客户/业务员、产品经理、研发三方，各自能看到的内容不一样，要做分层。
- **诀窍是一层窗户纸。** 很多客户的问题，研发知道「调个 pH 就行」。不懂化学的客户只该拿到包装好的「传化产品＋工艺」，否则关键工艺知识可能外流；懂化学并明确要求的客户，可以解密给他。
- **知识在研发脑子里，不在库里。** 已有知识库能检索，但「场景语言 ↔ 化学语言」的转化只有研发掌握。
- **权责不对等。** 研发把自己的专业知识交出去，却难以获得明确归属与认可，所以不愿意贡献。要让贡献有回报，比如按被引用计积分。
- **已有语料可以续上。** 企业已有的场景语言转化语料，可以作为初始知识导入，在真实需求中继续校正。

### 2.3 重新定义

真正的问题不是「翻译不准」，而是一条会失真的需求传递链，有三个病根：

| 病根 | 表现 | 一次性翻译器能解决吗 |
|---|---|---|
| 信息不完整 | 客户没说面料、工艺，业务员也没问 | 不能，翻译再准也变不出没说的信息 |
| 转述失真 | 业务员按自己的理解改写 | 部分能 |
| 知识不愿共享 | 研发不贡献，转化知识沉淀不下来 | 不能 |

## 3. 三根支柱

### 3.1 主动追问：从「翻译需求」到「问对问题」

对话进行中，觉持续判断「现在缺哪个关键信息、值不值得问」，并提示业务员**趁客户还在就问**。追问是结构化的：「信息槽位 × 需要追问的概率」，按信息价值排序，**问得少、问得准**。这是觉在本系统中的本职，也是和「在提示词里加一句缺了就追问」的区别。

### 3.2 失真可度量：一个别人拿不出来的评测台

用「需求卡＋模拟客户」构造可重复的测试：模拟客户只用宏观现象描述，被问到才透露细节。在同一批需求卡上对比三组方案——业务员转述（现状）、一次性翻译 Agent（大多数队伍的做法）、化言——比较关键信息完整率、失真率、追问次数、需要研发退回重问的比例。

### 3.3 组织机制：只有内部人员才知道的规则

- **按客户画像决定披露**：保护客户黏性和定价，而不仅是保护研发；
- **沉淀有回报**：每条经研发确认的转化知识记在研发名下，被引用、试样成功都记积分；研发手里握着自己知识的「解密钥匙」，谁能看、看到哪一级，由研发审批。这把「权责对等」落到了机制上。

## 4. 角色与三层

| 层 | 角色 | 能看到什么 | 在流程中做什么 |
|---|---|---|---|
| L1 | 客户、业务员（销售） | 产品推荐、用法、产品说明书 | 提出需求、回答追问、拿到推荐 |
| L2 | 产品经理 | 中间过程：转述记录、研发需求单 | 把场景需求转成产品需求，衔接市场和研发；写产品说明书 |
| L3 | 研发 | 全部，包括客户完整原话、配方、实验记录 | 开发配方、试样，审批解密 |

中间过程只对产品经理和研发开放。

## 5. 闭环

1. 客户和业务员对话，觉提示追问，需求被补全；
2. Jev 在 L1 知识里匹配产品，有把握就推荐，按客户画像决定披露版本；
3. 没有合适产品时升级给产品经理，产品经理转述成产品需求，再生成化学语言的研发需求单；
4. 研发开发、试样，市场端评价；
5. 产品经理写说明书，**发布回 L1 知识库**，下一位客户在 L1 就能直接匹配；
6. 每一组经确认的「场景语言 ↔ 化学语言」对照沉淀为知识，贡献记在研发名下；
7. 觉在后台持续扫描：多个客户的同类未满足需求（机会汇聚）、知识互相矛盾（知识冲突）、有人在拼凑不该看的内容（泄露风险）。

**每走完一次升级，系统就多会一件事。** 这也是续上已有转化数据投入的方式：每处理一次真实需求，就顺带沉淀一条经研发确认的转化数据，已有的转化语料可以导入作为初始知识库。

## 6. 觉与 Jev

- **觉：判断「现在是不是该提一个问题」，以及是什么问题。** 持续运行，绝大多数时候输出「没有」。
- **Jev：问题提出来后，判断各个答案的可能性。** 有问题才调用。
- 最终拍板的是人。

觉和 Jev 来自团队赛前项目 JUE。觉的骨架（问题模板 × 对象、打分、发布、问题总线）与业务无关，在 JUE 中用于物流场景；化言把它用在知识协同领域，训练版称为 **Jue-K**。

## 7. 边界：不做什么、不能说什么

**不做：**
- 不接入真实钉钉、ELN、客户系统，只描述接入路径；
- 不做语音识别，对话以转写文本输入；
- 不做配方生成或配方优化；
- 不做完整的积分兑换、绩效体系，只做账本和视图；
- 不训练大模型。

**不能说：**
- 不说「已接入传化数据」：全部是模拟数据；
- 不说「零泄露」：结构性隔离挡得住前台 Agent，挡不住从大量结论反推原理，后者由泄露风险发现来缓解；
- 不说「真实业务已验证」：评测是在模拟客户和模拟业务周上的相对比较；
- 不把演示里的概率数字说成实测结果，除非它来自真实运行；
- 不点名评价其他团队或供应商的已有方案，只说「常规 RAG 在这个场景下的结构性局限」。

## 8. 对外定位

**目标用户**：传化功能化学的业务员、产品经理、研发，以及希望把专家知识沉淀为企业资产的管理层。

**对管理层的价值主张是双赢**：研发的知识贡献可度量、有回报，所以愿意持续贡献；公司因此获得可复用的知识资产，降低对个人经验的依赖，同时保护客户黏性和定价。

**30 秒介绍（演示版完成后使用）：**
> 客户说「洗几次就发硬」，业务员转述成「要更柔软」，研发做了柔软剂，方向错了——真正的问题是耐洗性。化言让需求在传递中不走样：对话中主动提示该追问什么，生成的需求单每一条都能回查客户原话，按身份分层披露知识，解决不了的需求逐层升级，新产品再回流到一线。研发的每一条知识贡献都被记录和回报。

## 9. 未来方向（对外只讲到这里）

更多化学业务场景（配方优化、缺料预警等可以复用同一套发现层）、真实对话与实验数据接入、按企业组织结构配置的层级与审批流程。
