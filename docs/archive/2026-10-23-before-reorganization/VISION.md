# 化言：愿景与定位

> 内部设计文档，对外材料以 README 为准。
> 要点：化言管理的是**组织里的专业判断**：觉是**任务的来源**（3.0），契是**能力的来源**（3.0′），Agent 的自主任务从觉来，也接受人的明确委托；能力从契来，人负责判断和授予。流程由觉提出的决策推动；**四层是知识边界，不是审批节点**，需求按性质分流（第 4、5 节）；产品经理 Agent 在后台承担逐单转述，真人产品经理负责产品适用范围、产品机会与例外纠偏；低风险推进由觉自动执行，高影响动作由人签字；人以「工作面 + Agent 协作」工作，助手生产内容，人判断和签字。**叙事要大胆，数据和运行要真实：愿景、当前实现、证据同屏。** 每条主张都配上已经拿到的证据和下一步要拿的证据，愿景完整保留。

> **当前状态（2026-10-22，基线 `62192d6`）**：契已实现，授予、撤销、续跑都有运行证据；177 条官网公开目录已经起草接入，引文全部核对通过，词表与归属交真人审定。**V9 的目标：2026-11-08 决赛前，业务员、产品经理、研发、研发负责人在一个共享试用实例中，完成一次全链条真实业务试用**，把多角色演示升级为多人共享协作。研发负责人在同一权限体系里看进展与例外，四层知识边界保持不变。实施与验收见 [REPLAN-v9](workpackages/REPLAN-v9.md)，展示见 FINALS-SCOPE，本页讲愿景与证据。

## 1. 主张

> 在需要跨岗位使用专业判断的企业里，文档、培训和审批都有了，同一个问题却还是一遍遍回到专家本人。化言让专家确认过的判断在明确的适用范围和责任人之下持续发挥作用。
>
> 化言的目标是让专业判断成为组织能力：研发判断一次，在授权范围和适用条件内被多次使用，保留来源、责任和撤销权。哪里需要判断，由觉提出；判断交给谁用，由契授予。真实处置用于校准觉的注意力，经确认和授予的判断成为下一次可复用的能力。

口号：**问对的人，只问一次。** 需求上行那一段的副标题仍是「传声不走样」：化言关注需求在传递中如何保持原意——会追问、可溯源、能度量、肯沉淀。

**架构版：化言探索由业务对象、决策发现与受治理能力驱动的多层 Agent 组织。Agent 的自主任务从觉来，也接受人的明确委托；能力从契来，人负责判断和授予。「此刻什么需要被决定」由觉提出，规则与可训练模型按决策类型分工，Agent 起草，低风险推进自动执行，高影响决定由人签字；需求按性质分流——常规问题客户自助解决，商务诉求回到业务员，产品机会交产品经理判断，现有产品解决不了的才带着原话直达研发；跨层时逐层转译，每一句都能回到客户原话和知识的主人；研发的判断经契授予给需要它的那一层，可用、不可见、可撤销。**

**给企业的目标：让研发能力通过被授权的专业判断服务更多客户，把专家的注意力留给真正新的问题。**V9 的真实试用把这件事放到四个真实岗位手里检验。增收、降本、控险、资产、管理五类价值的全景见 `docs/PITCH.md` 第 9 节。

### 1.1 八条主张

1. **该判断的事主动出现。** 觉从会话、需求和事件中提出追问、回问、机会与例外；推进类由规则打分，发现类由训练模型打分，界面上分别标明。
2. **处置经验让注意力更准。** Jue-K 在模拟对照里把研发要的信息提前问到，研发退回比例从约 95% 降到 19.5%；V9 在真实业务里看它多问对、少打扰。
3. **需求可回查，失真可定位。** 每条需求条目都绑着客户原话和知识依据；失真对照把「传话游戏」变成了可度量的指标。
4. **能读与能用分开授权。** 研发可以只授予前台「追问某个条件」，机理留在研发手里；三态演示已经跑通。
5. **授权一变，后续行为立刻跟着变。** 撤销即停用；依据资料一改，依据它的结论自动挂起、交复核；状态跨重启保留。
6. **一次专业判断，在后续业务里反复用上。** 授权有效、条件符合时，下一单在一线解决；新条件和例外照样回到研发。
7. **企业现有知识直接接入，按需要形成能力。** 适配器接上已有知识来源，研发只签被需要的判断；来源、归属与适用范围在接入时核定。
8. **专业贡献有账可查。** 谁确认、谁批准、谁的判断被用上，都记在本人名下。

## 2. 我们要解决的问题

### 2.1 官方场景

赛道 AI＋功能化学的重点推荐场景是「AI 化学家」：专业需求理解、内外部知识检索与融合、解决方案辅助生成。官方列出的痛点包括：客户描述不专业、难以转成标准化技术需求；知识分散在非结构化资料里；外部知识容易覆盖内部专业知识；方案生成依赖专家经验。

这些能力是专业底座。化言在底座之上再走一步：让理解出来的需求进入组织判断，让判断经授权在后续业务里反复用上。

### 2.2 一线业务需求交流看到的真实情况

（基于功能化学一线业务需求交流归纳）

- **传话游戏。** 客户和业务员都不懂化学，只会描述宏观现象；业务员转述一遍，需求就变形了，研发按变形的需求开发，反复返工。
- **三方互相保密，看到的东西不同。** 客户/业务员、产品经理、研发三方，各自能看到的内容不一样，要做分层。
- **诀窍是一层窗户纸。** 很多客户的问题，研发知道「调个 pH 就行」。不懂化学的客户拿到的是产品＋工艺方案，机理与配方受控，以保护产品竞争力；懂化学并明确要求的客户，可以解密给他。
- **知识在研发脑子里，不在库里。** 常规知识库能检索，但数据杂乱、不标准，而「场景语言 ↔ 化学语言」的转化只有研发掌握。
- **权责不对等。** 知识贡献缺少归属与回报，专家缺乏把经验交给组织的动力。要让贡献有回报，比如按被引用计积分。
- **系统都在，缺的是把它们串起来的东西。** 业务流转在协作平台上，对话可以转写；实验在电子实验记录（ELN）里，报告在知识库里；缺的是一套贯穿这些系统、按需求推进的协作流程。
- **研发之间也需要互通有无。** 研发共享各自的「知识盲点」也应有补偿，比如积分或互换知识。
- **真正的问题在组织层面。** 多数方案只面向客户、按以往经验输出方案；组织封闭、知识共享程度低、权责不对等，才是更深层的问题。

### 2.3 重新定义

真正的问题不是「翻译不准」，而是组织里的专业判断流转不起来：该问的没问，问了传歪，判断了用不上。三个病根：

| 病根 | 表现 | 一次性翻译器能解决吗 | 化言的机制 |
|---|---|---|---|
| 信息不完整 | 客户没说面料、工艺，业务员也没问 | 不能，翻译再准也变不出没说的信息 | 觉：趁客户还在就问 |
| 转述失真 | 业务员按自己的理解改写 | 部分能 | 三层转译：每一句回到客户原话 |
| 判断用不上 | 研发知道「调个 pH 就行」，这句话走不到一线：说了怕泄密，交出去也没回报 | 不能 | 契：可授权、可复用、可撤销；被使用就记功 |

例子：客户说「洗几次就发硬」，业务员转述成「要更柔软」，研发做了柔软剂，方向错了，真正的问题是耐洗性。这是第二个病根；第一个和第三个病根见 2.2 的「传话游戏」与「窗户纸」。

第三个病根过去叫「知识不愿共享」。它其实有两个原因：没有回报，和不安全。积分只解决第一个，契解决第二个。

## 3. 三根支柱，和撑起它们的两层

### 3.0 架构层：觉是任务的来源

今天的 Agent 再能干，任务也要人或工作流先给出来：人下指令，或流程图写死「升级之后交给谁、确认之后做什么」。需求协同恰恰是流程图写不全的地方：什么时候该追问、哪张单该升级、哪几位客户其实在说同一件事、谁在换着角度套配方——这些「该有人决定」的时刻散落在对话、需求单、试样和检索记录里，没有人会替它们开工单。

化言把「任务从哪来」单独做成一层，交给觉：

- **觉看着全过程，只回答一件事：此刻有没有需要被决定的事，是什么决定、针对谁、多大把握。** 绝大多数时候它的回答是「没有」。
- **提出之后，由决策目录写定的主人准备、签字人签字。** 产品经理 Agent、业务员和研发的 Agent 都是被觉派单后才动手；签字改变状态，觉再看。模板写明 `auto_action` 的低风险推进（自动升级、交业务员）由觉直接执行并留痕，不再让人逐个签字。
- **发现与执行各司其职。** 门面提供原子动作，hub 根据总线派单，流程推进规则写进受治理的目录；觉专心判断需求的形成与筛选，契和人负责授权。新增决策类型先用规则冷启动，有了处置数据再换学习评分。
- **企业自己的流程图，可以直接写成决策目录。** 流程图上每一个「谁在什么条件下决定什么」，就是一个模板：前置条件、主人、签字人、打分方式。已有对象和动作范围内的责任调整，改目录即可生效；新的业务对象和动作，加一个门面原子方法和一个模板。

所以化言的三根支柱是**同一层发现 + 不同的决定**：追问是觉在客户面前的决定，升级、交业务员、接单、扩展适用范围、回问、沉淀、封存 / 放出、发布是需求链上的决定，机会汇聚、知识冲突、拼凑机密是没有人会来问、只能被发现的决定。

这是团队在赛前项目 JUE 中提出的「信息反射层」第一次进入多角色组织（见 6.1）：在物流里，它发现「该不该调车」；在化言里，它发现「该追问什么、谁在套话、哪条知识在打架」。发现层方法整套复用，换的是领域对象、目录、特征和训练数据。

### 3.0′ 能力层：契是能力的来源

觉回答「此刻该谁决定什么」；决定做完之后，研发的判断怎样回到需要它的地方，是另一个问题。V6 里研发的判断有六个零散的出口：放出对外要点、复用审定、扩适用范围、解密、沉淀转化知识、新品发布，各有各的规则。权限系统管读取和操作，知识管理管审核与版本；契再往前一步，把专业判断、允许的使用形式和适用条件一起建模，授权直接改变业务行为。

契把这件事做成一层：

- **依据 → 结论 → 能力。** 企业资料里的原文片段是依据；专家确认过的专业判断是结论；把一条结论授权给某一层使用，是一条能力。结论按密级控制谁能读，能力按授予控制谁能用。**能读和能用从此分开：研发的知识不给你看，但可以授权给你用，授权还能收回。**
- **能力是引擎唯一执行的单元。** 每一次正式适用判断都必须落在某个已授权的完整情境内，条件没问全时只是「可能适用」，不给确定推荐；跨层专业输出只能使用相应层级已授权的能力，由能力渲染，Agent 不能自己写一句再声称被授予；视图按「谁」计算，是引擎读知识的唯一路径，撤销一条能力，所有路径上的行为一起停；契的有效状态跨重启保留；依据带指纹，资料一改就能发现。
- **降密只有一条规则：由能读原级别的归属人逐条签。** 研发的判断由研发签，会话里来的信息由业务员签；定级按来源决定，模型和 Jev 都不参与。
- **签字跟着使用需要走。** 公开资料直接可用，产品经理和研发核定候选结论、归属与适用范围；同层研发访问他人的受控原文，由归属人授予。跨层使用由觉提出需要、归属人判断授予。适配器直接复用企业知识来源，来源与访问范围在接入时核定。

所以化言是**两层 + 三根支柱**：Agent 的自主任务从觉来，也接受人的明确委托；能力从契来；追问、转译和组织机制，是在这两层之上流转的决定。两层研究的是不同的问题：觉研究决策需求怎么产生，此刻为什么需要人判断；契研究专业能力怎么形成和传播，一个人的判断怎样在保留边界和责任的前提下，变成别人能持续使用的能力。契的完整设计见《契：化言的知识能力层》v3.3（定型版）；当前状态：已在模拟数据上实现，对应 1.2 里主张 4 到 8 的证据。

### 3.1 主动追问：从「翻译需求」到「问对问题」

对话进行中，觉持续判断「现在缺哪个关键信息、值不值得问」，**趁客户还在就问**：客户自助时直接向客户追问，业务员陪同时提示业务员追问。追问是结构化的：「信息槽位 × 需要追问的概率」，按信息价值排序，**问得少、问得准**。这是觉在决策目录里离客户最近的一类决策（觉的全貌见第 6 节），也是和「在提示词里加一句缺了就追问」的区别。

**哪些候选问题值得提出，由处置结果训练评分。** 前台的价值是「问了推荐就对了」，研发面前的价值是「我要的信息在客户还在时就问到了」。觉在对话中要预判这张单最后会不会到研发，按概率权衡——这正是学习评分胜过固定规则的地方。Jue-K 学到之后，在多半要升级的会话里多问研发必问的信息，在 L1 能解决的会话里少问，在 300 张模拟卡中应升级的 41 张上，按信息缺失定义的退回比例从约 95% 降到 19.5%。同一段对话，经过不同处置结果训练的觉，注意的东西不同——这是「经验塑造注意」的第一个实证。

### 3.2 失真可度量：可复现的机制评测

用「需求卡＋模拟客户」构造可重复的测试：模拟客户只用宏观现象描述，被问到才透露细节。在同一批需求卡上对比三组方案——假设噪声下的业务员转述、规则实现的一次性翻译、化言——比较关键信息完整率、失真率、追问次数、需要研发退回重问的比例。

展示时先看**单卡对照**：同一张需求卡、同一个模拟客户，左边一次性翻译，右边化言，看到研发会不会退回；再看整批需求卡上三组的统计。

**先造尺子，再说自己准。** 评测台把需求失真变成同种子可复现的指标，「研发需退回」就是研发返工的代理指标。这把尺子是公共的：任何一种需求理解方案都能放进来比。对自己不利的结果我们也一起公开（只看全部卡时规则觉好于 Jue-K、留出现象上 Jue-K 更差）——可信的尺子比好看的分数更有说服力。

### 3.3 组织机制：来自一线交流的责任与贡献需求

- **按客户画像决定披露**：既保护研发，也保护客户黏性和定价；
- **沉淀有回报**：每条经研发确认的转化知识记在研发名下，被引用、被使用、试样成功都记积分；研发手里握着自己知识的「解密钥匙」，谁能看、看到哪一级，由研发审批。这把「权责对等」落到了机制上。

**把「窗户纸」变成可计量、可授权的资产。** 化言把归属、授权与使用记账连成一体，专业贡献和使用责任都有账可查：**上层知识对下层「可见归属、不可见内容」**——产品经理 Agent 知道这句转译依据了哪位研发的知识，却看不到原文；每一次引用都记在主人名下，就像版税；谁能看原文由主人本人审批，就像授权。研发贡献知识，换来的是被记录、被引用、被回报。这是「权责不对等」这个组织问题的机制解。契把「授权」从解密扩展到使用：研发可以只把一条判断授予给前台用，而不交出原文；判断在哪一层被用上、被用了多少次，都记在研发名下。

**每一次经确认的处理结果，都让后续业务多一项可用能力。** 研发在需求单上改过的转译，由 Agent 提炼成知识、研发审定后入库；新品发布回前台，下一位客户在自助入口或业务员那里就能直接拿到推荐；研发判定一次「已有产品适用」，产品经理把它扩成产品适用范围，同类需求以后在自助阶段就解决。企业已有的场景语言转化语料，可以作为初始知识导入，从此在每一次真实需求中被研发校正和续写。

### 3.4 Agent 治理：借权不越权，无主无权

Agent 越能干，越需要回答「它凭什么能做这件事」。化言的回答写在代码里：

- **Agent 的权限是委托人权限的子集**：业务员的 Agent 看不到业务员看不到的东西，工具在代码里绑定委托人；
- **Agent 只起草，人才生效**：草稿写进领域对象，人在工作面上按按钮签字，按钮直接调用门面；助手没有确认工具；
- **没有委托人的 Agent 没有生效工具**：产品经理 Agent 不签字、不记积分，它的产出以研发接单为生效点；
- **产生决策需求 ≠ 获得执行权限**：觉提出问题，不替任何人做决定；觉自动执行只限模板写明的低风险推进（自动升级、交业务员），由门面内部入口执行、不经 HTTP 暴露，立项、技术确认、封存、发布、解密必须人签。

这四条都有测试守住（`test_wp_l`：产品经理 Agent 拿不到 L3 原文与封存项、没有生效工具，非委托人不能确认）。

### 3.5 数据层安全：结构隔离挡住 Agent，行为发现盯住人

企业不敢上 Agent，最常见的理由是「它会不会把不该说的说出去」。提示词守密挡不住提示注入，化言的做法是**让 Agent 根本拿不到**：权限只在知识库、披露和门面里执行，传给 Jev 和 L1 Agent 的内容只含请求者权限内的知识，L0、L1 的任何输出都不含 L2/L3 内容。有了契之后，研发可以把判断授予给前台使用，前台得到的是被授予的行为（一条追问、一个推荐、一句允许说的话），L2/L3 的内容始终留在上层。

结构隔离管住 Agent；人一点点拼凑，交给觉：一位业务员换着角度、短时间内反复打听同一产品的原理和配方，这种事只能被发现——它是觉的「拼凑机密」决策。两道防线叠起来：**结构隔离管 Agent 能拿到什么，觉管人在做什么。**

## 4. 角色与四层

**四层是知识边界。** 同一份需求可以在 L0 当场解决、带着已有信息交给业务员，或由产品经理 Agent 后台转译后直达研发；是否要人签字取决于动作的影响，不取决于层级。

| 层 | 角色 | 能看到什么 | 在流程中做什么 |
|---|---|---|---|
| L0 | 客户（下游印染企业等） | 公开的产品说明书、用法、脱敏公开案例；只看自己的会话 | 在公开入口自助描述问题、回答觉的追问、拿到可公开的推荐；需要报价、采购时点「我要报价」，由觉交给业务员 |
| L1 | 业务员（销售） | L0 内容＋内部评价报告 | 处理带着原话与已推荐产品过来的商务事项（报价、采购、客户关系）；陪同会话中按觉的提示追问、签字升级；把样品交给客户并带回客户评价 |
| L2 | **产品经理 Agent ＋ 真人产品经理** | 中间过程：场景需求卡、L2 转化对照、产品需求、研发需求单（所引研发知识只见归属，封存项不可见） | 产品经理 Agent 在后台做**第一步转译**：场景语言 → 产品需求语言（如「加一点保护剂，让染料均匀分散」），把研发放出的对外要点反向包装成说明书，只起草、不签字；真人产品经理**扩展产品适用范围**、**判断产品机会**（签字附商业判断）、**纠正被研发退回的转译** |
| L3 | 研发 | 本人及已授权的客户原话、L3 转化对照、机理、配方、实验记录与封存项；同层他人原文经归属人授予后可读 | 看开工门槛后**接单**（= 立项）、**不立项**（可指定「已有产品适用」）或写理由退回；**第二步转译**：产品需求 → 化学语言；修改的转译沉淀为自己的知识；开发、试样；决定哪些窗户纸**封存**、哪些作为对外要点**放出**；审定发布；审批解密 |

中间过程按参与关系与授权向产品经理（Agent 与真人）、研发开放。研发负责人使用同一权限体系中的管理视图，核查进展、重复判断、能力使用和需要管理介入的例外，只在例外处出手。

**产品经理回到产品本职，Agent 接过逐单转述。** 产品经理是「市场和研发的衔接」。逐单的转述与衔接由产品经理 Agent 在后台承担：它只用 L2 知识，产出是草稿，以研发接单为生效点。真人产品经理专注「产品」与「例外」两个层面：研发每判定一次「已有产品适用，只是超出标注范围」，产品经理把它签成产品适用范围，同类需求以后在客户自助阶段就命中；多位客户的同类需求由产品经理附上商业判断汇成一个课题，立项 = 产品经理的商业判断 + 研发的技术判断；研发退回的单由产品经理修正产品需求，修正可沉淀为本人名下的知识。产品经理的修订、适用范围扩展和过去积累的转述经验都记在本人名下，被 Agent 引用照常记分。

**人类角色以「工作面 + Agent 协作」工作。** 工作面是这个人的工作对象（客户面前是自己的问题，业务员面前是客户与商务事项，产品经理面前是适用范围、产品机会与待纠偏的单，研发面前是需求单），人直接在上面干活；业务员和研发**与自己的 Agent 协作**：Agent 旁听、起草、批注，人也可以用自然语言让它查询、起草、修改草稿。**助手生产内容，人判断和签字**：唯一必须由人提供的是研发脑子里的窗户纸，助手负责结构化、泛化，研发审定。

## 5. 闭环与分流

**先分流。** 需求按性质走不同的路，人只在有判断价值的地方出现：

| 路径 | 发生什么 | 谁承担判断 |
|---|---|---|
| A · 自助 | 客户只说现象，觉追问必要条件，按公开知识当场推荐 | 无需专业人员 |
| B · 商务归位 | 客户拿到推荐后要报价，觉把会话连同原话与推荐交给业务员 | 业务员（商务、价格、客户关系） |
| C · 直达研发 | 现有产品都不合适，觉自动升级，产品经理 Agent 后台转译，研发收到带原话和开工门槛的单 | 研发（接单、不立项或退回） |
| C′ · 判断复用 | 研发判定已有产品适用，产品经理签字扩展适用范围，下一位同类客户在自助阶段直接命中 | 研发判技术适用，产品经理管产品边界 |
| D · 机会汇聚 | 觉发现多位客户的同类未满足需求，产品经理附商业判断汇成一个课题，研发只接一张合并单 | 产品经理对机会负责，研发对技术负责 |

**再走完专业闭环。** 进入研发的需求，从追问到新品回流是完整的一条链：

1. 客户自助描述（或业务员陪同对话），觉追问，需求被补全；
2. Jev 在请求者可见的知识里匹配产品，有把握就推荐，按客户画像决定披露版本；
3. 没有合适产品时升级：自助会话由觉自动升级，陪同会话由觉提出「是否转产品经理 Agent」、业务员签字。产品经理 Agent **先用 L2 知识查有没有现成产品**——前台只按说明书匹配，它还能看历史案例，常能找到「说明书没写、但案例里用过」的方案；找到就交研发审定——产品经理 Agent 写给客户的那句说明出自 L2 案例，要由能看全部依据的研发审过才回到客户；研发只审一句话、不立项，案例的归属人照样记分，产品经理随后可把它扩成产品适用范围。查不到才进入**分层转译**：产品经理 Agent 把场景语言转成产品需求语言，研发看开工门槛后**接单**（= 立项）、不立项或写理由退回（退回的单由产品经理纠偏）；研发 Agent 再转成化学语言，研发修改、确认。每一层只用本层能看的知识，每一句都能回到客户原话，并标明依据了谁的转化知识。起草中发现客户没说的信息会改变转译时，觉提出**回问**，趁客户还在回头去问；
4. 研发开发、试样；业务员把样品交给客户，带回**客户评价**（市场端评价）；研发 Agent 起草「封存 / 放出」两栏，研发审定哪些窗户纸封存、哪些作为对外要点放出；
5. 产品经理 Agent 把对外要点反向包装成说明书，觉检查有无泄密，研发审定后**发布回前台知识库**，下一位客户在自助入口就能直接匹配；
6. 研发在需求单上修改过的转译，由 Agent 提炼成可沉淀的转化知识，研发审定后记在自己名下；产品经理的修正与适用范围扩展记在产品经理名下；知识被引用、试样成功、产品发布都记在归属人名下；
7. 觉在后台持续扫描：多个客户的同类未满足需求（机会汇聚）、知识互相矛盾（知识冲突）、有人在拼凑不该看的内容（泄露风险）。机会汇聚到点后，产品经理 Agent 读几位客户的原话，判断说的是不是同一件事、起草合并；产品经理签字合并并写商业判断，研发接单即立项。

上面每一个「谁要决定什么」的时刻——追问、升级、交业务员、现成产品复用、接单、扩展适用范围、机会汇聚、回问、确认、沉淀、客户评价、封存 / 放出、发布——都由觉提出，交给主人（产品经理 Agent 或业务员、研发的 Agent）准备，签字人在工作面上签字；低风险推进（自动升级、交业务员）由觉直接执行并留痕；签字或自动执行改变状态，觉再看下一步。**流程由决策目录、觉提出的事项、授权动作与人的判断共同推进，每份需求走最短的那条路。**

**专业判断经确认、审定和授予后，直接改变下一次业务。** 沉淀只收经研发审定的有效判断，知识库越用越干净。企业已有的转化语料可作为初始知识，经真实需求继续修订。

## 6. 觉与 Jev

- **觉：全过程的决策点发现器。** 它看着整个过程——会话、需求单的各层条目与修改、回问、退回、签字、对外文本、试样与评价、检索行为——对**决策目录**里每一个「决策 × 对象」给出「此刻需要被决策」的概率，超过阈值就提出问题；绝大多数时候输出「没有」。决策目录分两类：**推进类**（流程往前走需要有人决定：追问、升级、交业务员、现成产品复用、接单、扩展适用范围、机会汇聚、回问、确认、沉淀、客户评价、封存 / 放出、发布；其中自动升级、交业务员为低风险推进，由觉自动执行）与**异常类**（出了需要处理的情况：转译失真、对外泄密、知识冲突、拼凑机密）。按性质，目录里的决策又分两种：**流程推进与规则检查是确定性的**——状态满足就提出，相当于把流程写成数据，流程可改、可审计；**发现是觉的本职**——追问、回问、机会汇聚、知识冲突、泄露风险、授予请求，看的是跨时间、跨对象的模式，单看当前状态看不出，提早了是打扰、提晚了有代价，觉的打分与学习都用在这里。觉不回答问题、不调用大模型、不签字；每个决策由谁准备、谁签字，由目录写定。
- **Jev：问题提出来后，判断各个答案的可能性。** 有问题才调用；推荐哪个产品的概率同时是觉判断「是否升级」的信号。
- 最终拍板的是人。
- **角色 Agent 与产品经理 Agent。** 业务员和研发各有一个 Agent：被派到觉的决策时自己准备，把草稿写在工作面上对应的位置；人看、改，按按钮签字。Agent 借用委托人的权限，只能起草和提议，签字权在人手里——这让「权责对等」对 Agent 同样成立。产品经理 Agent 没有委托人，所以只起草、不签字、不记积分；需要签字的产品判断（适用范围、产品机会、纠偏）由真人产品经理在工作面上完成。
- **三个数据飞轮。** 知识飞轮：每一次升级和研发的每一次修改，沉淀为经研发确认的转化知识，新品回到前台；研发每一次「已有产品适用」的判断，经产品经理变成产品适用范围。判断飞轮：觉的每次判断与人的处置被记录，用来校准概率、调阈值、重训 Jue-K。**决策目录飞轮**：被忽略的问题说明提多了，人在没有被提问时自发做出的决定说明漏了；后期据此调整已有决策点、生成候选的新决策点，经人批准加入目录。这份数据现在已经全量记录。三个飞轮合起来就是觉的自进化，见 6.2。

**模型与规则的分工**：Jue-K 覆盖有样本的五类发现（追问、回问、机会汇聚、知识冲突、拼凑机密），每类与规则打分同台比较，胜出就换上模型；推进类决策（自动升级、交业务员、扩展适用范围等）由规则打分、到点即提出，界面上标「规则」。谁打的分，界面上一眼可见。

觉和 Jev 来自团队赛前项目 JUE，**Jev 与 Jue（觉）各管一段**：Jev 评价已提出问题的候选答案，OneJev 是可选外部接入；觉负责形成、维持、筛选和提交值得处理的事项。觉的骨架（问题模板 × 对象、打分、发布、问题总线）与业务无关，在 JUE 中用于物流场景；化言把它用在知识协同领域，训练版称为 **Jue-K**。

### 6.1 觉从哪来、要去哪

**JUE 的长期定义**：觉是一个可通过经验训练的**信息反射层**——从持续的外部信息中形成候选事项、维持尚待处理的状态、筛选值得投入注意的内容，再提交给恰当的处理者，在没有人下达具体任务时，也能把值得进一步处理的内容交给高层 Agent 与人。它研究的是「还没有人出题时，什么值得被想」。Jev 回答已经提出的问题，觉负责提出问题；介绍时可以说「Agent 的发现层」「任务的来源层」。

**化言在这条路线上的位置**：

| JUE 的长期主张 | 化言当前的实现与验证位置 |
|---|---|
| 替代 Agent 的「需求目标输入层」：具体任务由发现层提出 | 业务待办由觉提出，人也可以随时委托自己的 Agent；产品经理 Agent 根据总线事项准备材料；发现范围由受治理的决策目录界定 |
| 产生认知需求与获得执行权限分开 | 落成可测的不变量：觉只提出，Agent 只起草，人才生效（3.4） |
| 共同机制可迁移，领域经验决定激活什么 | 同一套骨架从物流（调车、限流）搬到知识协同（追问、泄密、知识冲突），两个领域的业务语义完全不同，换的只是决策目录和训练数据 |
| 经验塑造注意（「警察和普通人面对同一件事，联想不同」） | 追问标签加入「研发必问」后，Jue-K 在同样的对话里把注意分给下游研发需要的信息（3.1） |
| 发现「没有人会来问的问题」 | 机会汇聚、知识冲突、拼凑机密：「他在套配方」这种事，只有发现层能提出来 |
| 决策类型自生长 | 决策目录飞轮的数据（被忽略率、人自发决策）已经全量记录；自动生成新决策点是下一步 |

**路线**：比赛中原型与 Jue-K 跑通、数据记全 → 上线**影子模式**（觉只提问、不动作，人照常工作，积累「状态、决策、处置、结果」，这类数据只能在运行中得到，是壁垒所在）→ 用真实处置数据重训和校准，扩充决策目录 → 同一发现层接入配方优化、缺料预警等场景。

### 6.2 觉的自进化：让判断可复用，让注意力可校准

觉随经验改进，衡量它要同时看三件事：**有效的判断复用、该提出的事项提出了没有、对人的打扰有多少**。自进化分三层，每层的机制与证据如下：

| 层 | 发生什么 | 燃料 | 现状 |
|---|---|---|---|
| 能力进化 | 觉发现某类判断在一线反复被需要：分层召回反复记到「本层无能力」，研发为同一现象反复回问同一个槽位，试样反复因同一个条件没问到而失败。觉提出授予请求（`qi_grant`，主人与签字人是研发），研发签字授予后，从下一位客户起一线自己解决 | 决策记录，加上契的授予与使用记录 | 已实现：`qi_grant` 由回问次数、本层无能力记录、试样失败三路提出。回问这一路在主演示中完整跑通（`docs/reports/qi_demo/demo.md`）；「本层答不了」一路在 Q8 改为答不了一次即提出，探针验证通过；试样失败一路已跑通单张单的返工回路（`trial_rework`），由它触发授予是下一步演示 |
| 校准进化 | 处置和真实结果流回来，Jue-K 在运行中按窗口重训、换上新模型，提得更准、更少打扰人 | 决策记录里人的处置和真实结果 | 已实现，模拟数据：运行中按窗口重训，世界偏离专家先验时与冻结模型同批对照（`docs/reports/jue_evolution/`）；5 个种子里业务员层格有 4 个在 W4 前自动换上重训模型（3 个是 W3 结束训练、W4 起用上，1 个从 W2 起）；W4 正确处理率 +1.7 个百分点、错误推荐 −2.0 个百分点。下一步把真实试用的处置与结果回填成追问标签，让追问格在真实环境里在线重训 |
| 结构进化 | 人在没被提问时自发做的决定，说明觉漏提了；据此生成候选的新决策点，经人批准进入决策目录 | 人自发决策、问题被忽略率 | 数据已全量记录，为自动生成新决策点备好了燃料 |

**决策记录是燃料。** 它就是事件日志上的一张只读视图，零额外存储：谁、在什么情况下、对哪个决策点、做了什么决定、后来结果怎样。两条规则让燃料干净：

- **只有人的处置和真实世界的结果能当标签。** Agent 和系统自己的决定只记作当时的情况；标签只认人和世界，学习才不会自己教自己。
- **代谁判断，就用谁那一层的决策来学。** 研发按 L3 判断发起的回问，留在研发层；要让客户侧以后都问，就让「反复回问」成为觉提出 `qi_grant` 的理由，由研发签字授予。觉的学习始终经过契。

**核心指标是「每解决一个客户问题，需要几次研发判断」**，同时看需求质量、必要判断的召回、打扰与真实耗时。模拟报告按时间顺序回放，这条曲线随授予下降，直接体现判断复用的价值；V9 用四角色真实试用再拿一次。校准进化另用一组对照：世界偏离专家先验时，运行中重训的觉与冻结的觉跑同一批问题，标签来自与觉无关的真实结果。

## 7. 讲法：每句话都有力，也都站得住

**本轮聚焦的范围**（精力全部放在判断的形成与复用上）：
- V9 在一个共享试用实例中，由四个真实岗位跑完全链条业务；钉钉、ELN 等入口按试用需要接入，接通一项就展示一项；
- 检索直接复用企业已有的向量检索，Demo 里的关键词检索专门用来演示权限分层与归属；
- 对话以转写文本输入，语音交给企业现成的听记；
- 配方生成与优化留给研发，化言让研发的判断用得更广；
- 积分做成账本和视图，兑换与绩效接企业自己的制度；
- 大模型直接用现成的，化言训练的是发现层小模型。

**推荐说法与依据：**

| 话题 | 这样讲 | 依据 |
|---|---|---|
| 数据来源 | 「官网 177 条公开产品目录已经接入、引文全部核对通过；挂在型号上的机理与案例是模拟数据，V9 换上获准的试用资料」 | `docs/assets/`、`docs/reports/catalog_stats.md` |
| 安全 | 「Agent 结构上拿不到上层知识；人的拼凑行为由觉盯住——两道防线」 | `test_wp_a1`、`test_wp_l`、业务周泄露对照 |
| 验证程度 | 「模拟业务周与失真对照上的相对比较已经跑出；V9 把它交到真实岗位手里」 | `docs/reports/distortion/`、`docs/reports/week/` |
| 概率 | 「发现类由训练模型给出校准概率；推进类由规则到点提出，界面标『规则』」 | `models/jue_k/model_card.md` |
| 觉的能力 | 讲 6 个发现类（追问、回问、机会汇聚、知识冲突、泄露风险、授予请求）；另外 16 个推进与检查模板讲成「流程写成数据」 | 第 6 节 |
| 自进化 | 「觉在运行中重训、自动换上新模型；客户层问什么由契的授予决定，学习只调排序」；「每解决一个问题需要几次研发判断」随授予下降 | `docs/reports/jue_evolution/`、`docs/reports/qi_demo/compare.md` |
| 结构进化 | 「决策目录飞轮的数据已全量记录，为自动生成新决策点备好了燃料」 | 6.2 |
| 研发签字量 | 「研发只签被需要的判断，按需要签，不按资料总量审」 | 主张 7 |
| 数据出境 | 「换上私有化模型，原文全程留在企业内；觉本身就在本地 CPU 上跑」 | 第 11 节、模型网关 |
| 密级 | 「定级按来源，降密由归属人签」 | 3.0′ |
| 资料变化 | 「带依据的结论，资料一改自动挂起复核；真实目录上已有 69 条第 0 天能力挂上了依据」 | 主张 5、`docs/reports/qi_demo/demo.md` |
| 产品经理 | 「产品经理 Agent 承担逐单转述，产品经理回到产品适用范围、产品机会与例外纠偏」 | 第 4 节 |
| 竞品 | 讲「常规 RAG 在这个场景下的结构性局限」，聚焦我们自己的组合 | 1.3 |

**大叙事的落点：**
- 「潜意识」「反射」是好比喻，主张落在「我们把发现层单独做成可训练、可度量、可替换的一层」；
- 决策目录是受治理的闭集：觉在目录界定的范围内主动发现，目录本身可以扩；
- 「跨领域迁移」讲机制与代码骨架的复用：同一套骨架从物流搬到知识协同，Jue-K 在化言数据上重新训练；
- 第 11 节的接入讲「接缝已经在代码里」：唯一检索入口、模型网关配置、总线与签字按钮，指给评委看；
- 创新讲「发现层 + 能力层」的组合：觉负责发现需求，契负责专业能力授权，执行工具按需选用；
- 「零大模型调用」放在效率一栏，讲成「觉全天开着只花 CPU」；
- 每个数字都带来源报告；说「研发退回从 95% 降到 19.5%」时连同「模拟数据上、应升级的 41 张卡」一起说，人工中转节点的「传统」一列讲成按流程定义计数。

## 8. 对外定位

**目标用户**：传化功能化学事业部的业务员、产品经理、研发，下游客户（公开自助入口），以及希望把专家知识沉淀为组织资产的管理层；逐单转述由产品经理 Agent 承担，产品经理回到产品层面的判断。

**给企业的价值**：让一次专业判断成为跨岗位可复用的组织能力，让知识贡献始终有明确归属，让成熟问题逐步减少对研发的重复占用。按增收、降本、控险、资产、管理五类展开，每一类都写明机制、证据和现状，见 `docs/PITCH.md` 第 9 节；路演结构与评委追问也在 PITCH 里。

**30 秒介绍（决赛路演）：**

> 化言要让客户需求直达专业能力，让研发创新重获时间。客户需求不清、跨岗位反复转述，会让专业人员陷入补问和返工。我们提出觉与契：觉持续发现值得处理的问题，Agent 组织依据与方案，人在关键处贡献专业判断，契让这些判断成为后续业务可以使用的能力。销售回到市场，产品经理回到产品，研发回到创新。我们从功能化学的一条需求链路出发，探索企业的决策神经系统。

**10 秒版（架构）：**
> 化言让「此刻该处理什么」由觉持续提出，让「专家的判断能被谁用」由契授予。Agent 接收觉提出的事项，也接受人的委托；人负责专业判断和授予。问对的人，只问一次。

## 9. 长期愿景：企业决策神经系统与通用信息反射

**化言要让组织持续发现问题、调用专业能力、从结果中积累经验；觉要探索智能系统怎样在持续变化的信息中，形成自己的待处理事项。**企业协作提供清晰的产业起点，通用信息反射提供可以长期发展的研究主线。

### 9.1 企业与产业：让专业能力持续积累，让创新重新获得时间

从功能化学的客户需求出发，连接产品适用经验、研发判断、需求转化知识与实际业务结果。销售把精力投入客户与成交，产品经理投入产品全生命周期和新机会，研发投入技术难题与中长期探索。企业每解决一类问题，就增加一份后续可用的能力。

共同发现机制可以继续进入研发实验、生产现场、原料替代与跨产品线协作。每个场景补充自身的业务对象、决策语义、专业工具和训练数据，形成发现、处理与结果反馈的循环。面向上下游，进一步连接客户的使用语言、产品适用边界与研发技术语言，让专业能力触达更广的应用场景。

研发之间的知识共享与贡献记录、专业判断逐步自动化、跨产品线管理分析，都沿这条路线发展。已有的同层 `share` 授予、撤销与记分机制提供共享基础；Agent 草稿、人工修改、签字与实际结果记录，为进一步校准和授权提供依据；V9 的研发负责人视角提供管理分析的起点。

### 9.2 Agent：从持续信息中形成任务

觉作为独立的信息反射层，持续形成候选事项、维持未解决状态、筛选值得关注的内容，再将事项提交给高层模型、Agent 或人。预设机制提供基础反应，经验训练塑造后续关注。它与规划和执行模块协作，研究目标、环境和结果变化后，系统怎样发现接下来值得做什么。

### 9.3 机器人与具身智能：让反射与高层规划协作

物理世界带来连续的感知、时间约束和行动反馈。觉可以沿多模态状态、环境变化发现、反射与规划协作、跨任务迁移继续研究：哪些变化值得深入推理，哪些经验应形成稳定反应，哪些待处理事项需要持续跟踪。研究对象由企业信息进一步扩展到智能体与环境的持续交互。

### 9.4 面向更自主智能的基础问题

通向 AGI 的研究包含这样的长期问题：**拥有目标、记忆与经验的系统，如何持续形成值得思考的事项，并把有限的计算和行动能力用在值得处理的地方？**觉以通用信息反射切入任务产生、注意分配、经验学习和新事项类型形成；契则提供专业能力获得、共享、使用及责任承接的研究视角。

这一愿景应当在对外路演中完整呈现。发展方向与研究目标集中讲清，当前实现与实验进展由证据章节回答。化言让我们从产业中的真实问题出发，把一条需求链路的改进，发展为组织能力与主动智能的长期探索。

## 10. 评委追问

| 追问 | 回应 |
|---|---|
| 这不就是工作流 / BPM 加了个 LLM？ | 工作流负责按图执行；化言回答的是图上画不出来的那部分：哪些事值得判断、什么时候提出、交给谁、判断完怎样授予给别人用。推进规则我们写成了受治理的决策目录，发现层和能力层是化言自己的两层 |
| 觉不就是规则告警？ | 觉输出的是要做的决定（是否追问面料、是否合并需求单），不是指标异常；五类有样本的决策由训练模型打分、概率经过校准；在困难负样本上，业务周里 Jue-K 误报 0/4，常见规则告警 2/4 |
| 为什么不让一个通用大模型每隔几分钟看一遍？ | 成本和稳定性：觉全天开着几乎不花钱，同样的输入给同样的判断，每次判断都记录下来可以复盘、可以重训；大模型只在有问题时出场 |
| 标签和客户都是你们自己模拟的 | 模拟是我们刻意造的尺子：把「传话游戏」变成了可度量、可复现的任务，任何方案都能放进来比，对我们不利的结果也照样公开。V9 再把系统交给四个真实岗位，影子模式开始后真实处置直接变成标签 |
| 一次性翻译的对照组是不是太弱？ | 对照组输在结构上：客户开场白里没说的面料、设备、工艺，翻译得再准也翻不出来，只有追问能补上——换更强的模型也补不上这一块。（补上真实大模型的 G2 列后，在此替换为实测数字） |
| 产品经理是不是被 Agent 取代了？ | 产品经理被解放出来了。产品经理 Agent 承担逐单转述，真人产品经理做只有人能做的三件事：扩展产品适用范围、判断产品机会（签字附商业判断）、纠正被研发退回的转译；这些判断记在本人名下，并直接改变系统下一次的匹配与分流 |
| 研发真的愿意用吗？ | 研发最在意知识贡献能否得到认可与保护。化言让知识有主人：可见归属、不可见内容，引用记分，解密本人审批，被用上一次记一次功。V9 请真实研发来用，拿到第一手反馈 |
| 权限靠提示词能守住吗？ | 权限写在数据通路里：Agent 拿到的内容只含委托人权限内的知识，结构上就看不到；人拼凑机密的行为由觉发现 |
| 企业已经有很强的 RAG 了，你们的检索很简单 | 对，检索交给企业 RAG。RAG 解决「找得到」，化言解决「找到之后谁能看、谁能用、怎么转成研发听得懂的话、依据了谁的知识、该不该有人决定」。企业 RAG 经契的适配器接入当依据来源，文档留在原处；契在上面决定每一层能用什么（替身 RAG 上已实现） |
| 这和 RBAC、知识库权限有什么区别？ | 权限系统管读取与操作。契在业务层把「能读」和「能用」分开：客户层用得上研发授予的判断（追问 pH、推荐对的产品），却读不到判断背后的机理；授予能撤销，撤销后行为立即停止。三态演示就是这个区别 |
| 研发会不会被签字累死？ | 研发只签被需要的判断：公开资料核一遍正确性与归属就能用，跨层授予由觉在真正需要时提出。V9 把各岗位的签字量实际记下来 |
| AI 对客户说错了，谁负责？ | 每一句对外的专业结论都由一条能力渲染出来，能力写明谁授予、依据哪份资料；资料一改，依据它的能力自动挂起交复核；授予人随时可以撤销 |
| 觉的进化是不是自己教自己？ | 标签只认人的处置和真实结果，系统自己的决定永不当标签。客户层能问什么由视图和授予决定：没授予时 pH 根本不在客户层视图里，训练怎么混数据都问不出来（5 个种子、三组都是 0）——学习越不过契。决赛展示两样：授予机制带来的「研发判断次数下降」；运行中重训的觉与冻结的觉同批对照，按层过滤让客户层排序不被研发层结果带偏 |
| 要不要先把知识库治理好？ | 从获准资料和明确场景直接开始：来源、归属、访问范围与适用性在接入时核定，内部来源默认最高密级，边用边治理 |
| 员工要换一个新系统吗？ | 化言嵌进企业既有入口：觉的问题就是钉钉 / 飞书里的待办卡片，签字就是卡片上的按钮。V9 先用 Web 共享试用实例跑通真实业务，接口位置已经留好 |
| 数据出不出企业？ | 大模型全部经过 OpenAI 兼容网关，换成企业私有化部署的模型只改配置；觉是本地小模型，CPU 推理；契只查询、不复制企业文档，结论、能力与账本都在企业内部。编译和研发 Agent 两处换上私有化模型，原文就全程留在企业内 |

## 11. 落地形态：嵌进企业现有的系统

**定位：在企业现有系统上连接需求、专业判断与能力复用。** 企业知识库、协作平台与 ELN 各自管好权限、版本与审批，化言补上它们之间的那一段：需求怎样交接、判断怎样复用。V9 的真实试用把这段缺口指认清楚，适配范围随之确定。

| 企业已有 | 化言怎么接 | 当前 Demo 里的替身 | 代码里的接缝 |
|---|---|---|---|
| **企业 RAG / 向量知识库**（实验报告等） | 作为依据的来源：契经适配器查询；片段密级先按来源设定（公开来源 L0，内部来源默认 L3），再核查来源、归属和访问范围；资料按需经确认与授予变成各层能用的能力，即接即用 | 字符二元组关键词检索 + 种子知识；决赛用替身 RAG 装决赛资料 | 已有：全系统唯一的检索入口 `KnowledgeBase.search`。已实现：适配器 `SourceAdapter`、按人计算的视图 `view(actor)`，引擎只读视图 |

**当前 V9 终点与后续上线路径**：

V9 由四类真实岗位在项目方陪同下处理同一份业务：业务员提交和纠正需求，产品经理判断产品边界，研发形成专业判断与反馈，研发负责人核查进展和例外；一次授权改变后续符合条件的业务，条件变了或授权收回时交回研发判断。一个共享试用实例、按角色进入，权限沿用现有体系，业务随时保存、回来就在，Agent 失败一键重跑。具体工作包与验收见 REPLAN-v9。试用之后的路径：

0. **接入**：从企业的公开资料（产品说明书、官网产品目录）起草产品目录与词表，产品经理和研发逐条审定、认领归属后启动；第 0 天把它们迁成已授予的能力；之后重启都是续跑，工作与授权不丢；
1. **影子模式**：接上钉钉听记与企业 RAG，觉只提问不动作（自动执行也先关闭），问题只推给试点的一位业务员、一位产品经理和一位研发；人照常工作，系统记录「觉提出了什么、人怎么处置、结果如何」；
2. **试点签字**：一个产品线、一个现象族上启用工作面签字与知识归属，研发审定的转译开始沉淀、记分；
3. **重训与扩目录**：用影子期的真实处置数据重训 Jue-K、校准阈值；按被忽略率和人自发决策调整决策目录；
4. **扩场景**：同一发现层接配方优化、缺料预警、设备切换等场景，加的是模板与训练数据。

**当前进度**：架构与业务全流程已在 Demo 中跑通，契在模拟数据上有完整运行证据，177 条公开目录已经接入。V9 把这些能力交到四个真实岗位手中，跑出共享业务、真实操作与结果回流；企业系统集成接通一项展示一项。
