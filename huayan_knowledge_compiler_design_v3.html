01 / ARCHITECTURE & IMPLEMENTATION

系统形态：读取归工具，判断归契

读取工具是替身 RAG 的升级，负责把多格式资料定位、回取和读准；契的编译只做判断，形成候选结论和能力提议，经人签字后生效。内部资料查证由工具直接提供，不进契。

本版根据主办方 OriginalData 资料目录调整实施范围：首版覆盖 Word 报告、PPT 图表、文字 PDF、扫描页、工作簿和实验图片；采用 EmbeddingGemma 2 文本＋视觉检索补充证据召回。这些能力全部落在读取工具一侧，相当于 QI 中“企业 RAG／替身 RAG”的位置：原文、版本、页面和索引以资料侧为准。契按 QI 的分工只经适配器读取原文，保存结论、能力和指回原文的指针；业务缺口和来源变化由觉提出事项，角色 Agent 执行，人签字。[7][21][22]

读取工具 · LOCATE & READ

查到原文，读出数值

文件头识别、原生内容提取与页面渲染；型号、版本、关键词与图文向量定位页面、表格和图片；读取图表的值、单位、图例与相邻条件，逐项带回原始位置。

契 · COMPILE

判断成候选

读数和原文进入契的编译：形成观察、主张与完整条件，对齐现象、产品和槽位，生成候选结论与能力提议。编译只产生候选，从不降密。

契 · CONFIRM & REUSE

签字后复用

研发确认技术结论并授予用途与受众，产品经理批准适用范围。后续需求匹配生效能力；来源变化经觉提出复核。

这份方案遵守的契的规则（以 docs/QI.md 为准）
  1. 契只经适配器访问资料，不导出、不缓存文档；原文以资料侧为准，契保存结论、能力和指回原文的指针。QI · 与企业 RAG 的分工
  2. 契不是检索系统，检索和读取质量由资料侧负责；契自己的组件在运行期不调用大模型。QI · 契不是什么
  3. 依据的密级由来源决定：公开来源 L0，内部来源默认 L3，模型不参与定级。QI · 依据
  4. 编译只产生候选，从不降密；候选不跨层，驱动任何行为前必须经确认，跨层还要授予。QI · 编译
  5. 资料里影响判断的条件不能丢；表达不了的保留原文交专业人员，“没识别到条件”不等于“不限”。QI · 保留实际资料的条件

本方案只写在这些规则之下新增或改动的部分；与 QI、CONTRACTS 的差异集中列在第 17 章。

直接采用的七个决定

决定具体做法
一个应用内的模块沿用 Python、Pydantic、HuayanApp、KnowledgeBase、模型网关和事件日志。解析、读取、检索与编译采用普通函数。
读取前移到工具，判断留在契解析、检索、回取和图表读数属于读取工具，是适配器背后的实现，可以整体换成企业 RAG；从读数形成候选结论、对齐、条件覆盖、lower 与 admit 属于契的编译。
读取结果不是候选读数由模型或解析器产出，只是“原文写了什么、在哪里”；进入契后经编译才成为候选，图表读数由研发对照原图核实后才能确认。
查证不进契有权读取来源的内部工作面直接使用工具查证，答案带出处但不形成知识；正式业务消费通过 view / explore 获得已确认结论和已授予能力。
首版图文召回EmbeddingGemma 2 仅加载文本与视觉编码器，首轮使用 768 维；与型号、版本、关键词检索并用，按第 16 章对照验证增益。
读取与检索分别验收检索返回证据编号和定位；原生数据读取或视觉模型读取数值、单位、图例与条件。引用回到原始证据。
保留现有知识主干资料侧 EvidenceBlock → 契的依据指针 → Candidate IR → KnowledgeUnit → Capability；完整条件、专业确认、用途授予及来源复核贯穿始终。
原文留在资料侧原件版本、页面、裁图、索引放在读取工具的运行目录；契只存依据指针、指纹和片段密级表，编译包放在 ingest 目录；正式状态由应用统一写入 qi_state.json；评测材料独立保存。
第一条交付链路

先从主办方一道图表题完成“问题 → 正确页 → 正确读数 → 可回看的引用”；随后从一份真实实验或试样报告完成“完整条件候选 → 专业确认 → 授予 → 下一次业务复用”。两条链路使用相同的证据、读取与版本记录。

总体架构与实际部署

读取工具在适配器之后，契在适配器之前。内部查证直接用工具；需要复用的判断走契的编译与签字。部署继续保持一个 Python 应用及本地处理产物。

每个模块接收什么，交出什么

模块输入 → 输出实现职责
来源接入
读取工具		资料清单／来源系统 → 固定版本原件登记来源、真实格式、产品、资料类型、归属和版本；记录同一资料的多个文件表示与实际修订。
结构解析与页面渲染
读取工具		原件 → EvidenceBlock、页面和区域图提取正文、表格和原生图表数据；渲染扫描页及含图页面，建立页号、幻灯片号、表格单元格和区域坐标。
证据检索
读取工具		问题＋处理者＋允许来源 → 候选证据按产品与版本过滤，合并关键词和 EmbeddingGemma 2 文本／视觉命中；返回 evidence_id、定位、版本与相关性信息。
证据读取
读取工具		选定证据 → 读数、条件与原始位置优先读取原生表格；图像交支持图片的读取模型。核对图例、轴、单位和相邻条件，将结果逐项关联原始位置。读数不是候选，只作为编译和查证的输入。
内部资料查证
读取工具		已读取证据＋问题 → 带出处答案回答资料明确记载的内容和可核验比较；保持本次资料的条件与版本，按题目输出文字或表格。可读范围按契登记的来源密级计算，答案不进契。
依据登记
契		适配器取回的原文与读数 → 依据指针与密级按来源定级（公开 L0、内部默认 L3），记录 doc_id、版本、块键与指纹；不保存原文。
知识抽取与检查
契 · 编译一		原文、读数与证据编号 → Candidate IR 与审阅包抽取观察、主张、建议和假设；保留全部条件与限制，归一实体和单位，准备重复／冲突材料。
能力提议
契 · 编译二		审阅包 → candidate KU＋能力提议复用 admit，保存证据和 IR↔KU 对应；研发确认，归属人授予，产品经理批准适用范围。
签字与业务门面
契		角色＋当前需求 → 已授权业务结果沿用 view、explore、条件匹配、追问、出口渲染、使用记录、挂起和撤销。
觉
觉		事件与业务状态 → 提交给人的事项从需求、使用和来源变化的事件中发现缺口与冲突，用现有家族提出事项；不检索、不编译，评分只用规则、OneJev 与本地 Jue-K。
角色 Agent
Agent		觉提出的事项 → 准备好的材料调用读取工具定向检索与读取，交契编译候选、准备授予材料，结果沿 request_id 回到原需求；签字由人完成。

模型相似度用于候选排序；读取后的数值和结论引用原始表格、页面或图片区域。内部查证入口使用处理者的来源可读范围，客户层的自动推荐与对外表述继续消费已授权能力。[7][22]

进程与文件的实际安排

第一阶段扩展现有 CLI：对选定资料执行识别、解析、渲染、索引和读取，并写入本次任务目录；导入正式知识状态时沿用应用停止后的离线方式。工作台阶段将同一批函数接入现有后台执行方式，任务产生证据与编译包，HuayanApp 使用当前 KnowledgeBase 导入候选和处理生效。[2]

EmbeddingGemma 2 由本地检索适配器按配置加载文本与视觉部分。视觉读取沿当前模型网关增加图片输入和结构化输出适配；抽取、用量与 caller 标记继续沿用。首版只配置一套实际可用的图文读取模型，通过同一批题目检查数值、条件与引用。[19][22]

页面、文本、读取结果与向量索引作为可重建产物记录来源版本。任务保留处理范围、进度、产物位置和具体错误；修正源文件或读取配置后重跑对应材料。应用负责正式状态和引用关系，评测脚本负责题集与指标。

与现有业务的连接点

专业人员从查证结果中选出值得沉淀的观察或主张，交契的编译形成候选；觉从业务缺口或来源变化中提出事项，角色 Agent 执行定向检索，同样回到契的编译。授权、需求、会话、确认和复核入口继续沿原应用调用，签字由人完成。

切片：索引、证据、抽取三种单位分开

常规 RAG 用同一个文本块同时承担“被检索命中”“交给模型读”“交给模型抽取”三件事：块切小了条件丢失，切大了召回变模糊。本方案把三件事拆成三种单位，用 block_id 和父级关系连接。

单位用途边界与大小
索引单元
检索		被关键词、文本向量和图像向量命中。小而聚焦，一个意思一块。中文正文起点约 200–600 字；表格按“表头＋行组”；图表按区域裁图。每块带确定性前缀（见下）。
证据单元
读取与引用		命中后回扩，交给读取模型和审阅人。按结构边界回扩到父级：一节、一张幻灯片、一张完整的表（含标题、表头、单位行、脚注）或一页。通常不超过一页或一节；被正文引用的“见表 3”“按第 2 节工艺”解析成指针，一起带出。
抽取单元
结构化抽取		交给大语言模型抽取结构化记录或 Candidate IR。短而格式固定的文档（试样报告、实验报告）整份交给模型；长文档按章节。最长的试样报告约 4000 字，整份放得下。

边界按结构切，缺的上下文在回取时按父级和指针补齐，因此不设置固定长度的重叠窗口。固定长度切分只用作没有任何结构的纯文本兜底。

文档级条件头：解决“条件在一处、结果在另一处”

实验类资料的典型结构是：工艺条件写在前面（实验方法、基本信息），结果写在后面的表格或图里，两者不相邻。无论怎么切，结果块里都不会有条件。因此每份文档先抽一次条件头：产品、织物、设备、工艺、用量、浴比或液量、温度、测试标准，然后作为前缀挂到这份文档的所有索引单元上。表格或图有自己的条件（如表题写“30 g/L NaOH 下”）时，再挂一层表级条件，覆盖文档级条件。

  • 确定性前缀优先。 型号、文档类型、章节路径、报告编号、日期直接从元数据和标题取得，不调用模型。按 EmbeddingGemma 2 的文档格式写成 title: 试样报告 TS-xxxx · TF-213HE · 四、试样工艺 | text: …。[22]
  • 模型生成的上下文只补缺。 条件分散、确定性方法拿不到时，才由大语言模型生成一段上下文说明，并标记为“检索辅助文本”，不作为证据引用。[16]
  • 条件头复用到编译。 条件头同时是 Candidate IR 条件字段的初稿，研发审阅的是同一份内容。

验收增加一项证据完整率：回取到的证据单元里，答案所需的数值、单位、条件和图例是否全部在内（第 16 章）。切片的问题多表现为“页找对了，条件缺了”，Recall@5 看不出来，这一项能直接看出来。

一个证据块同时保留“内容”和“原位置”

正文按完整陈述及必要上下文组合；表格按“标题＋表头＋对应行列＋单位＋脚注＋关联工艺段”形成证据包。跨页表格保留同一表编号和表头引用。页面图用于定位整体布局；密集图表再保存区域裁图，并记录它在原页中的位置。文字、表格和图片采用共同的证据标识，以便检索命中后回到同一原始位置。

配方写法74 份用表格（染料、用量、助剂、用量）；37 份用空格排版的纯文本，如常亮、田卫国、王平三的全部报告。用量单位混用 %（owf）、g/L，也有直接写 4.0kg 一缸的。表格直接读；文本版必须由模型解析；单位不能在抽取时换算。
工艺曲线升温曲线是最关键的条件（起温、升温速率、保温时间），多数画在 Word 的绘图对象或文本框里，有的用空格拼成字符画，有的“原工艺曲线：”后面是空的，图在绘图对象中。只有约三分之二的报告能从正文抽到升温速率。常规文本抽取拿不到；需要读 XML 文本框，最后渲染成图交给视觉模型。
基本信息详略写到克重的不到一半（48%），浴比或液量 49%。有人写“150*150 平纹，克重 115g/㎡，液量 3000kg，米数 3000m，门幅 149cm”，有人只写“涤纶布”“东霖染缸”。模型容易把没写的内容补出来，必须防编造。
结论写法崔青龙的 41 份（约四成）高度程式化：“工厂工艺总升温 166min，快速升温 87min，节省 79min，布面无色花……”，常附操作经验，如“不建议前半段超过 2.5℃/min，否则有色花风险”。其他人可能只写一句“布面效果认可，需要在不同颜色不同布种上再试”。也有失败或打平的结果：常亮的一份报告成本高 15%、节省 18 分钟，但色花更严重。程式化部分可用规则核对；操作经验和负例是最有价值的内容，需要单独保留。
长度400 字到 4000 字，相差 10 倍。整份放得进抽取单元，不需要再切。
重复至少一份报告被两人各存一份（舒传奇与陈成的箱包布报告，内容完全相同）。按资料族合并，依据计数只算一份。

目标结构：TrialRecord

抽取目标不是零散事实，而是一条成对记录。“差异”与“结果”放在一起，就是一条可复用经验的原型：在什么共同条件下，把什么改成什么，得到什么结果。每个字段都带出处（章节号＋段落或表格单元格＋原文片段）；原文没写的字段为 null，状态为“原文未记载”。

    cite: Cite

class RecipeLine(BaseModel):
    material: str            # 物料名或产品型号，经批准别名归一
    role: Literal["dye", "auxiliary", "other"]

    start_c: float | None; end_c: float | None
    rate_c_per_min: float | None; hold_min: float | None
    cite: Cite

    recipe: list[RecipeLine]
    curve: list[CurveSegment]

    metrics: list[dict]      # 时间节省、成本差、色花、色差、牢度……各带 cite

章节切分：规则完成，不调用模型

按模板标题（“一、试样目的”“二、基本信息”……）及其常见变体切分，表头栏的报告编号、人员、时间、产品用键值规则读取。识别不到某个章节时，把该章节标为缺失，不让模型猜。三、四两节的配方与曲线一旦切开就各自带上组别标记，后续任何块、读数和引用都携带 arm=A 或 arm=B，避免把原工艺配方当成试样配方。

配方：按写法分流

写法读取方式核对规则
表格版（74 份）直接读单元格，合并单元格展开，表头映射到物料、用量两列。不经模型；单元格位置即出处。
空格排版版（37 份）从 XML 读出保留空格的原始行，交大语言模型解析成配方行。原文行同时保存。每行必须有物料名和数值；单位必须在白名单内；物料名经批准别名表归一，归不上的列为待审；解析出的每个数值都必须能在原文行中找到。

用量单位原样保存。%owf 与 g/L 只有在已知液量、布重或浴比时才能互换，而这几项只有约一半的报告写了。因此换算值作为派生字段，记录换算依据；缺少依据时只保留原值，比较时按同一口径分组。

工艺曲线：三层读取，用总时长交叉校验

  1. 先读 Word 内部 XML。 文本框（w:txbxContent）、绘图对象与形状中的标注文字（如“80℃×20min”“2℃/min”）在 XML 中通常存在，只是常用的 Word 文本读取器不读。这一层用代码完成。
  2. 再解析字符画。 用空格拼出的曲线交给文本模型解析，比交给视觉模型更准。
  3. 最后渲染读图。 真正的线条图、嵌入图片，或标题后为空的情况，渲染成页面图，裁出曲线区域交视觉模型读取，输出分段结构，并标为估读。

曲线统一抽成分段结构：起温、每段的目标温度和速率、保温时间，再由代码算出总时长。报告结论常写“总升温 166min”“节省 79min”，由曲线算出的总时长必须与结论中的数字一致（容差在金标上确定）；不一致的曲线标为 needs_review。这一步用文档内部的冗余信息发现读图错误，不依赖额外的人工。

防编造：没写就是 null

  • 抽取提示明确要求原文未写的字段返回 null，不填写常见值。
  • 抽取后逐字段回查：数值必须能在原文片段中找到（字符串或数值匹配，允许全半角与单位写法差异）。找不到的值作废，并记入 review_items。
  • 文字类字段（如织物组织、设备型号）由 Jev 判断“这个值是否由原文直接写出”，低把握的转人工（第 10B 章）。
  • 缺失条件进入 IR 时状态为“原文未记载”，不等于“不限”，与 QI 的条件规则一致。

结论：四个字段，负例单独保留

崔青龙的 41 份报告句式固定，用正则抽出“总升温／快速升温／节省”等量化结果，再与模型抽取结果对照，两边一致即通过，约四成报告的量化结果可以自动核对。其余报告由模型拆成量化指标、总体判断、操作经验、后续计划四个字段。“布面效果认可，需要再试”对应总体判断“初步成功”、后续计划“扩大验证”。

操作经验最有价值，如“不建议前半段超过 2.5℃/min，否则有色花风险”。进入契后，它是带条件的建议，可以发展成追问升温速率的 ask，或适用能力中的限制条件，因此单独列出、优先给研发审阅。失败和打平的结果标为负例并全部保留，它们是 knowledge_conflict 与 stale_capability 的直接输入，也防止系统只学到“产品总是有效”。

重复：按资料族合并，再比一次记录

内容指纹相同的文件合并到同一资料族，保留全部作者与文件名，依据计数只算一份。抽取完成后再比较结构化记录：编号不同但共同条件、配方、曲线和结果完全一致的，可能是同一次试验的两份记录，标出供人确认。

结构化试样表：查证与汇总的主入口

全部 TrialRecord 汇成一张可重建的结构化试样表（编译目录中的本地表文件），按产品、织物、设备、结果、单位口径筛选。跨报告问题先查表，再回原报告对应章节引用：

  • “TF-213HE 在哪些条件下失败或效果不理想？”——筛选产品与 verdict，列出每份报告及其条件。
  • “锦纶和涤纶上平均节省多少时间？”——按织物成分分组计算，只统计时间字段经核对的记录，并报告参与统计的份数。
  • “报告 XX 的布克重是多少？”——字段为 null 时回答“原文未记载”。

常规检索取前 5 个候选再总结，在原理上答不了需要看全部报告的问题；全量抽取后，这类问题变成查询。向量检索只用于“没给型号、描述模糊”的兜底。

归属：试样表属于读取工具，不属于契

TrialRecord 和试样表是读数，回答“这份报告写了什么”，用于查证和汇总时直接使用，不进契。需要沉淀为专业判断的部分（操作经验、可比条件下的规律、与已确认结论冲突的负例）再经适配器交给契，编译成 Candidate IR 并由研发确认。以后换成企业 RAG 时，这张表也由资料侧提供，契的代码不变。

常规 RAG 的八个失效点与本方案措施

下表列出这批报告会打中常规向量检索 RAG（解析成文本 → 按长度切块 → 向量 top-k → 生成答案）的地方，以及本方案的对应措施。传化现有 RAG 是否存在这些问题，用第 16 章的 10 道对照题实测，不作推断。

失效点常规做法的结果本方案措施
1. 曲线在绘图对象、文本框里只读正文段落，关键条件没有进入索引。XML 文本框 → 字符画 → 视觉读图三层读取，总时长交叉校验。
2. 原工艺与试样工艺混淆两节配方在向量上几乎相同，可能把原工艺配方当成试样配方回答。规则按章节切分，所有块和读数带组别标记；记录为成对结构，差异由程序比对。
3. 条件与结果被切开结果块里没有织物和设备，可能把涤纶上的结论说成通用结论。第二节作为文档级条件头挂到全部块；结构化记录本身就把条件与结果放在一起。
4. 文本排版的配方被打乱连续空格被压缩，物料与用量对应关系丢失。从 XML 读原始行；模型解析后规则校验，数值必须能在原行找到。
5. 单位混用可能直接比较“2% 与 2g/L”。单位原样保存，派生换算记录依据，比较按口径分组。
6. 没写的内容被补出来生成模型给出“常见值”，且不标注是推测。强制 null、逐字段原文回查、Jev 核对、统计编造率。
7. 汇总问题前 k 个候选覆盖不了 109 份报告，结论以偏概全。全量抽取成结构化试样表，汇总变成查询，并报告统计份数。
8. 重复与负例重复文件被算作两条证据；负例不在前 k 个候选中就消失。资料族合并计数；负例全部保留并优先进入冲突审阅。

这些组件单独看业界都有，本方案的不同在于三点组合：以成对对照记录作为知识的基本单位；用文档内部的冗余信息（总时长）校验读图；条件从读取、编译一直贯通到业务匹配，并接到签字与复用链路上。

读数和 IR 的分界

读取工具交出的读数回答“原文写了什么、在哪里”；IR 属于契的编译，回答“这是一次观察还是一条主张、在什么完整条件下成立、还有哪些限制”。读数可以直接用于查证，IR 只在契里流转，经确认后才成为结论。

Knowledge IR：把专业语义保存完整

IR 是编译过程中的结构化记录。它把“说了什么、在什么条件下说、依据在哪里”放在一起，供检查、比较和专业审阅。

真实资料中，图表读取先形成值、单位、对象、条件和原始位置；IR 再将这些字段放入完整陈述。图例、轴标签、表头和工艺脚注与结果保持关联。下方 DEMO-A 及数值为合成机制示例；第 13 章给出主办方资料的实施案例。

四类陈述采用同一结构，保留各自性质

陈述性质含义后续处理
observation · 观察某次实验、试样或客户现场记录了什么结果。保存当次材料、设备、参数、时间与测量口径。
assertion · 主张说明书、报告或专业记录明确写下的判断。保存原文的适用范围、排除项、版本和发布者。
recommendation · 建议资料或专业人员提出了某种操作建议。保存建议的执行前提、适用对象和确认来源。
hypothesis · 假设跨文档分析提出的解释或待验证研究方向。进入专业工作材料，关联支持与相反观察，由后续试验或判断处理。

条件和限制是每类陈述的组成部分。对于本身就是规则的材料，例如“高温工艺需先做小样”，可以形成一条带触发条件的主张，并在授权时落入相应追问或业务准备能力。

引文核对怎样适配读数

一次图文检索怎样执行

  1. 确定问题范围。 从问题与当前任务取得产品型号、资料类型、指定版本和已知工艺条件。明确的型号、版本作为检索约束；没有指定的维度保持开放。
  2. 并行取得候选。 在可读资料范围内运行型号与关键词检索、EmbeddingGemma 2 文本召回、页面或图表图像召回。文字索引携带文档标题、章节和必要表头；图像索引记录原页及区域对应的证据键。
  3. 合并候选并补齐上下文。 先按各路名次合并候选，再按 evidence_id 和同报告关系去重；补齐命中区域所需的标题、表头、脚注与工艺段。首轮采用固定候选预算，便于与第16章的对照配置比较。
  4. 证据门控。 合并后的候选取较宽的预算（如 20 个），由 Jev 对每个候选的文字内容（正文、表格文本或 OCR 文本，连同条件头）回答“是否包含问题指定条件下的答案”，按概率重排后取前 5 个。Jev 不接收图像，纯图片候选保持原名次。这一步补上设计中缺少的重排序（第 10B 章）。
  5. 回取原页并读取。 将命中的原文、原生表格、原始页面和必要裁图交给读取环节，提取数值、单位、条件、比较对象及其位置。检索时生成的摘要保留为检索辅助，答案与候选结论引用原始证据。
  6. 按任务输出。 查证任务返回带出处答案；专业任务输出可继续规范化与检查的记录；业务任务匹配现有能力，缺少依据时把检索结果送入定向编译。

页面检索负责定位完整上下文；图表区域检索补充页面中细小图像的定位。两种命中都回到同一个原页和来源版本。跨页问题合并所需证据后再生成答案，引用逐项落到实际支持该内容的页面或区域。

Jev 的定位与限制

Jev 是 TypeSafe AI 的决策模型，不生成文字，只对开发者定义的问题给出类型化答案和概率；问题分单选（Choice）、打分（Score）、是否（Noul）三类，多个问题在一次请求中并行回答。公开规格：上下文 64,000 token，其中状态加最长问题不超过 32,000 token；主要语言为英语；不支持直接的多模态输入。[27]

公开评测显示：在评分标准封闭、证据随请求给出的核对上，Jev 与大语言模型评审准确率相当（95.5% 对 94.3%），概率校准更好（Brier 0.043 对 0.054），成本约五分之一，延迟约十分之一；需要通读长文、标准开放的评判，大语言模型更贴近专家。[28] 另一组测试中，Jev 几乎确定的样本上大语言模型只有约 3% 会改答案，Jev 接近五五开的样本上改答率达 71%，说明它的概率能标出难题。[29]

因此 Jev 放在“证据已经在手、问题封闭”的核对与分流位置。它对本方案的主要价值不是省钱，而是有校准的把握：高把握的自动通过，低把握的交人，研发只看需要看的部分。它碰不到切片、条件关联和读图这几处正确率的上限。

阈值与边界

  • 先校准，再放行。 首轮不设自动通过，全部结果与人工判断对照。用第 16 章的金标（读数级、字段级样本，数百条）画出可靠度表，只有当某个概率区间的实际正确率达到要求（如 ≥98%）时，该区间才允许自动通过；其余一律交人。
  • 中文要单独验证。 Jev 以英语为主，本批资料全是中文专业术语。状态中的字段名和问题可以用英文写，原文保持中文；是否可靠以校准结果为准。
  • 只喂文字。 图像先由视觉模型或 OCR 转成文字，Jev 只核对文字层面的一致性。
  • 不越过契的边界。 Jev 的输出只作为候选材料和审阅提示：不定密级、不降密、不签字，不让能力生效；业务匹配中“条件是否满足”仍由条件比较函数决定，不由 Jev 的把握代替（与 QI 一致）。
  • 不进觉的训练。 按现有约定只有觉学习；Jev 的结果只进入统计报告。

大语言模型的使用约束

  • 所有抽取都要求逐字段给出原文片段；没有片段的字段不进入结果。
  • 每次抽取保存模型名、版本、提示版本和输入的 block_id，结果可重现、可对比。
  • 读数模型在第 16 章对照中固定下来后，查证、编译与验收使用同一个配置。
  • 契的组件在运行期不调用大语言模型；大语言模型只出现在读取工具和契的编译期。

批准别名后更新映射版本，重跑引用该别名的候选归一；新增条件字段时增加类型、单位和比较方式，并补到需求抽取与展示。已有生效能力保留原范围；新增映射影响专业主张或授权范围时，生成修订候选交对应归属人处理。每次审定记录涉及的候选和结论，便于后续查看影响。

更新与失效：让后续使用跟随当前依据

复用已有指纹检查、挂起、撤销和 qi_review，补上版本化证据与按引用范围进行的增量处理。

更新按以下顺序执行

  1. 登记新版本。 由资料维护人显式刷新选定来源，保存新 SourceRevision。
  2. 匹配引用块。 按文档键、结构位置与规范化内容匹配旧块和新块。内容比较同时覆盖正文、单位、表头、脚注与条件段。
  3. 定位受影响对象。 从块到 IR / KU 的索引找到结论，再沿现有 Capability.based_on 找到使用能力。
  4. 更新业务状态。 引用内容发生变化或被撤回时调用既有 evidence_changed()；结论进入候选，相关能力挂起，现有推荐通过门面重新匹配。[4][6]
  5. 准备专业复核。 使用 qi_review 展示旧、新原文、结构化差异与受影响业务。
  6. 按复核结论处理。 原主张与原范围继续成立时确认新依据并恢复；内容或范围修订时建立新的结论和能力，完成对应授予与批准。
变化类型系统动作专业人员看到什么
文件换页或无关段落改变，引用证据内容相同更新版本定位，保留既有生效状态。新版本与旧版本的相同引用。
引用数值、单位、工艺限制或结果改变挂起依赖能力，提出复核。逐字段差异、原文对照、当前受影响情境。

新增资料给出不同条件下的观察保存新观察，按条件归组。不同情境的结果对比。
同条件新证据与现有结论冲突形成冲突材料，进入既有专业处理。支持与相反证据、记录时间及来源。

“内容保持一致”由明确的规范化比较识别，例如空白和排版变化；专业语义有修改的块进入复核。更新只重处理改变的资料和相关候选，保留其它编译产物。当前 recheck() 的入口继续使用，内部增加版本与引用块比较即可。[2]

修订与历史记录

原结论和原情境经复核后仍成立，更新依据引用并记录复核事件，恢复原能力。结论内容、用途或授权范围改变时，创建新 KU / Capability，保留旧对象及其历史使用；产品适用范围按现有职责重新批准。

为支持历史回看，复核事件补存旧、新证据引用和来源版本；使用事件补存当次能力、结论及实际采用的证据版本。历史业务通过该次事件中的引用显示原依据，后续复核沿用同一能力编号时也能回看当时的资料。

已有推荐依据发生变化时，继续调用 V9.6a 的重匹配路径：能找到另一条当前有效且覆盖该业务的能力，则更新推荐依据；找不到时撤回当前自动推荐并把需求交回专业流程。已经发生的试样、推荐和使用记录按当时状态保存。[6]

图文索引随来源版本更新

来源修订后，先重新生成受影响页面和证据块，再更新关键词与图像／文本索引；新增的查证结果引用新版本。历史查证和已确认结论保留当次原页或固定版本指针。候选索引按资料族合并重复表示，正式 KU／Capability 的挂起与复核继续沿已有引用关系执行。

嵌入模型、权重版本或维度改变时，重建对应向量集合，并让查询使用相同配置；保留来源、证据键与正式知识编号。来源修订和模型配置变化分别记录，复核由实际证据内容变化触发。

觉的位置觉从事件与业务状态中提出事项，Agent 执行检索与编译，人签字；觉的评分不使用 EmbeddingGemma 与大模型网关。每个事项都有对应家族、执行者和签字人，处理结果回到原需求。
知识组织与条件沿用产品 ID、批准别名、条件化 IR、引用索引与问题分组；先贯通真实案例需要的枚举、常用数值比较和区间。条件满足、待补、冲突三类需求得到正确结果，新增观察保持原有计量口径。
切片索引、证据、抽取三种单位分开；按资料类型以结构边界切分，不设固定重叠；每份文档挂确定性前缀与条件头。证据完整率与 Recall@5 一并报告；切片对照显示前缀与条件头的增益。
试样报告规则切模板章节，按写法分流抽取，形成成对 TrialRecord；汇总成结构化试样表作为查证与汇总主入口；操作经验与负例交契编译。20 份分层金标的准确率、漏抽率、编造率与曲线一致率；10 道对照题逐题结果。
模型分工嵌入模型只负责召回；大语言模型负责抽取、读图和组织答案；Jev 负责封闭问题的核对与分流，先校准再放行；人负责签字。每个模型调用都可追溯到输入块、模型版本与提示版本；Jev 放行区间有可靠度表支撑。
来源与版本同一报告的不同格式关联为一个资料家族；实际修订版本分别保存。来源版本、页／区域、IR、KU 和 Capability 通过普通索引关联。重复副本合并检索与证据计数，版本变化准确定位到受影响结论与能力。
持久化与运行保留 qi_state 和现有业务文件；编译目录保存页面、证据与候选，向量作为可重建的本地索引。CLI 启动处理，工作台沿现有后台任务方式接收产物。一个项目内能够完成资料处理、查证、审阅和复用，索引可依据已保存证据重建。
知识生效复用确认、授予、批准、复核与撤销入口；原文、结构化结果和用途集中呈现在审阅工作面。每条生效能力有确认结论、明确受众、使用范围和可回看的依据。
验收资料题目表和预期答案放在评测侧，原始资料形成检索证据。真实业务案例与合成机制样本分别标注，资料缺项逐题登记。交付可复现的检索对照、图表查证和专业复用记录。

为什么既不把编译并进读取工具，也不把读取工具并进契

  1. 换企业 RAG 时契不动。 传化已有 RAG，阿里做过向量化。读取工具在适配器之后，整体可以替换；编译和签字规则留在契里，换实现时只需按指纹重新映射依据指针。
  2. 契的承诺保持成立。 QI 规定契不缓存文档、运行期不调用大模型、契里的内容都经人签字。查证和读图放进契会同时破坏这三条；把编译并进工具，则会让候选和密级规则散到两处。
  3. 对外讲清分工。 读取工具回答“资料里写了什么”，这一项用 35 题成绩证明；契回答“这条经验谁认了、能在什么条件下用、什么时候失效”，这是化言与检索系统的区别。

交给执行 Agent 的完成定义

资料层面：能够识别主办方资料中的真实格式，恢复题目所需的文字、表格、页面和图片，并保存完整定位与来源版本。查证层面：能从用户问题定位可读证据，读取图表数值与条件，给出支持结论的引用。编译层面：能把真实观察整理成可审阅 IR，接入现有专业确认和契。业务层面：专业确认与授予后，后续需求按完整情境使用能力，资料修订与新问题能够进入复核和定向编译。

交付材料：列明实际修改文件、运行方式、资料与模型版本、题目答案及来源状态、A/B/C 检索结果、图表读取问题、真实案例的确认与复用记录，以及各阶段用时和模型用量。原件与客户标识保存在授权资料目录，代码和演示使用适合交付的机制样本。

本轮开发以适配器为接缝
